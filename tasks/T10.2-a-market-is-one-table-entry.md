# T10.2 — A market is one table entry, and weather gets a seam at all

Size: M · Prereqs: T7.9 · Files: `server/server.py`, `server/providers_*.py`,
`server/tests/`, `docs/ARCHITECTURE.md`

Requires: none

## Goal

Adding a row of prices to the panel means editing `server/server.py` in **four places that are
not near each other**, found by walking it in [the design review](../docs/DESIGN-REVIEW.md):

- `producers` in `App.quotes()` — the fetch
- `wanted` in `App.quotes()` — the expected row count, which drives the partial-market badge
- `_history_producer()` — an `if/elif/else` on the market name
- `key_for()` — which field identifies a row, with FX as the exception

A contributor who finds three of the four gets a market that renders with no sparkline, or one
whose stale badge never fires. Both look like the panel working.

Twelve lines away, `server/actions.py` does the same job with a table that every reader consults
— `describe()`, `run_action()` and the 501 path all read it, and none of them changed when the
microphone press became four commands. **This task applies the pattern this codebase already
has**; it is not a plugin system and not a provider base class.

## Steps

1. **One `MARKETS` table**, entry per market, carrying: the loader, the history loader, the
   config key, and the row key (`symbol`, or `pair` for FX). `producers`, `wanted`,
   `_history_producer` and `key_for` all read it and stop branching.

2. **Adding a market is one entry plus one `providers_*.py`.** Assert it: a test that walks the
   table and fails if a market is missing any of the four, so the next contributor cannot land a
   half-wired one.

3. **Weather gets a seam.** Today `App.weather()` calls into `providers_openmeteo` four times by
   name, so a second provider is an `if` inside a method — the worst answer of the four
   contributor walks, and the exact question T7.9's manual check asks a stranger. Weather is
   two-step (geocode, then forecast) and does not fit the market table; it needs its own small
   one, or a documented reason why one provider is enough. **Either answer is acceptable and it
   has to be written down.**

4. **Do not unify the five provider modules' call shapes** beyond what the table needs. They
   differ because the upstreams differ — a token here, a symbol-per-request limit there — and
   flattening that into one interface would put the differences somewhere less honest.

5. `docs/ARCHITECTURE.md` gains the table as the answer to "where does a provider go".

## Acceptance

```bash
python -m unittest discover -s server/tests -t .
grep -q 'MARKETS' server/server.py
! grep -q 'def key_for' server/server.py
grep -q 'MARKETS' docs/ARCHITECTURE.md
python scripts/check_links.py --skip-remote docs/ARCHITECTURE.md
make check
```

The third line is the one that bites: `key_for` is the fourth place, the easiest to miss, and it
should not survive as a function of its own.

## Manual check

Ask somebody who has not seen the server where a fourth market goes. One file and one table entry
is the answer this task exists to produce.

## Notes

- The partial-market badge is the subtle one. `wanted` exists because brapi sends one symbol per
  request, so a 429 on one ticker returns the others and looks like success. Whatever the table
  becomes has to keep that.
- This is a refactor with no behaviour change, so the existing server tests are the safety net.
  If they do not catch a mistake made during it, that is a test gap worth its own finding.
