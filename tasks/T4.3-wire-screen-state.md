# T4.3 — Wire state to the panel and the screen  🏁 Milestone B

Size: M · Prereqs: T4.2, T2.2 · Files: `MainActivity.java`, `web/js/app.js`

Requires: phone (on adb), PC server reachable, a dark room

## Goal

The product's actual behaviour: PC off, screen dark; PC on, panel back.

## Steps

1. On every transition, call into the page:

   ```java
   webView.evaluateJavascript("window.onPcState(" + online + ")", null);
   ```

2. `web/js/app.js` — on `false`, render pure black `#000000` and hide everything; on `true`,
   restore. On AMOLED, black pixels are off pixels.
3. Native brightness, on the UI thread:

   ```java
   WindowManager.LayoutParams lp = getWindow().getAttributes();
   lp.screenBrightness = online ? -1f : 0f;   // -1 = system default, 0 = minimum
   getWindow().setAttributes(lp);
   ```

   Window-scoped, so no permission is required and the system brightness is untouched.
4. Log `screen=sleep` / `screen=wake` on each change — the E2E suite depends on these markers
   (TT.6, [ADR 0009](../docs/adr/0009-testing-strategy.md)).

## Acceptance

With the app running on the phone and the server up on the PC. **Clear the buffer before
logging off, not after** — the app notices within one poll interval, and a clear that lands
after the transition erases the marker being asserted on (see TT.6).

```bash
adb logcat -c && <log off the PC> && sleep 20 \
  && adb logcat -d -s DeskPanel | grep -q 'screen=sleep'
```

Log back in, same order:

```bash
adb logcat -c && <log in on the PC> && sleep 20 \
  && adb logcat -d -s DeskPanel | grep -q 'screen=wake'
```

## Manual check

**Step 3 was not implemented, and the manual check below is moot as a result.** T4.3 and T4.4
landed in the same wave (2026-09-19), so brightness was never made the mechanism: the code went
straight to real screen sleep and left `screenBrightness` at the window default of `-1f`.
Writing the dim-to-black path first would have meant writing code whose only purpose was to be
deleted an hour later by the task immediately after it. The dark-room observation this section
asked for belongs to T4.4's manual check, which is where it now lives.

Kept as written below, because what it was watching for is real and comes back the moment
anyone reinstates the fallback: `screenBrightness = 0f` is the minimum controllable brightness,
not off, and some MIUI builds clamp it higher than asked. If the panel is ever visibly glowing
in a dark room, that is the evidence, and it is an argument against the fallback rather than
for it.

The panel must also return on log-in without anyone touching the phone.

## Notes

- This is the milestone worth reaching before quotes and weather. It is the riskiest part and
  the most satisfying to see working.
- If black is not black enough, the interim workaround is an opaque black `View` over
  everything. T4.4 supersedes both approaches if MIUI cooperates.
- **The poller stops when the screen does, and this task is where that becomes a contradiction.**
  T4.2 starts polling in `onResume` and stops it in `onPause`, which its own task file asked for
  and which is right while the screen is held awake. But invariant 3 says offline means clearing
  `FLAG_KEEP_SCREEN_ON` and letting Android sleep — and the screen going off delivers
  `onPause`/`onStop` to the foreground Activity. The moment this task does what it exists to do,
  the loop that would notice the PC coming back is the thing it switched off, and `screen=wake`
  can never fire. Nothing in T4.2 is wrong today only because `setKeepScreenOn(true)` is still
  unconditional in `onCreate`; this task removes exactly that.

  So the first decision here is not about brightness, it is about what owns the poll loop once
  the Activity is not resumed. `onStart`/`onStop` instead of resume/pause is not enough on its
  own — the screen going off reaches `onStop` too. The candidates are a foreground service, an
  `AlarmManager` schedule, or a partial wakelock held only while offline, and each one trades
  against the battery budget in `docs/DEVICE-CARE.md`, since the phone is on battery precisely
  when the PC is off. Whatever is chosen belongs in an ADR amendment: ADR 0005 describes the
  screen policy and says nothing about who is awake to enforce it.
