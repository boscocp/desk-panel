# T7.7 — Opening the repository: contributor strategy and the settings that back it

Size: M · Prereqs: T7.6 · Files: `CODE_OF_CONDUCT.md`, `SECURITY.md`, `LICENSE`, `CODEOWNERS`,
`.github/ISSUE_TEMPLATE/config.yml`, `docs/MAINTAINING.md`

Requires: the `gh` CLI authenticated against the repository, and admin rights on it

## Goal

Decide what this repository is to other people *before* it is public, and then set the switches
that make the decision real. The failure this avoids is the common one: a repo flipped public
with no stated scope, which then collects issues asking for features its owner never intended to
maintain, and goes quiet.

## Steps

1. **Say what the project accepts.** One short section at the top of `CONTRIBUTING.md`, written
   as scope rather than as apology. A defensible position for this project: bug reports and
   device reports are wanted from anybody; themes and panel layouts are the natural contribution
   surface (`web/themes/`, once [T6.7](T6.7-theme-boundary.md) lands); new data providers are
   welcome behind the existing normaliser shape; and anything that touches the three invariants
   needs an ADR before a PR. Whatever is decided, write it down — the point is that a reader
   knows in thirty seconds whether their idea belongs here.

2. **Device reports are the contribution this project actually needs.** Almost everything
   expensive here was a vendor behaviour discovered on one Redmi. A short, structured "it works /
   it does not on my device" report — model, Android version, which of the screen behaviours
   held — is worth more to this codebase than most code, and nothing currently invites it. Give
   it an issue template and a place in the README.

3. **`SECURITY.md`** — where to report privately, and the honest scope: this is a LAN appliance
   holding an API token in a local file, so the interesting reports are about the token leaking
   into git or into the APK, and about the server binding wider than intended. Say what is out of
   scope too; a panel with no authentication on a home LAN is a design decision, recorded in
   ADR 0004, not a vulnerability.

4. **`CODE_OF_CONDUCT.md`** — Contributor Covenant, with a real contact address in it. A file
   with an unfilled placeholder is worse than none.

5. **`LICENSE`** — confirm one exists and that the README names the same one. [T7.3](T7.3-pre-public-review.md)
   also asks for this; whichever lands first does it, and the other verifies it.

6. **Repository settings, applied with `gh` and recorded in `docs/MAINTAINING.md`** so they can
   be restored or audited:

   - branch protection on `main`: PRs only, CI required green, no force push
   - the CI workflow from [TT.9](TT.9-ci-workflow.md) as the required check, by name
   - labels that match how this repo already thinks — one per phase area, plus `device-report`,
     `needs-adr`, `good-first-issue`
   - issue template chooser with a link to Discussions for "will it run on my phone" questions,
     which are not bugs
   - `CODEOWNERS` naming the maintainer, so review is requested automatically

7. **Seed three `good-first-issue`s that are genuinely small**, from the existing backlog rather
   than invented. A label with nothing behind it is a broken promise on the README.

8. **`docs/MAINTAINING.md`** — the other half of contributing, for whoever holds the repo: what
   a PR must have before merge, that reviews are applied before the merge rather than after, how
   a wave branch is named and squashed, and what to do with a PR that is good but unverifiable
   without the hardware. Say plainly that the maintainer is one person with one device.

## Acceptance

```bash
test -f CODE_OF_CONDUCT.md && test -f SECURITY.md && test -f LICENSE && test -f CODEOWNERS
! grep -rniE '\[(INSERT|TODO|YOUR)[^]]*\]' CODE_OF_CONDUCT.md SECURITY.md
python scripts/check_links.py CODE_OF_CONDUCT.md SECURITY.md docs/MAINTAINING.md
gh api "repos/{owner}/{repo}/branches/main/protection" --jq '.required_pull_request_reviews != null'
gh api "repos/{owner}/{repo}/branches/main/protection" --jq '.required_status_checks.contexts | length > 0'
test "$(gh issue list --label good-first-issue --json number --jq 'length')" -ge 3
python scripts/check_acceptance.py
```

The second line is the one that catches the usual failure — a Code of Conduct shipped with
`[INSERT CONTACT METHOD]` still in it, which tells a reader the document was never meant
seriously.

**Lines 4 and 5 cannot pass while the repository is private**, found 2026-09-29 (wave 36): on
GitHub Free, both the branch-protection and the rulesets endpoints answer 403, *"Upgrade to GitHub
Pro or make this repository public"*. Everything else in this task is applied. The protection
command is in `docs/MAINTAINING.md`, ready to run, and it is the first thing to do after the flip.
Then these two lines pass and the row can close.

## Manual check

Read the repository's front page as a stranger who arrived from a search result. Within one
screen it has to answer what this is, whether it runs on their phone, and where to start.

## Notes

- Do this **after** [T7.3](T7.3-pre-public-review.md)'s secret audit, never before. Branch
  protection on a repository whose history contains a token protects nothing.
- Every `gh` command in step 6 belongs in `docs/MAINTAINING.md` as a runnable line. Settings
  clicked in a web UI are lost the first time the repository is transferred or recreated.
- Scope written narrowly is not unfriendly. An honest "this project does not accept X" saves a
  contributor's evening; a silent repository that never merges their PR does not.
