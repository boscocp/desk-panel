# T7.5 — Running it locally, for a contributor with no phone and no LLM

Size: M · Prereqs: T3.12, T7.4 · Files: `docs/RUNNING-LOCALLY.md`, `docs/REQUIREMENTS.md`,
`scripts/check_requirements.py`, `README.md`

Requires: none — that is the point of the task

## Goal

Someone clones this repo on a laptop, with no Redmi, no Windows PC, and no model writing the
commands for them. They should reach *something moving on screen* in under ten minutes, and know
exactly which parts of the project they cannot exercise and why.

The repo already answers this in pieces — `docs/BUILD.md` for the APK, `docs/TESTING.md` for the
suites, `docs/SERVER-SETUP.md` for the PC half — and nowhere from the top. There is no page that
starts at `git clone` and ends at a panel rendering.

## Steps

1. **Three tiers, in the order of what they cost.** The document is organised by what the reader
   has, not by what the project contains:

   - **Web only** — open `web/` against the mock payload in a browser, run `node --test`. No
     Docker, no Python, no phone. This is where a contributor changing the panel's look lives,
     and it is most of the interesting surface.
   - **Web plus server** — `python server/server.py` with a config, real quotes in the page.
     Standard library only, so there is nothing to install beyond Python itself.
   - **The full rig** — Docker for the Android toolchain, a phone on adb, the PC on the LAN.
     Say plainly that this tier needs hardware, and that a contributor without it can still have
     a green `make check`.

2. **`docs/REQUIREMENTS.md`** — the floors and where each one is enforced, not a wish list:
   Python (`tomllib`, so 3.11 is the floor), Node for the test runner, Docker for everything
   Android, and the JDK and SDK versions that live **only inside the image** (ADR 0003). For each
   one: the minimum, the reason it is the minimum, and the file that pins it.

3. **The dependency inventory, with the honest headline.** This project's dependency list is
   nearly empty by design — no framework in `web/`, standard library only in `server/`, no build
   step. Write that down as a *constraint that contributors must not break*, and list what is
   actually there: the container image's toolchain, the Gradle plugins, the two key-free
   upstreams. A PR that adds `requirements.txt` is a design change and should read as one.

4. **`scripts/check_requirements.py`** — the versions quoted in the document match the versions
   the build actually uses, read from `docker/Dockerfile`, `android/app/build.gradle.kts`, the CI
   workflow and `server/`'s floor. Documentation that drifts from the build is worse than no
   documentation, and this is the only kind of prose in the repo a script can keep honest.

5. **Every command in the tutorial is a Makefile target where one exists.** `make check`,
   `make test-web`, `make apk`. A tutorial that teaches the long form teaches something the repo
   will change without telling the reader.

6. **README gets a three-line Quickstart** pointing here, above the existing "Getting started".

## Acceptance

```bash
python scripts/check_requirements.py
python scripts/check_links.py docs/RUNNING-LOCALLY.md docs/REQUIREMENTS.md README.md
grep -q 'RUNNING-LOCALLY.md' README.md
make check
python scripts/check_acceptance.py
```

`make check` is in the list because the tutorial's first tier promises it passes on a machine
with no phone attached. If that stops being true the tutorial is wrong, and it is the tutorial's
acceptance that should say so.

## Manual check

Follow the document on a machine that has never built this project, from `git clone`, without
skipping a step and without filling a gap from memory. Every gap found is the defect.

## Notes

- Write for someone reading it at 23:00 after a day job. Short numbered steps, the expected
  output quoted under each, and no paragraph that has to be parsed before the next command.
- Do not send the reader to `CLAUDE.md`. Those files are instructions for agents and are written
  in a register that will read as bizarre to a human contributor. Anything in them a human needs
  belongs in this document instead.
- The phone-shaped parts belong in [T7.4](T7.4-phone-setup-doc.md); link, do not restate.
