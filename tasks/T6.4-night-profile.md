# T6.4 — Night profile

Size: S · Prereqs: T4.3, T6.1, TT.1 · Files: `MainActivity.java`, `PanelService.java`,
`NightWindow.java`, `DataPayload.java`, `web/js/app.js`, `web/js/host.js`,
`web/css/style.css`, `web/themes/neon/theme.css`, `server/server.py`

Requires: phone (on adb) and a reachable PC for the brightness half; node for the predicate;
Firefox for the page's half

**The `Files:` line above was amended when the task was done, and so was the acceptance.** The
original named three files and the original acceptance was
`adb logcat -c && sleep 90 && grep -q night=on`, which cannot pass against a correct
implementation: the marker is emitted on transitions, like every other marker in this app, and
with nothing changing there is nothing to log. The transition has to be driven. See
**The acceptance this task shipped with could not pass** below.

## Goal

Dim the panel during configured night hours. Less glare in a dark room, less heat, less panel
wear.

## Steps

1. `night_start` and `night_end` (24h) are already in `server/config.example.json`. Serve
   them with the data payload, as `night: {start, end}` in the T1.2 contract, so changing them
   does not mean rebuilding the APK.

   **The phone's clock decides.** The window is configured on the PC, but `isNight()` compares
   it against the device's own local time — the panel is looking at you from the desk, and the
   phone is the thing whose screen dims. Say so in the code, because the opposite reading (the
   PC's clock, sent as a boolean) is just as plausible and produces a panel that dims an hour
   late after a timezone change.
2. Native side: during night hours set `screenBrightness` to a low value — around `0.15f` — and
   restore `-1f` outside them.
3. Web side: drop glow intensity and stop animations at night. Glow is what makes a dark room
   feel lit.
4. Re-evaluate on every data refresh, not on a separate timer. One less thing running.
5. Night mode applies only while **online**. Offline the screen is asleep and none of this
   matters.

## Acceptance

No phone, no PC:


The page's half, in a real browser, for both themes:

```bash
python e2e/layout/check_night.py
python e2e/layout/check_night.py --theme plain
```

And the device's half, which is the backlight and is the one thing no browser can see:

```bash
python e2e/check_night_marker.py
```

The predicate `isNight(now, start, end)` is pure and tested as one, including the window that
wraps midnight — the case that is always wrong first. `NightWindow.java` is the same predicate
for the backlight, tested the same way, and the two are tied together by one property asserted
on both sides: the shipped window is night for exactly 540 minutes of the day.

### The acceptance this task shipped with could not pass

`adb logcat -c && sleep 90 && grep -q 'night=on'` waits for a line a correct app is right not
to write. `night=` is emitted on transitions — the contract every marker in this project keeps,
because `state=`, `screen=` and `dormant=` would otherwise be a line a second — so ninety
seconds of an unchanging panel produce nothing at all. An implementation that *did* pass it
would be one logging the marker on every refresh, which is the thing the contract forbids.

The transition has to be driven, and the only input a test can reach is the window in the PC's
config. `e2e/check_night_marker.py` walks it — day to night, then night back to day, asserting
both edges — and runs the server itself, because changing that config means restarting it and
restarting somebody's running server is not a script's to do. Both edges, because either is
free to be wrong alone: an app that logged on every refresh passes the first for ever, and one
that never cleared its state passes the first and fails the second.

## Manual check

Set `night_start` to a minute from now: the panel dims without going dark. Set it back and it
restores.

## Notes

- Put the "is it night" decision in `web/js/format.js` as a pure function taking a clock time
  and the two bounds. It has to handle the wrap across midnight, which is exactly the kind of
  thing that is wrong until it is tested.
- Do not tie this to the weather API's sunrise data. A fixed schedule is predictable, and
  predictable is what you want from something on your desk.

### Written while doing it

- **The predicate ends up existing twice, in two languages, on purpose.** `isNight` decides
  what the panel looks like and `NightWindow.java` decides what the backlight does, and the
  two mechanisms do not meet: one is a CSS custom property, the other is
  `WindowManager.LayoutParams.screenBrightness`, which no page can reach. Pushing a boolean
  from Java into the page would make the browser — where there is no Java and `js/mock.js` is
  the whole feed — the one place the profile could not be developed. Both read the same two
  bounds out of the same payload against the same device clock.
- **`DataPayload.merge` rebuilds the payload key by key, so a key nobody names there never
  reaches the phone.** The first build had a correct server, a correct page, a correct
  predicate on both sides, and no `night` in the merge — and the panel simply stayed bright,
  with nothing in logcat to say why. The device acceptance is what found it; there is now a
  JVM test for the copy, and one for it surviving `withBattery`, which is a second rebuild.
- **Heat outranks night, and it has to be a precedence rather than two vetoes.** The two
  blackouts in `applyScreenState` are independent because each has its own mechanism; night
  and the thermal cutoff share one, so `applyBrightness` holds the order in a single
  expression. A night that outranked heat would light the backlight on a phone at 46 degrees
  because the clock said 23:00.
- **The page's half is `animation: none`, not the blackout's `animation-play-state: paused`,
  and the panel is visible here, which is the difference.** A paused pulse is one number
  frozen at its brightest until morning. Core only sets the night attribute while the panel is
  visible, so the two rules never apply at once and a card blacked out at night still resumes
  where it left off.
- **The night window survives the offline stretch, unlike the prices.** It is configuration
  rather than a measurement, and it is exactly as true at midnight with the PC off as it was
  at ten — which is what makes a 23:00 login come up dim instead of at full brightness for the
  minute until the first payload lands.
