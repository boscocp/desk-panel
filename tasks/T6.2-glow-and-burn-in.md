# T6.2 — Glow, micro-animations and burn-in mitigation

Size: S · Prereqs: T6.1 · Files: `web/js/format.js`, `web/js/host.js`, `web/css/style.css`,
`web/themes/neon/`, `e2e/layout/`, `docs/THEMING.md`

Requires: node and Firefox on the host; Chrome for the manual check

**Paths amended after T6.7.** Glow is a palette, so it lands in a theme; `web/js/app.js` holds
no element name at all, and the two lines it used to be written in are gone.

**Amended again while doing it, and the amendment is the task's one real decision.** The
burn-in shift is **core**, not a theme's. T6.7's own rule is that a promise about *hardware*
lives in `css/style.css` — that is why the blackout is there, and why T6.6 put the animation
pause beside it — and a theme that forgot to move would look perfectly fine and quietly etch
the display, which is the same failure in the same shape. So `offsetFor(now)` decides in
`format.js` (pure, tested), `js/host.js` writes the answer into two custom properties on every
tick, and one rule in `css/style.css` translates `body > *`. A theme owes it nothing, which is
the point; `docs/THEMING.md` says what it owes it anyway, and all three are "do not"s.

**Read T6.6 before starting.** There is now a second motion available on a card — an
overflowing list walks slowly through its rows — and T6.6's notes ask that the two not fight.
Two independent movements on one card are visible in a way neither is alone.

## Goal

The neon look, plus the thing that keeps a static panel from etching itself into an AMOLED.

## Steps

1. Glow via `text-shadow` and `box-shadow` in the accent colours. Restraint matters — heavy
   shadows on a large panel cost real GPU time and make text mushy.

   **Done, and the restraint is the deliverable.** Four things glow and nothing else: the clock
   at 16px of blur (it already did), the weather temperature at 12 (the other number read from
   across the room), a tight halo on the cards' borders at `--glow-dim`, and the STALE badge,
   which is the one glow meant to be *noticed*. Nothing under 24px gets a text-shadow at all —
   a blur under a 20px glyph does not read as light, it reads as a font slightly out of focus,
   which is the opposite of T6.3's whole argument.
2. Subtle transitions on value changes. A brief colour pulse on update reads well; anything
   longer than ~300 ms becomes tiring on a panel you sit next to all day.

   **"On update" is the trap, and this step is really about not falling into it.** `onData` is a
   full replacement: every row in every card is rebuilt once a minute whether or not a number
   moved. A pulse keyed on the payload arriving looks perfect in a browser — `mock.js` jitters
   every price every three seconds — and on the desk, with the upstream down and the server
   serving last-good values, it flashes the whole panel once a minute while STALE sits in the
   corner saying nothing has moved.

   So it is keyed on the *rendered text*, read out of the markup a moment before it is
   replaced. `e2e/layout/check_pulse.py` is that assertion, and it came from this step.
3. **Burn-in mitigation:** shift the whole layout by a few pixels every few minutes. A CSS
   `transform: translate()` on the root container, cycling through a small set of offsets, is
   enough. Keep the amplitude small enough not to be noticeable and large enough to matter.

   Three constraints the shipped cycle has that this paragraph does not, each of which came out
   of writing it:

   - **Every offset is up and left, never down or right.** A transform past the bottom or right
     edge becomes the document's scrollable overflow; the panel is exactly one screen, and a
     page that can scroll is a page with somewhere to hide a row (T6.6).
   - **The count runs from the epoch, not from midnight.** Counting from midnight was the first
     cut and it fails this task's own last note in one sentence: the PC is on for roughly the
     same hours every day, so every offset would land under the same glyphs at the same hour
     for ever. From the epoch, a day is 360 steps against a cycle of seven and the phase
     advances three positions a night.
   - **No transition.** A glide would be a second motion on a panel that already has one and
     that T6.6 asks not to fight — and a transition is not an animation, so the blackout's
     `animation-play-state: paused` would not stop one caught in flight.
4. No animation while offline. The screen is asleep; anything running is wasted battery.

   **Already done, in wave 14.** T6.6 put the first animation on this page and `web/css/style.css`
   gained `animation-play-state: paused` under `:root[data-panel="dark"]` at the same time —
   core rather than per-theme, because it is the page's half of a hardware promise exactly as
   the blackout beside it is, and it covers the thermal cutoff as well as offline.
   `check_blackout.py` asserts it. Anything this task animates inherits the rule; there is
   nothing left to write for this step, only something not to override.

## Acceptance

```bash
node --check web/js/app.js
node --check web/js/host.js
node --test "web/test/**/*.test.js"
python e2e/layout/check_layout.py
python e2e/layout/check_layout.py --theme plain
python e2e/layout/check_pulse.py
```

The burn-in shift is a pure function of the clock — `offsetFor(now)` — and it is tested as one
in `format.js`, which is what makes "the offset changes" assertable without watching a screen
for ten minutes.

**The two browser lines are not decoration, and the first one is new work on the harness.**
`check_layout.py` used to measure the panel wherever the wall clock happened to have put it,
which after this task means checking the worst position one run in seven: a card that only
escapes the viewport at `(-4,-3)` would have been a check that failed on a Tuesday. It now
drives the page through every position in the cycle and measures each, and asserts two things a
single measurement cannot — that core's offset actually reaches the glass, and that the panel
moves at all. Delete the rule in `css/style.css` and it fails on the first; stop calling
`shift()` in `host.js` and it fails on the second. Both were run.

`check_pulse.py` is the other half, and it is a check of a theme rather than of the panel —
`plain` deliberately does not pulse. It fails if a fresh mount pulses, if a payload with one
changed value pulses anything else, if an identical payload pulses at all, or if the pass runs
longer than ~300ms. All four were mutation-tested.

One thing here is deliberately *not* asserted: what any of it looks like. A `box-shadow` grep
would say the declaration exists and nothing about whether the panel reads well, and T6.1's
acceptance already carries the warning about mistaking one for the other.

## Manual check

In Chrome, left for ten minutes with devtools open: no console errors, no growing memory. Ten
minutes is two and a half burn-in steps, so the shift is visible in that window if you watch
the panel's left edge against the window frame.

**Outstanding, and it is the half no harness reaches:** the glow and the pulse on the device,
at 50cm, on the real AMOLED with Roboto Condensed rather than the host's wider fallback. The
harness measures geometry and drives Firefox; whether a 10px halo reads as light or as a smudge
is a question for eyes at the desk.

## Notes

- Prefer `transform` and `opacity` for anything animated — they stay on the compositor. Animating
  `top` or `left` forces layout on every frame, which on this hardware is noticeable.
- The offset cycle should be irregular enough that it does not settle into a pattern that itself
  burns in.
