# T7.2 — Wireless adb from the container

Size: M · Prereqs: T0.1, T2.4 · Files: `docs/INSTALL-PHONE.md`

Requires: phone (on adb), same Wi-Fi as the PC

## Goal

A development loop with no cable: build in the container, install straight to the phone.

Resolves one of the open questions in `STATUS.md` — the Android docs confirm wireless pairing
but say nothing about doing it from inside a container.

## Steps

1. On the phone: Developer options → **Wireless debugging** → *Pair device with pairing code*.
2. From inside the build container:

   ```bash
   adb pair <ip>:<pair-port>      # enter the 6-digit code
   adb connect <ip>:<port>
   adb devices                    # expect: device
   ```

3. If pairing fails, the likely cause is mDNS not crossing the container boundary. Try
   connecting to the explicit `ip:port` without discovery.
4. **Fallback:** extract `platform-tools` into `tools/platform-tools/` in the repo and run adb
   from the Windows host. A zip, no installer, no PATH change, `tools/` is gitignored, and
   deleting the folder removes it completely — the clean-host promise survives either way.
5. Record whichever route worked in `docs/INSTALL-PHONE.md`, and update the open question in
   `tasks/STATUS.md`.

**Answered 2026-09-23 (wave 22), by measurement, for the container half — which turns step 4
from a fallback into the recommendation:**

- The image *does* ship adb (`platform-tools`; 1.0.41 / 37.0.1), so "can the container run adb"
  was never the question. The question is whether it should own the device, and it should not.
- `host.docker.internal` is a **Docker Desktop** invention and does not resolve on Docker
  Engine. `docker/compose.yml` now maps it with `extra_hosts: …:host-gateway`. That line is a
  prerequisite of TT.7's `make connected`, which was written against a name that did not exist
  here.
- **adb cannot bind to one interface.** `adb -a -L tcp:172.17.0.1:5037 nodaemon server` exits
  with `could not install *smartsocket* listener: listening on specified hostname currently
  unsupported`. The only server a container can reach is `adb -a` on `0.0.0.0:5037`, which is
  unauthenticated adb for the whole LAN. With that server running, a container does attach to
  it — so the route works, and costs more than it is worth on a desk whose whole security model
  is "the network is the boundary" (T3.6's note).

What is still open is the phone half: pairing needs *Developer options → Wireless debugging →
Pair device with pairing code* tapped on the device, and the acceptance below needs an
authorised device. Neither can be done from a checkout.

## Acceptance

```bash
adb devices | grep -qw device
test -f out/desk-panel-release.apk
adb install -r out/desk-panel-release.apk
adb logcat -c && sleep 10 && adb logcat -d -s DeskPanel | grep -q 'state='
```

`adb devices` prints "List of devices attached" and exits 0 even with nothing plugged in, so
the grep is the assertion, not the command.

## Notes

- Pairing is a one-time step per host; the connection persists until forgotten or revoked.
- The APK-over-browser route from T3.6 remains the primary install path. This is for the
  development loop, and for `adb logcat`, which the E2E suite needs.
- Some access points block mDNS. If pairing fails on your network and works on a phone hotspot,
  that is the cause.
