# T7.9 — A design review of the seams, before strangers arrive

Size: M · Prereqs: T7.6 · Files: `docs/DESIGN-REVIEW.md`, `docs/adr/` (new records if the review
produces one), `tasks/` (a task file per finding worth fixing)

Requires: none

**After [T7.6](T7.6-contribution-guide.md) and before [T7.3](T7.3-pre-public-review.md), and the
order is the point.** `CONTRIBUTING.md` states the rules this repository says it follows — the
why in comments, logic out of Android classes, `format.js` pure, no dependency without an
argument. This task is the first time anybody reads the **whole codebase** asking whether that is
true, with a written rule to measure against. Run the other way round, the review would be one
person's taste.

Asked for from the chair on 2026-09-27, in those words: is there a wave that looks at design
patterns, dependency inversion and decoupling, *thinking about external contribution*.

## Goal

Find the places where a contributor who did not write this code will **put their change in the
wrong file**, and fix the seam rather than the symptom. Produce `docs/DESIGN-REVIEW.md`: what was
looked at, what was found, what was changed, and — most valuable — **what was deliberately left
alone and why.**

## What this task is not

Read this section before starting, because the failure mode here is enthusiasm.

- **Not a pattern hunt.** A factory, a builder or an interface introduced because a book names it
  is ceremony this project pays for twice: once to write and once for every reader who has to ask
  what it is for. The repository's own comments are the standard — a structure that needs a
  paragraph to justify its existence is usually wrong, in either direction.
- **Not a framework, a container, or a DI library.** [ADR 0006](../docs/adr/0006-no-framework-web-layer.md)
  and [docs/REQUIREMENTS.md](../docs/REQUIREMENTS.md) make the empty dependency list a design
  decision. Dependency *inversion* here is constructor arguments and injected functions — which
  the codebase already does in two places, see below.
- **Not a rewrite.** Any finding that cannot be stated as "a contributor would do X, and the code
  makes X land in the wrong place" is out of scope.
- **Not a licence to contradict an ADR.** A finding that requires one is a new ADR, argued, with
  the rejected option written down.

## Where to look, and what "good" already looks like

The project has three worked examples of the seam this task is about, and they are the yardstick:

- **`server/actions.py`** injects `runner` and `which`, so every test asserts on an argument list
  without a mixer, a desktop session or a subprocess. That is dependency inversion with no
  vocabulary attached.
- **`web/js/format.js`** is pure functions, which is why its tests need no browser.
- **`PcState` and `ThermalState`** hold the decisions that an `Activity` would otherwise hold,
  which is why they run on the JVM.

The question for every other file is the same one: **what does testing it require, and is that
requirement essential or accidental?** A class that needs a device, a socket or a clock to test
is where a contributor's change will go wrong.

## Steps

1. **The four layers, one pass each**, each ending in a written paragraph rather than a verdict:
   `web/`, `server/`, `android/`, and the scripts plus harness under `scripts/` and `e2e/`.
   For each: what the units are, what depends on what, and where a change of the kind a
   contributor is likely to make would have to touch more than one layer.

2. **Name every seam that crosses a layer**, because those are the ones that break silently. The
   payload shape is the one this project has already paid for twice — `mock.js`, the server's
   responses and `DataPoller` all have to agree, and `DataPayload.merge` rebuilds it key by key,
   which shipped the same bug in T6.4 and again in T8.2. A comment warns about it. **The
   question this task must answer is whether a comment is the best that can be done**, or whether
   one shared description of that shape could make the class of bug impossible. If the answer is
   "a comment is the best available", write down why, and that closes it for good.

3. **Coupling that is real, measured rather than felt.** For each layer, list what a change to it
   forces elsewhere: adding a quote provider, adding a theme, adding a panel row, adding an
   action. Each of those is a plausible first contribution — walk them. Anything that touches
   more than two files for a one-line behaviour change is a finding.

4. **Where the tests are hard to write, and why.** The repository's test discipline is unusually
   strong, so the places without tests are informative: they mark the code that is hard to
   construct. That is a design statement, not a gap in effort.

5. **One task file per finding worth fixing**, added to `tasks/STATUS.md` like any other work, and
   **no fixing inside this task** beyond what a single review commit can honestly carry. A review
   that also rewrites is a review nobody can check.

6. **Say what is fine.** The document must have a section of things that look wrong to a fresh
   reader and are deliberate, with the reason — Java over Kotlin, no framework, standard library
   only, one Activity, `SharedPreferences` instead of a database. Half the value of this document
   for a contributor is knowing which oddities are load-bearing.

## Acceptance

```bash
python scripts/check_links.py docs/DESIGN-REVIEW.md
grep -q 'deliberately left alone' docs/DESIGN-REVIEW.md
grep -qE 'web/|server/|android/' docs/DESIGN-REVIEW.md
python scripts/check_status.py
python scripts/check_acceptance.py
make check
```

The second line is the one that cannot pass by accident: a review with no "left alone" section
did not look hard enough to have an opinion about what to keep.

## Manual check

Hand `docs/DESIGN-REVIEW.md` and `CONTRIBUTING.md` to somebody who has written Android or Python
and has never seen this project, and ask them where they would add a second weather provider.
If they name the wrong file, the review missed a seam and that is the finding.

## Notes

- Comparing against the guide is the method: for every rule `CONTRIBUTING.md` states, find the
  place in the code where it is *not* true and decide whether the code or the rule is wrong.
  Both answers are legitimate and the second is more common than people expect.
- The reviews that have caught the most in this repository were adversarial about one specific
  claim, not broad. Prefer ten named questions over a general read.
- Keep it in one document. A design review split across five files is read by nobody, which is
  the same reason `CONTRIBUTING.md` is one file.
