# T3.13 — One command to run after a pull

Size: M · Prereqs: T3.8, T3.9, T3.12 · Files: `scripts/after_update.py`, `docs/UPDATING.md`,
`README.md`, `.gitignore`

Requires: nothing. No phone, no Docker, no elevation — `Stop-ScheduledTask` and
`Start-ScheduledTask` on a task you own need no admin.

**Asked for from the chair on 2026-09-22**, after the failure below cost an evening: a note in
the repo saying what has to be done on Windows when there is an update, and macOS later. Then,
in the same breath and it changes the deliverable: *"de preferência um script sh ou algo do
tipo, que seja determinístico pra n gastar token, só eu executar."* A page you read is a page
you skim; the ask is for something that decides.

## The failure

The phone had a fresh APK and two new cards — the moon (T6.13) and the chance of rain (T6.15) —
and both were empty. Everything anybody would check was innocent: `/ping` answered, the panel
was lit, the config was valid, the tests were green, the APK was current.

The Scheduled Task had started at **00:31:18**. The pull rewrote `server.py` at **00:32**. The
process serving the phone was one minute older than the code it was supposed to be serving, and
nothing in the system had any reason to mention it. `probe.py` would have exited 0 throughout.

Two things follow, and the second is the interesting one:

1. A pull is not a deploy. The launcher's action points into the checkout, so the *files* update
   and the *process* does not — it holds what it loaded at your last login.
2. **"Does it answer" is the wrong question.** Every existing check in this repo asks it:
   `probe.py` asks it, `/ping` asks it, `verify_login_scope.py` asks why it answers. None of
   them can tell yesterday's server from today's.

## Goal

`python scripts/after_update.py` — exits 0 when the process now serving the phone is running the
code that is on disk, non-zero with a reason otherwise.

## Steps

1. **Ask the launcher; never spawn the server.** The Windows branch reads the Scheduled Task's
   action, the Linux branch the systemd user unit. A `pythonw` this script started would answer
   just as well and would outlive the desktop — invariant 2, and the one bug this repo cannot
   allow itself to ship. Restart is `Start-ScheduledTask` / `systemctl --user restart`, always.

2. **Every path comes from the launcher, not from the repo.** `install_task.ps1` bakes an
   absolute `--config` into the action, so the config this script validates has to be the one
   the server will actually read. `parse_task_arguments` reads quoted runs rather than
   `.split()`, because the default interpreter lives under `C:\Program Files`; it returns `None`
   rather than a half-filled dict, since acting on a guessed config path means validating one
   file and restarting a server reading another.

3. **Wait for the socket between stop and start.** `allow_reuse_address` is off on Windows
   deliberately — a second server must fail loudly rather than quietly serve half the requests —
   so a start issued before the old process has released the socket dies with `WinError 10048`
   and leaves **nothing** running. Discovered by doing it: a `Stop` and `Start` back to back
   took the server down entirely, and the surviving process was the one that had just been
   asked to die. `wait_for_port` polls the socket in both directions; if something still holds
   the port after the timeout the script refuses to start rather than make it worse.

4. **The check that would have caught it**: `/weather` is compared against the key set the
   tree's **own** `normalise()` produces, imported rather than hardcoded, plus `moon` when
   `providers_usno.py` is present. Next time a field joins the payload this check starts
   requiring it with nobody editing the script, and a server left on yesterday's code fails it.

5. **The test suite does not gate the restart, and the first cut had this wrong.** Blocking on
   any failure reads as prudence and is not: the new code is already on disk and the next login
   will load it whatever this script does. The pull deployed it; the restart only decides
   whether the phone waits until tomorrow. Refusing would leave the panel on stale code *and*
   the tree broken. Failures are reported and still set the exit code. A broken **config** does
   block, because that is the one thing that stops the server coming back up at all.

6. **`make check` is not the suite it runs.** There is no `make` on the Windows host and putting
   one there would breach ADR 0003 by the same argument that keeps the JDK off it. The Android
   suite needs Docker and is reported as skipped rather than silently dropped.

7. **The APK half is a proxy and says so.** `web/` and `android/` cannot reach the panel without
   a rebuild, so the script diffs them against the last commit it saw run cleanly here, recorded
   in `.after-update-state.json` (gitignored — two machines on the same commit have rebuilt
   different things). The repo cannot know what is installed on the phone; a first run reports
   `unknown` rather than inventing a verdict.

8. **macOS reports `unknown`, on purpose.** T3.10 is `blocked` and the plist has never run on a
   Mac. `docs/UPDATING.md` records the three things that join the script when one exists —
   reading `ProgramArguments`, `launchctl kickstart -k`, and no socket wait — so the next person
   is not re-deriving it.

9. **The pure functions carry every decision**, and `--self-test` covers them on a box with no
   task, no systemd and no Mac — the split `server/CLAUDE.md` asks of the request handler, and
   the precedent `verify_login_scope.py --self-test` set.

## Acceptance

```bash
python scripts/after_update.py --self-test
python -m unittest discover -s server/tests -t .
python scripts/check_acceptance.py
python scripts/check_harness_notes.py
node --test "web/test/**/*.test.js"
python -c "import sys; sys.path.insert(0,'.'); from scripts.after_update import expected_weather_keys as e; sys.exit(0 if {'moon','precipProb'} <= e(True) else 1)"
python -c "import sys; sys.path.insert(0,'.'); from scripts.after_update import needs_rebuild as r; sys.exit(0 if r(['server/server.py','web/js/app.js']) == ['web/js/app.js'] else 1)"
python -c "import sys; sys.path.insert(0,'.'); from scripts.after_update import parse_task_arguments as p; sys.exit(0 if p('\"C:\\\\Program Files\\\\x\\\\server.py\" --config \"C:\\\\Program Files\\\\x\\\\config.toml\"')['config'].endswith('config.toml') else 1)"
! grep -q "Popen" scripts/after_update.py
```

The last line is the invariant, not a style rule: nothing here may background a process. The
only two ways the server is allowed to start are the launcher's own, and a `Popen` in this file
would be the beginning of the second way.

## Manual check

On the next real pull, the report's `payload` line is the one to watch — it is the only line
that distinguishes a server that answers from a server that answers *with the new code*.

## Notes

- **A restart empties every cache, and it is visible from the chair.** Three verification runs
  in a row made the FX sparkline vanish and the moon drop from 85% to 79% -- the series has a
  six-hour interval so a cold start has nothing to draw, and the moon answers from the synodic
  mean until the USNO refresh lands. Both self-heal within a minute. Recorded in
  `docs/UPDATING.md` because the script's core action causes it, and both symptoms read as
  defects.

- **`python_for` was caught by its own self-test.** It round-tripped through `Path`, so
  `/usr/bin/python3` came back as `\usr\bin\python3` on Windows — a path corrupted by a function
  whose job was to leave it alone. It now returns the argument untouched when it is not a
  `pythonw`.
- **The exit codes are `verify_login_scope.py`'s three**, and failure outranks unknown for the
  same reason: a machine that both failed a check and could not read another is broken, and
  reporting 2 would file it under "have a look sometime".
