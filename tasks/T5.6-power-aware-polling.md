# T5.6 — Power-aware offline polling

Size: M · Prereqs: T4.3, T5.3, T5.4 · Files: `PcState.java`, `PcPoller.java`,
`PanelService.java`, `Markers.java`

Requires: phone (on adb), PC server stoppable

## Goal

Stop the offline wake lock draining the phone.
[ADR 0014](../docs/adr/0014-poll-loop-outlives-the-screen.md) holds a `PARTIAL_WAKE_LOCK` for
the whole offline stretch and says plainly that this is
affordable **only** because the board keeps USB powered with the PC off — "offline means
charging with the screen off". The ADR asks for this branch to be written the day that stops
being true, and names its three parts: drop the wake lock while discharging, fall back to
`AlarmManager` for a sparse probe, and take `ACTION_POWER_CONNECTED` as the immediate signal
that the PC is back.

**It has stopped being true, and not for the reason the ADR predicted.** Measured 2026-09-19 on
the real desk:

```
Max charging current: 100000      # 100 mA, i.e. 0.5 W
level 22 at 12:44  ->  level 20 at 13:11
```

The port supplies 100 mA and the phone loses about 4.4% an hour **while reporting `status: 2`,
charging** — roughly 220 mA net on a 5000 mAh cell, so the draw is on the order of 320 mA. ErP
Ready is not the culprit: USB is live right now, with the PC on. The supply is simply smaller
than the draw.

**`Charge counter` does not move on this device.** It sat at exactly `1188000` across eight
samples over six minutes, so it is reported coarsely and cannot give a rate. Whoever repeats
this measurement should take `level` over time and nothing else, and allow for its 1% quantum:
two levels twenty-seven minutes apart is the measurement above, and it is an estimate, not a
meter reading.

That makes the offline stretch the one place the arithmetic can still be won. Screen off, a
partial wake lock costs something like 60–120 mA against the 100 mA coming in, which is roughly
break-even: the phone hovers instead of recovering. Drop the lock and the same hours become
net-positive, so the panel charges overnight rather than starting each morning lower than the
last. That is the whole point of this task, and it is a bigger win than the ADR's own framing
of it.

## Steps

1. `PcState` learns whether the device is on mains, and answers one new pure question:
   **is the poll loop dormant?** Dormant means offline *and* discharging — the one state where
   an in-process schedule must not exist at all. Keep it a pure function so TT.5 covers it on
   the JVM: no clock, no Android, no waiting.
2. `PanelService` already receives `EXTRA_PLUGGED` on every `ACTION_BATTERY_CHANGED` (T5.4), so
   the power state needs no new source. Feed it to `PcPoller`.
3. While dormant: **do not hold the wake lock, and do not reschedule in-process.** `PcPoller`
   stops booking its own next probe and says so; the service releases the lock and arms an
   `AlarmManager` probe instead.
4. The alarm is a **backstop, not the mechanism.** Inexact and allow-while-idle, around 15
   minutes — Doze clamps anything tighter to roughly nine minutes anyway, so a tighter number
   would be a promise the platform does not keep.
5. `ACTION_POWER_CONNECTED` is the **fast path, not the guarantee.** Where the phone's power
   dies with the PC, it arrives the moment the PC returns and the alarm never matters. Where it
   does not — a wall charger, or a board that keeps USB live with the PC off — no power event
   ever fires and the alarm is the only mechanism. Treat fifteen minutes as the worst case that
   has to be acceptable on its own, rather than as a number the fast path excuses. Ending
   dormancy and probing must be **one step**, not a flag one receiver clears and another reads:
   plugging in fires `ACTION_BATTERY_CHANGED` too, and the delivery order between two receivers
   is not ours to depend on.
6. A probe while dormant needs the CPU for its own duration. The alarm's implicit wake lock
   only covers `onReceive`, and the probe is blocking I/O on another thread, so take the lock
   **with a timeout** for the probe and let the platform drop it — a lock released by a callback
   that never runs is the leak this whole task is about.
7. Leaving dormancy must be immediate and complete: cancel the alarm, and go straight back to
   the 2s cadence rather than waiting out an interval.

## Acceptance

`dumpsys battery unplug` is what makes this testable without touching the cable: it overrides
what the framework reports and fires the real `ACTION_POWER_DISCONNECTED`, which is the layer
the app reads. `dumpsys battery reset` puts it back and fires `ACTION_POWER_CONNECTED`.

```bash
docker compose -f docker/compose.yml run --rm build ./gradlew test
```

Then, with the PC server stopped so the panel is offline:

```bash
adb shell dumpsys battery unplug
adb logcat -c && sleep 90 && adb logcat -d -s DeskPanel > /tmp/desk-panel-dormant.log
grep -q 'dormant=on' /tmp/desk-panel-dormant.log
test "$(grep -c 'ping=' /tmp/desk-panel-dormant.log)" -le 1
! adb shell dumpsys power | sed -n '/^Wake Locks: size=/,/^$/p' \
    | grep -q 'DeskPanel:offline-poll'
```

Dormancy is entered, the in-process loop is silent for a minute and a half where it used to
manage six probes, and the wake lock is gone from the platform's own list.

**The `sed` is the assertion, not decoration.** `dumpsys power` prints a *history* of ACQ and
REL events as well as the locks currently held, so a bare `grep` for the tag matches a lock
that was released hours ago and the check fails on a phone that is behaving perfectly. The
range from `Wake Locks: size=` to the blank line is the held-lock listing and nothing else.
Proved to discriminate on the device before this task was written: offline while charging it
prints `PARTIAL_WAKE_LOCK 'DeskPanel:offline-poll'`, and online it prints only
WindowManager's `SCREEN_BRIGHT_WAKE_LOCK`.

Then, still with the server stopped, power comes back:

```bash
adb logcat -c && adb shell dumpsys battery reset && sleep 10 \
    && adb logcat -d -s DeskPanel > /tmp/desk-panel-repowered.log
grep -q 'dormant=off' /tmp/desk-panel-repowered.log
grep -q 'ping=' /tmp/desk-panel-repowered.log
```

Power returning probes immediately instead of waiting out the alarm — within 10s, against a
backstop of 15 minutes, which is the difference this step exists to prove.

Then, while dormant, the handover itself: the schedule has to be somewhere, and "somewhere" is
an alarm that actually exists.

```bash
adb shell dumpsys deviceidle whitelist | grep -q dev.bosco.deskpanel
adb shell dumpsys battery unplug
adb logcat -c && sleep 20 && adb logcat -d -s DeskPanel | grep -q 'dormant=on'
adb shell dumpsys alarm | grep -A5 'walarm\*:dev.bosco.deskpanel.DORMANT_PROBE' \
    | grep -q 'power_pending=--'
adb shell dumpsys battery reset && sleep 6
! adb shell dumpsys alarm | grep 'walarm\*:dev.bosco.deskpanel.DORMANT_PROBE' \
    | grep -qv 'reason='
```

Armed while dormant, **armed for when it was asked for**, and gone once power returns.

**The whitelist line is an assertion, not setup, and the `power_pending` one is why.** A first
version of this block checked only that the alarm was *present*, and it passed on a device where
the alarm was deferred to **three days** — requested `+12m51s`, scheduled `+3d0h12m51s`, listed
as armed the whole time. The deferral is Android's battery optimisation, and the app was not
exempt from it: `docs/INSTALL-PHONE.md` step 2 is MIUI's own list and step 6 is Android's, and
only step 6 governs this. `power_pending=--` is the platform saying it did not push the alarm
out, and the whitelist check names the cause when it did.

That combination is this project's recurring failure in its most expensive form: an assertion
that passes while the thing it is about is broken, guarding the one mechanism that has to work
when nobody is watching. **`grep -v 'reason='` is the assertion**, for
the same reason the `sed` above is: `dumpsys alarm` prints a per-uid *history* whose entries
carry `reason=alarm_cancelled`, so a bare grep for the tag matches an alarm that was cancelled
minutes ago. Measured — the naive grep finds three lines both while the alarm is armed and
after it is cancelled, and this one exits 0 then 1.

**This replaces an assertion that could not pass.** The obvious version of this step is to stop
the server, go dormant, and wait for `state=online` within 60s with no power event. But the
whole point of dormancy is that the only thing keeping time is a **15-minute** alarm, so a 60s
window fails on a panel doing exactly what it was built to do. Recovery without a power event
is minutes away by design, and the thing worth asserting in seconds is that the alarm is
registered, of the right type, and cancelled when it should be. That the alarm then *delivers*
is the long check below.

## Manual check

**The alarm delivers.** Go dormant with the server stopped and leave it for twenty minutes: a
second `ping=` has to appear without any power event, roughly fifteen minutes after
`dormant=on`. This is the mechanism of last resort — the one path that runs when the USB never
changes, because the phone is on its own charger while the PC is off — and it is the only part
of the design that cannot be checked in seconds.

**The overnight number.** Leave the phone overnight with the PC off and read the level in the
morning. The number to beat
is the one this task was opened for: **20% and falling at 4.4% an hour.** Net-positive by
morning is the win; merely flat is still a win against a wake lock held all night.

## Notes

- **On this desk, dormancy may never trigger — and that is a property of the desk, not a bug in
  the branch.** Dormant means `EXTRA_PLUGGED == 0`. The measurement above found USB *live* with
  the PC on, and whether it survives the PC being **off** is untested here, because the dev box
  is the PC: shutting it down ends the session that would observe the result. If the board keeps
  USB live overnight, the phone stays "plugged", never goes dormant, and the wake lock is held
  all night exactly as before — so **the overnight win this task was opened for is conditional,
  and the condition is unverified.** Check it with the PC off and the phone still on the board's
  USB: `adb shell dumpsys battery | grep 'USB powered'`. What is *not* conditional is that the
  branch is now written, tested, and correct for the state it names.
- **Keying dormancy on net discharge instead of `EXTRA_PLUGGED` was considered and rejected.**
  It would make the branch fire on this desk, where the phone drains while plugged. But
  `Charge counter` is frozen on this device and `current_now` is not readable, so the only
  signal left is the level falling — minutes of latency and a 1% quantum — and the sign
  convention of `BATTERY_PROPERTY_CURRENT_NOW` varies by OEM. A heuristic with a threshold, on a
  reading this device reports badly, to decide whether the panel may sleep. The honest fix for a
  phone that drains while plugged is a power source that supplies more than 100 mA.
- **This does not fix the online case, and nothing in software can.** With the screen on the
  panel draws more than this port supplies, so it discharges whenever anybody is looking at it.
  That is a cable and a power source, not a code change: a port or charger that will actually
  negotiate more than 100 mA. Check `Max charging current` in `dumpsys battery` after changing
  it — if it still says `100000`, nothing was gained.
- **Do not reach for `setExactAndAllowWhileIdle`.** It wants `SCHEDULE_EXACT_ALARM` or
  `USE_EXACT_ALARM` from API 31, and exactness buys nothing here: the mechanism is
  `ACTION_POWER_CONNECTED` and the alarm is only the fallback.
- **Register the power receiver dynamically, not in the manifest.** The process is alive — it is
  a foreground service — so there is nothing to gain, and implicit broadcast restrictions since
  API 26 make the manifest route the fragile one.
- ADR 0014 must record that this branch now exists and why the trigger was not the one it
  predicted. The ADR is the file that says this decision rests on an assumption about one desk;
  it should also say what happened when that assumption was measured.
