# T9.1 — The next meeting, under the clock

Size: XL · Prereqs: T8.2, ADR 0015, T3.12 · Files: `server/providers_calendar.py`,
`server/oauth.py`, `server/config.example.toml`, `web/js/format.js`, `web/themes/neon/`,
`web/themes/plain/`, `docs/SERVER-SETUP.md`, `docs/adr/0016-calendars-are-personal-data.md`

Requires: the phone on adb and a reachable PC for the manual check; a Google account and a
Microsoft 365 account for the contract test, which is opt-in and skipped by default.

**This is a future improvement, not scheduled work.** Asked for on 2026-09-20 and deliberately
placed after every existing task: it is the first feature that puts *personal data* on a panel
whose server has no authentication, and both of the things it needs to sit on — the shortcut
strip and the threat model — are themselves unbuilt. Do not start it before T8.2 is `done`.

## Goal

The sidebar shows the next event from the owner's calendars — Google Calendar and Microsoft
Outlook together, merged and sorted, the soonest one wins — under the clock, in the
`#shortcuts` strip, between the mute-audio and mute-mic buttons.

One line, read at a glance from across the desk: what it is and how long until it starts.

## Where it goes, and why that is the hard part of the layout

The requested position is *between the two buttons* in `#shortcuts`. That strip is 56px tall
and laid out `grid-auto-flow: column` with equal columns, sized in T6.1 for two 56px touch
targets on a phone at arm's length (T8.2). Three equal columns makes both buttons too narrow
to hit and gives the event about 90px, which is not a line of text.

So the strip has to become two rows — buttons on one, event on the other — or the event has to
take the full width above them. **Decide that against the device, not on paper**, and
re-run `python e2e/layout/check_layout.py` for both themes afterwards: the sidebar is the one
column with no slack, and T2.3 already put a section off the bottom edge once.

Whatever it becomes, it is markup, so it belongs to a theme (T6.7) and `plain` gets its own
answer to it.

## Steps

1. **ADR 0016 first, and it is the reason this task is XL.** The server is LAN-only and has no
   authentication, deliberately (ADR 0004), and ADR 0015 states the threat model that made
   `POST /action/{id}` acceptable under it. That model was written about actions that are safe
   to repeat. This is different in kind: an event title is personal data about people who are
   not the owner, `/quotes` is unauthenticated, and anyone on the Wi-Fi can read it. The ADR
   has to say what the panel is allowed to show, what the server is allowed to keep, and what
   it does with a refresh token — which is a credential that grants read access to a calendar
   and which will be sitting in a file on a desktop PC.

   The answer is likely **titles are opt-in** (`calendar.show_titles = false` by default, so
   the panel says `Next: in 25 min` and nothing about whom with), but that is the ADR's call to
   make and to argue, not this list's.

2. **OAuth on the PC, never in the APK.** Both providers are an installed-app flow: Google's
   device authorization grant and Microsoft's device code flow both hand the owner a short code
   to type into a browser on any machine, which is exactly right for a server that may be
   running headless. Refresh tokens live beside the brapi token, in `server/config.toml` — which
   is gitignored, and which T7.3's secret audit already wants at mode 0600. **They must never
   reach the phone**: the APK ships no credential today and this must not be the task that
   changes that (`server/CLAUDE.md`).

   Standard library only, like the rest of `server/` — no `google-api-python-client`, no `msal`.
   Both flows are form posts and a JSON response; `urllib` does them. The token refresh is the
   part worth testing, because it is the part that fails silently at 3am when nobody is looking.

3. **The providers**, as siblings of `providers_brapi.py` and `providers_openmeteo.py`, with
   the same shape: a `load()` that returns rows or raises, and a failure that costs its own
   card and not the page. Google Calendar `events.list` with `timeMin=now`, `singleEvents=true`,
   `orderBy=startTime`, `maxResults` small; Microsoft Graph `/me/calendarView` with a window.
   **Ask for one event more than you need**: an all-day event and a declined one both have to be
   filtered after the fetch, and a window that returned exactly one can return none.

4. **Merge and choose in one pure function**, in `format.js`, with the rest of the decisions:
   `nextEvent(events, now)` takes both providers' rows already normalised and returns the one to
   show, or null. What it has to get right is what a calendar actually contains — an event in
   progress (show it, and say so, rather than skipping to the next one), an all-day event (not
   a countdown; it has no time), a declined invitation (not shown), a cancelled one (not shown),
   two starting in the same minute (deterministic, or the panel flickers between them once a
   minute for ever).

5. **The countdown is a pure function too**, and it is the one that will be wrong first:
   `untilText(start, now)` — `in 3 min`, `in 25 min`, `in 1 h 10`, `now`, `tomorrow 09:00`.
   Cross midnight, cross a DST boundary, and handle a start in the past.

   **The phone's clock decides**, exactly as T6.4's night window does: the panel is on the desk
   and the countdown is read there. The server sends an absolute instant (RFC 3339, with its
   offset), never a pre-computed "in 25 min", or a panel whose payload is a minute old counts
   down from the wrong number.

6. **Poll on the server's clock, not the panel's.** A calendar changes rarely and both APIs
   have quotas; `calendar_interval_s` belongs beside `quotes_interval_s` in `config.toml` with
   the same documented default and the same example-file guard T3.12 added. The panel re-renders
   the countdown every minute from the instant it already has, which costs no request at all.

7. **Dark while the PC is away**, like everything else: the panel is asleep, and a meeting
   nobody can see is not a reminder. The strip is dead for the same reason T8.2's buttons are.

```bash
node --test "web/test/**/*.test.js"
python -m unittest discover -s server/tests -t .
python e2e/layout/check_layout.py
python e2e/layout/check_layout.py --theme plain
python -c "import ast,sys; src=open('server/oauth.py').read(); sys.exit(0 if 'requests' not in src and 'msal' not in src else 1)"
! grep -rniE 'client_secret|refresh_token' android/app/src/main web/
test -f docs/adr/0016-calendars-are-personal-data.md
```

The last two are the ones that matter and they are cheap. A credential in `android/` or `web/`
is a credential in the APK, and an APK is a file anyone can pull off the phone; and the ADR is
a prerequisite of the code rather than a write-up of it, so its absence fails the task.

The contract test against the live APIs is opt-in and off by default, like `make contract`:

```bash
RUN_CONTRACT_TESTS=1 python -m unittest discover -s server/tests -t . -p "contract_calendar*.py"
```

## Manual check

On the device, with a real event ten minutes out: the line reads it correctly, the countdown
ticks down, and it disappears when the event ends. Then revoke the app's access from the
Google and Microsoft account pages and watch what the panel does — it must lose that card and
say so, not blank the page, and the server log must name which provider stopped answering.

And look at the sidebar with the buttons and the line together, at arm's length: this is the
one task whose layout decision the harness cannot make.

## Notes

- **Two providers, not one, is the point.** Either alone is half a day's work; the merge is
  where the design is, because the two disagree about almost everything — Microsoft returns
  times in UTC by default unless asked otherwise, Google returns `date` for all-day events and
  `dateTime` for the rest, and the two have different words for "you said no".
- A calendar is the first upstream here whose failure is **not** worth a stale value. A stock
  price from five minutes ago is useful; a meeting from five minutes ago may be one you have
  already missed. `stale` probably means "show nothing and say why" for this card alone.
- Nothing about this should need an APK rebuild to change: which calendars, whether titles are
  shown, how far ahead to look, all config (`server/config.example.toml`, ADR 0013).
