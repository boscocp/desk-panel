# T8.3 — The microphone button mutes every input on Linux and macOS too

Size: S · Prereqs: T8.1 · Files: `server/actions.py`, `server/tests/test_actions.py`,
`docs/adr/0015-the-panel-can-act-on-the-pc.md`

Requires: a Linux desktop session with two or more capture devices for the manual check; a Mac
for the macOS half

## Goal

On 2026-09-26 the first press of MIC on the Windows box muted the **default** input while the
owner was talking into a different one. The server answered 200, the button drew its cross, and
the microphone in use stayed live — the failure ADR 0015 calls worse than no button. Windows
was fixed the same day: `mute-mic` now takes its direction from the default input and applies
it to every active capture endpoint.

Linux and macOS still toggle the default alone, and have the same hole on any machine with a
headset, a webcam and a USB microphone plugged in at once.

## Steps

1. **Linux.** Enumerate sources with `pactl list short sources` (it works on PipeWire through
   `pipewire-pulse` as well as on PulseAudio) and **skip every `.monitor` source** — those are
   loopbacks of the outputs, and muting one breaks screen recording without silencing anyone.
   Read each remaining source's state with `pactl get-source-mute <name>`, then
   `pactl set-source-mute <name> <0|1>` on each. Every name comes from `pactl`'s own output,
   never from the request, and each call is an argument list (ADR 0015's rule).

   **This step said `pactl get-source-mute @DEFAULT_SOURCE@` and that was wrong** — corrected
   2026-09-27 after the review of PR #39, which had shipped it as written. The default source
   is not necessarily one of the sources this press touches: if it is a monitor the button
   becomes one-directional, and if it is muted beside a live headset the press *opens* every
   microphone. The direction has to come from the inputs being muted, by the same rule step 4
   reports them: unmute only when every one of them is already muted. `wpctl` has no
   "every source" verb, so `pactl` becomes the only mic command on Linux; say so in the table's
   comment.
2. **Several commands per press** is new for `run_action`, which today runs one argv. Keep the
   per-command timeout, and have the whole press fail loudly if any single mute fails: a partial
   success reported as `muted` is the exact lie this task exists to remove.
3. **macOS.** AppleScript's `volume settings` only knows the default input, and enumerating
   devices needs either a compiled helper or a third-party tool — both excluded by the
   standard-library rule. Unless a built-in route turns up, **write the limitation down in
   ADR 0015** instead of shipping a guess: macOS mutes the default input only.
4. The readback for `mute-mic` on Linux reports muted only if **every** non-monitor source is.

## Acceptance

```bash
python -m unittest server.tests.test_actions
grep -q 'monitor' server/actions.py
grep -qi 'default input only' docs/adr/0015-the-panel-can-act-on-the-pc.md
```

## Manual check

On Linux with two inputs plugged in, press MIC and then ask each input what it holds:

```bash
for n in $(pactl list short sources | awk '{print $2}' | grep -v '\.monitor$'); do
    echo "$(pactl get-source-mute $n)  $n"
done
```

Every one says `Mute: yes`. Press again: every one says `Mute: no`, and the `.monitor` sources
never moved at all. (`list short sources` does not print the mute flag -- its last column is
`RUNNING`/`IDLE`/`SUSPENDED` -- so the line that named it was asking for something it could not
show.)

## Done — 2026-09-27, wave 28

Linux does every input; macOS keeps the default and ADR 0015 says so out loud.

**The press stopped being one command, and that is the shape of the change.** `run_action` ran
one argument list per press; the microphone on Linux now needs four kinds -- a listing, a
direction, a set per input, a read per input -- so `_SEQUENCES` sits beside `_TABLE` and holds
the ones that are a *press* rather than a command. The row left in `_TABLE` is the press's first
command, which is also exactly the binary the 501 path and the startup line probe for, so
`candidates`, `describe` and `Unsupported` did not have to learn anything new.

**The direction comes from the inputs, and the first cut had that wrong.** It read
`pactl get-source-mute @DEFAULT_SOURCE@`, as step 1 said to, and the review of PR #39 caught
what that means: a default source that is a monitor is never one of the sources being muted, so
its state never moves and the button mutes for ever and never unmutes — and a default that is
muted beside a live headset, *the very state this task exists to end*, answers "already muted"
and the press opens every microphone in the machine. `state_from_sources` decides now, which is
the same function that draws the cross: a press unmutes only when every input is already muted,
and mutes in every other case — a mix, or a mixer nobody could parse, included. Step 1 is
corrected above.

**Every name comes from `pactl`'s own listing.** That is ADR 0015's rule surviving contact with
the one id whose commands are built at run time instead of written down, and it is asserted
directly: every argument of every command the press issues is either a literal or a name that
listing printed.

**`wpctl` lost the microphone.** It has no verb for "every source", so keeping it as a fallback
would mean a PipeWire box quietly back to muting the default alone -- the failure this task
exists to remove, reintroduced by the fallback that was supposed to be a kindness. It keeps the
speakers. A box with `wpctl` and no `pactl` answers 501 for `mute-mic` and the startup line says
so before anyone presses anything, which is the failure mode this project can actually diagnose.

**A partial mute is a failure, not a state.** One source refusing fails the whole press with its
name in the message, and the read-back answers `muted` only when every input is -- a mix is
`unknown`. The alternative is the cross drawn over a live microphone, which is the same lie the
Windows box told on 2026-09-26, arriving by a different road.

**macOS was not attempted.** `volume settings` knows one input and enumerating capture devices
needs Core Audio through a compiled helper or a third-party binary, both outside the
standard-library rule. Step 3 said to write the limit down rather than ship a guess, and that is
what ADR 0015 now carries.

Verified on this desk, which has three real inputs and four `.monitor` sources: both the direct
call and `POST /action/mute-mic` against a server on a spare port moved all three to `Mute: yes`
and back, the monitors never moved, `/ping` still answered, and the startup line read
`mute-mic: pactl`. Re-run afterwards on the mixed machine the review's finding describes — one
input muted by hand, two live — where the press closes all three rather than opening them.
