# T7.4 — Phone setup a stranger can follow, checked against the official docs

Size: M · Prereqs: T2.4, T7.2 · Files: `docs/PHONE-SETUP.md`, `docs/INSTALL-PHONE.md`,
`scripts/check_links.py`

Requires: phone (on adb) for the manual check only; the tests need network for link resolution

## Goal

`docs/INSTALL-PHONE.md` is a desk log: it tells *this* owner what to toggle on *this* Redmi
running MIUI 14, in the order that worked, with the app-op numbers read off the device. That is
worth keeping and is the wrong document to hand a contributor with a Pixel.

Split it in two. A device-neutral half that explains **what Android is being asked for and why**,
with every claim carrying a link to `developer.android.com`, and a vendor half that stays what it
is — the MIUI recipe, honestly labelled as one device's behaviour rather than as Android's.

The claims that need a citation, because all four are the kind that get repeated wrong:

- `FLAG_KEEP_SCREEN_ON` keeps the display on while the window is visible, and is not a wake lock
- `setShowWhenLocked` / `setTurnScreenOn` replaced the deprecated window flags in API 27
- battery optimisation exemption (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) is a user decision, and
  what it does and does not exempt
- `adb` over Wi-Fi and the developer-options path that enables it

## Steps

1. **`scripts/check_links.py`** — every Markdown link in the files it is given resolves: a
   relative link points at a file that exists, an `https://` link answers 2xx. Takes paths as
   arguments, exits non-zero listing what broke. **T7.3's acceptance already calls this script
   and it does not exist**, so that acceptance has never run clean; this task is where it lands.
   Network failures must be distinguishable from dead links — a timeout is not a 404, and a
   contributor offline should be able to skip the remote half with a flag.

2. **`docs/PHONE-SETUP.md`**, device-neutral. One section per thing the app needs, each saying
   what it is, why the panel needs it, how to grant it, and how to *verify* it was granted from
   `adb`. Verification matters more than the granting: every one of these silently resets on
   `adb install -r`, which is how they were lost twice on this desk.

3. **`docs/INSTALL-PHONE.md`** becomes the MIUI-specific half and links to the new file rather
   than repeating it. Keep the numeric app-ops (10020, 10008), keep the autostart and the
   battery whitelist steps, and keep the reinstall warning — they are device facts, and they are
   the most expensive knowledge in the repo.

4. **Say what is not Android.** MIUI's *Show on Lock screen* permission, its autostart list and
   its own battery manager have no AOSP equivalent, and a reader on a Pixel must not go looking
   for them. Label them as vendor behaviour where they appear.

5. **Screen suspension gets its own section**, because it is the project's whole point and the
   most confusing part to arrive at cold: what holds the screen on, what lets it sleep, what
   wakes it, and which of those three MIUI is allowed to override. Point at ADR 0005 and
   ADR 0012 rather than restating them.

## Acceptance

```bash
python scripts/check_links.py docs/PHONE-SETUP.md docs/INSTALL-PHONE.md
test "$(grep -c 'https://developer\.android\.com/' docs/PHONE-SETUP.md)" -ge 4
grep -q 'PHONE-SETUP.md' docs/INSTALL-PHONE.md
! grep -qi 'miui' docs/PHONE-SETUP.md
python scripts/check_acceptance.py
```

The fourth line is the split, enforced: the device-neutral document must not name the vendor at
all. It is the one assertion here that cannot pass by accident.

## Manual check

Hand `docs/PHONE-SETUP.md` to someone with an Android phone that is not this Redmi and watch
where they stall. The section that needed a follow-up question is the section to rewrite.

## Notes

- Cite the reference page, not a blog post and not a Stack Overflow answer. If the official docs
  do not say it, write that the behaviour was **measured on this device** and give the command
  that measures it — that distinction is the whole value of the document.
- `dumpsys deviceidle whitelist` and `appops get` are the verification commands worth teaching. A
  reader who knows them can debug a failed grant without asking anybody.
