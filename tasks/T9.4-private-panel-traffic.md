# T9.4 — Nobody else on the Wi-Fi can read the panel

Size: L · Prereqs: T9.1 · Files: `docs/spikes/2026-panel-tls.md`,
`docs/adr/0018-the-panel-traffic-is-private.md`, `server/server.py`, `server/config.example.toml`,
`android/app/src/main/res/xml/network_security_config.xml`, `android/.../DataPoller.java`,
`android/.../Actions.java`, `android/app/build.gradle.kts`, `.env.example`, `docs/SERVER-SETUP.md`

Requires: the phone on adb and a reachable PC, for the spike and for the manual check.

**Asked for on 2026-09-29, and scheduled for after the owner's half of T9.1.** The owner will
connect the calendars first.

## Why

T9.1 put meeting titles on `/quotes`, with titles on by the owner's decision.
[ADR 0017](../docs/adr/0017-calendars-are-personal-data.md) states the cost: **anyone on the same
Wi-Fi can read the titles of the owner's next five events.** The Host check closed DNS rebinding,
so a web page can no longer read them. A device on the LAN still can, in two ways:

- **by asking**: `curl http://<pc>:8777/quotes` works for any device on the network;
- **by listening**: the traffic is plain HTTP, and on WPA2-PSK anyone who knows the Wi-Fi
  password can decrypt other clients' traffic.

The owner asked for both to be closed. Two designs were discussed, and the order is the owner's:

1. **Try first: HTTPS with a pinned certificate, plus a shared key.** This is the recommended one.
   TLS encrypts everything, including the mute buttons, and it authenticates the PC as well as
   the phone. The server side is Python's own `ssl`, so it stays stdlib-only, and the crypto is
   audited rather than written here.
2. **If step 1 fails on this phone: the owner's design.** Encrypt the `agenda` block end to end,
   with a key shared by the PC and the phone. The transport stays plain HTTP, so nothing about
   the pollers or the cleartext pin changes.

## Step 0 — the spike, on the device, before any design is committed

Write the answer in `docs/spikes/2026-panel-tls.md`. It decides between design 1 and design 2,
and it must answer each of these with a measurement, not an opinion:

- **Does `HttpURLConnection` on the Redmi (Android 12, MIUI 14) accept a self-signed
  certificate pinned in `network_security_config.xml`**, for a host that is an **IP address**?
  - Use `<domain-config><trust-anchors><certificates src="@raw/pc_cert"/>`, or a `<pin-set>`.
  - The certificate needs the IP in `subjectAltName` (iPAddress), because hostname verification
    for an IP uses the SAN, not the CN.
- **What does TLS cost the battery?**
  - `/ping` runs every few seconds and dormant polls run under a wake lock (ADR 0014, T5.6).
  - Measure a handshake per poll against keep-alive or session resumption, the way T5.3 counted
    requests.
  - **Decide whether `/ping` stays plain HTTP.** It carries one fact, "somebody is logged in",
    and it is the login signal (invariant 2). Keeping it cleartext, with everything else on TLS,
    is a legitimate answer. The ADR has to argue it either way.
- **How is the certificate made, with nothing installed on the host (ADR 0003)?**
  - The Python stdlib cannot generate X.509.
  - Candidates: `openssl` inside the Docker image; `openssl` as shipped with macOS, Linux and
    Git for Windows; or a script run once at setup.
  - The private key never enters git. `check_secrets.py` already refuses a PEM private key and
    `*.pem`/`*.key` by name.
- **Do both servers still work behind one `PC_IP` list** (ADR 0016)? Each PC has its own
  certificate, and the phone pins all of them.

**Stop condition.** If any of the first three cannot be made to work on this phone, stop and
write down why. Then go to design 2.

## Design 1 — HTTPS with a pinned certificate, plus a shared key

1. **ADR 0018 first.** It amends ADR 0004 (plain HTTP) and ADR 0015, whose argument against a
   token was that `/app` hands the APK, and so the token, to anyone. That argument holds only
   while `/app` is open, which is why step 3 exists.
2. **TLS on the server.**
   - Use `ssl.SSLContext(PROTOCOL_TLS_SERVER)` with `minimum_version = TLSv1_2`.
   - Load the certificate and key from paths in `config.toml`. Both files are gitignored, and the
     key file is 0600.
   - Serve on its own port or the same one, as the spike decided.
3. **The shared key.**
   - A random `PANEL_KEY` in `.env` goes into `BuildConfig`, and the same value goes into
     `panel_key` in `config.toml`. Mismatched values are a startup warning, never a silent pass.
   - Every data route and `POST /action/*` requires the `X-Panel-Key` header, compared with
     `hmac.compare_digest`. A request without it gets 401.
   - `/ping` follows whatever the spike decided.
   - **`/app` is off by default** (`serve_apk = false`). Once the APK carries the key, whoever
     downloads it has the key.
4. **The phone.**
   - `DataPoller` and `Actions` switch to `https://` and send the header.
   - The cleartext `domain-config` narrows to whatever still needs plain HTTP (`/ping`, if the
     spike kept it).
   - `MIXED_CONTENT_NEVER_ALLOW` is untouched, because the WebView still never talks to the
     network (invariant 1).
5. **Docs.** `SERVER-SETUP.md` gets generating the certificate, rotating the key, and what a
   mismatch looks like on the panel.

## Design 2 — the owner's: the agenda encrypted end to end

Only if design 1 fails. Use the same `PANEL_KEY` in `.env` and `config.toml`.

- **The server encrypts the `agenda` block**, and only that block. The rest of `/quotes` is
  public data already.
- **The phone decrypts it in `DataPayload`** and passes the plaintext to the page, so `web/` does
  not change. A block that fails to authenticate is dropped and the card says so; it is never
  shown half-decoded.
- **The hard constraint is the stdlib.** Python's standard library has no AES. ADR 0018 must
  choose one of two options, and argue it:
  - **(a) Relax stdlib-only for one vetted library** (`cryptography`, AES-256-GCM), with its
    install documented. This is recommended if design 2 is reached, because it uses an audited
    construction.
  - **(b) Build from HMAC-SHA256.** Two subkeys derived from `PANEL_KEY` (HKDF), a random 16-byte
    nonce per message, a keystream of HMAC(key_enc, nonce ‖ counter), and encrypt-then-MAC with
    HMAC(key_mac, nonce ‖ ciphertext), verified in constant time. The phone side has
    `javax.crypto.Mac`. The construction is sound in theory and hand-made in practice, so it needs
    test vectors shared by both sides and a review lens aimed at it.
- **Replay** of an old `agenda` block is harmless: the phone checks the instants against its own
  clock. The ADR says so rather than adding a counter.

Whichever design ships, the server tests must pin these three behaviours:

- a data route without the key answers 401, and with a wrong key answers 401 without timing
  that depends on the key;
- `/app` answers 404 unless `serve_apk = true`;
- in design 2, an `agenda` block that was tampered with fails authentication and is not
  decrypted.

## Manual check

On the device, with a laptop on the same Wi-Fi:

- `curl` from the laptop gets 401 (design 1), or ciphertext in `agenda` (design 2). It never gets
  a title.
- A packet capture on the laptop (`tcpdump` or Wireshark, while the phone polls) shows no
  meeting title in clear. In design 1 it shows no HTTP at all on the data port.
- The panel still sleeps and wakes with the PC exactly as before (invariant 3). Watch
  `state=online`/`state=offline` in logcat across a logout, because the login signal is what
  this task must not break.

## Notes

- The screen is still readable by anyone at the desk. No design here changes that, and
  `calendar_show_titles = false` remains the answer for that case.
- A guest Wi-Fi that isolates visitors costs nothing, and it is worth doing before any of this.
- Keep the key out of logs, out of `probe.py` output, and out of any error message, as the brapi
  token already is.
