# T0.1 — Containerised Android toolchain

Size: L · Prereqs: none · Blocks: all of phase 2 · Files: `docker/Dockerfile`,
`docker/compose.yml`, `Makefile`

Requires: Docker installable on the dev host (needs root once)

## Goal

Be able to build an APK without installing the JDK or the Android SDK on the development
machine. See [ADR 0003](../docs/adr/0003-containerized-toolchain.md) for why that constraint is
non-negotiable.

## What changed, and why this task was rewritten

The original was written for a Windows host: `wsl --install`, `winget install
Docker.DockerDesktop`, and an acceptance criterion of `ls "$LOCALAPPDATA/Android/Sdk"`.
Development now happens on Linux, so those steps are notes, not steps.

Two consequences that are easy to miss:

- **`adb` on the host is now allowed, and expected.** The original acceptance demanded that
  `adb version` fail. That was a proxy for "no Android Studio", but nine tasks call bare `adb`
  in their acceptance, and the container cannot see the phone. `platform-tools` on the host is
  the only arrangement where both hold. What must stay off the host is the **JDK and the SDK
  build tooling** — that is the actual ADR 0003 constraint.
- **File ownership.** A bind mount with no `user:` mapping makes every Gradle artefact in
  `out/` and `android/build/` root-owned. `make clean` then fails from the host. This was
  invisible on Docker Desktop for Windows and is immediate on Linux.

## Node

`node` is **not** in the container. It goes on the host, via the distro package manager.

ADR 0003 restricts the JDK and the Android SDK — a multi-gigabyte toolchain with an
interactive installer. Node is already a de-facto requirement of this project: `make test-web`,
four task acceptances and the `web` CI job all call it, and [ADR
0006](../docs/adr/0006-no-framework-web-layer.md) uses `node:test` precisely because it needs no
dependency tree. Putting it in the Android container would make the whole web track wait on the
slowest task in the backlog, for nothing.

## Steps

1. Install Docker and the compose plugin, and let your user run it without `sudo`:
   ```bash
   sudo pacman -S --needed docker docker-compose nodejs npm
   sudo systemctl enable --now docker
   sudo usermod -aG docker "$USER"    # log out and back in for this to take effect
   ```
   On Windows the equivalent is `wsl --install` then `winget install Docker.DockerDesktop`,
   with the WSL2 backend; on macOS, Docker Desktop or colima.
2. Write `docker/Dockerfile`:
   - base on a JDK 21 image, pinned by digest or exact tag
   - install the Android SDK **command-line tools** — not Android Studio
   - `sdkmanager` for `platform-tools`, `platforms;android-36`, `build-tools;36.0.0`
   - accept licences non-interactively
   - set `ANDROID_HOME`, put the tools on `PATH`
   - working directory `/workspace`
3. Write `docker/compose.yml`:
   - one service, `build`
   - bind-mount the repository root to `/workspace`
   - **`user: "${UID:-1000}:${GID:-1000}"`**, so build output belongs to you and not to root
   - **named volume** for the Gradle home — a bind mount is noticeably slower
   - no ports, no privileged mode
4. `docker compose -f docker/compose.yml build`.

## Acceptance

The toolchain works inside the container:

```bash
docker compose -f docker/compose.yml run --rm build sdkmanager --list_installed
docker compose -f docker/compose.yml run --rm build java -version
```

The host stays clean — no JDK, no Android SDK:

```bash
! command -v java
! command -v javac
! test -d "$HOME/Android/Sdk"
! test -d "$HOME/.android/sdk"
```

Node is present, because the web layer needs it and the container does not carry it:

```bash
node --version
```

Build output belongs to you, not to root. This is the one that catches a missing `user:`
mapping, and it fails loudly rather than three tasks later:

```bash
docker compose -f docker/compose.yml run --rm build touch /workspace/out/.ownership-probe
test -O out/.ownership-probe && rm out/.ownership-probe
```

## Notes

- No AVD, no emulator image. Testing happens on the real phone; the emulator is several GB this
  project never uses.
- Pin exact versions in the Dockerfile. "Latest" turns a reproducible build into a moving one.
- The image is large. Budget the download; this is the one genuinely slow task.
- `adb` from inside the container is a separate problem, and it is answered in TT.7 rather than
  here — the container talks to the host's adb server over TCP instead of owning the USB device.
