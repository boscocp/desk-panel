# T3.8 — Windows: Scheduled Task, firewall, static IP

Size: M · Prereqs: T3.5 · Files: `server/install_task.ps1`, `docs/SERVER-SETUP.md`

Requires: the Windows PC, and another device on the LAN to probe from

## Goal

The server starts on login on Windows, with no manual step, and is reachable from the phone.
This is the primary platform — the one verified every release.

## Steps

1. `server/install_task.ps1` registering a task with an **"At log on"** trigger scoped to the
   current user, running `pythonw server\server.py` with no window.

   Four settings carry the invariant and all four have wrong defaults. See
   [ADR 0010](../docs/adr/0010-login-signal-is-session-scoped.md):

   | Setting | Value | Default is wrong because |
   |---|---|---|
   | `Principal.LogonType` | `InteractiveToken` | `Password`/`S4U` run without an interactive session — a service in disguise |
   | `Settings.ExecutionTimeLimit` | `PT0S` | Default 72 h kills the server on day four, mid-session |
   | `Settings.DisallowStartIfOnBatteries` | `$false` | Default `$true` never starts on a laptop |
   | `Settings.StopIfGoingOnBatteries` | `$false` | Default `$true` stops it on unplug |

2. Reject the Microsoft Store stub. If `sys.executable` is under `...\Microsoft\WindowsApps\`,
   the task launches the Store instead of Python — silently, and only at the next login. The
   installer must fail with a readable message instead.
3. Firewall rule on the **Private** profile only:

   ```powershell
   New-NetFirewallRule -DisplayName "desk-panel" -Direction Inbound -Action Allow `
     -Protocol TCP -LocalPort 8777 -Profile Private
   ```

4. Reserve a static DHCP lease for the PC on the router. Write the address into
   `docs/SERVER-SETUP.md` — T4.1 pins it in the app.
5. In the BIOS, disable **ErP Ready / USB power in S5**. Reason in
   [ADR 0008](../docs/adr/0008-device-longevity.md); a battery measure, not a networking one,
   but this is the session where you are already in setup mode.

## Acceptance

Shape, on the PC:

```powershell
powershell -ExecutionPolicy Bypass -File server\install_task.ps1
schtasks /Query /TN "desk-panel" /XML | findstr /C:"<LogonTrigger>"
powershell -NoProfile -Command "exit [int]((Get-ScheduledTask desk-panel).Principal.LogonType -ne 'InteractiveToken')"
powershell -NoProfile -Command "exit [int]((Get-ScheduledTask desk-panel).Settings.ExecutionTimeLimit -ne 'PT0S')"
powershell -NoProfile -Command "exit [int]((Get-ScheduledTask desk-panel).Settings.DisallowStartIfOnBatteries)"
powershell -NoProfile -Command "if (Get-Service desk-panel -EA SilentlyContinue) { exit 1 } else { exit 0 }"
python server\verify_login_scope.py
```

Behaviour, from **another device on the LAN**. The human action is the setup; the assertion is
still an exit code:

```bash
# 1. reboot the PC, do NOT log in, wait 90s
python server/probe.py --host <pc-ip> --expect down
# 2. log in, wait 60s
python server/probe.py --host <pc-ip> --expect up
# 3. LOCK the PC (Win+L), wait 15s
python server/probe.py --host <pc-ip> --expect up
# 4. log OFF, wait 30s
python server/probe.py --host <pc-ip> --expect down
```

Step 1 is the invariant: answering there means the task became a service. Step 3 pins the
opposite mistake — **locked is not logged out**, an at-logon task answers while locked, and
that is correct. `docs/SERVER-SETUP.md` reads as if answering at the lock screen were the bug;
it is not, and this step stops a future session from "fixing" it.

Testing from `localhost` does not count and will not catch the firewall.

## Notes

- Fast Startup (hiberboot) hibernates the kernel on "shutdown" but *does* log the user off, so
  the logon trigger must still fire. Run steps 1-2 across a Fast Startup shutdown as well as a
  real reboot.
- If DHCP later hands the PC a different address, the app reports "offline" forever and looks
  like a bug. The reservation is the fix, and it is easy to skip.
