# T3.10 — macOS: LaunchAgent

Size: S · Prereqs: T3.5 · Files: `server/dev.bosco.deskpanel.plist.in`,
`server/install_agent.sh`, `docs/SERVER-SETUP.md`

Requires: **a Mac**, and for the behaviour block a logout with a second machine to SSH from.
The shape half ran on 2026-09-29; the behaviour half has not, so the row stays `blocked`

## Goal

The same signal on macOS. The plist, the installer and the documentation ship now; the
behavioural acceptance waits for hardware.

## Why this is still `blocked`

`CLAUDE.md` says every acceptance criterion is a command with an exit code. The shape block
below now runs and exits 0 on a real Mac. The behaviour block needs the Mac sitting at its login
window while a second device asks it questions, which is a logout nobody can do from inside the
session being logged out. That is the same shape of blocked half T3.9 carries.

The parser half is testable on any machine, from fixtures — that is TT.10.

## Steps

1. `~/Library/LaunchAgents/dev.bosco.deskpanel.plist`. Never `/Library/LaunchDaemons`, which
   loads at boot as root with no login — the macOS Windows Service. Never
   `/Library/LaunchAgents` either, which loads for *any* user's login.

   | Key | Value | Why |
   |---|---|---|
   | `Label` | `dev.bosco.deskpanel` | |
   | `ProgramArguments` | absolute python3, `-u`, absolute `server.py`, `--config`, absolute path | launchd runs no shell |
   | `RunAtLoad` | `true` | |
   | `KeepAlive` | `{ SuccessfulExit: false }` | restart on crash, not on clean exit |
   | `LimitLoadToSessionType` | `Aqua` | **the invariant.** Unset also loads in `LoginWindow` and `Background` — answering at the login screen |
   | `ProcessType` | `Interactive` | keeps App Nap from throttling a long-lived listener |
   | `StandardOutPath` / `StandardErrorPath` | `~/Library/Logs/desk-panel.log` | launchd's only log capture |

2. Run `python3 server/server.py` in the foreground once, interactively, **before** installing
   the agent, so a human answers the "accept incoming network connections" dialog. Under
   launchd with no foreground app that dialog is a coin flip. On macOS 15+, check Local Network
   access too.

## Acceptance

Shape:

```bash
sh server/install_agent.sh
plutil -lint ~/Library/LaunchAgents/dev.bosco.deskpanel.plist
/usr/libexec/PlistBuddy -c 'Print :LimitLoadToSessionType' ~/Library/LaunchAgents/dev.bosco.deskpanel.plist | grep -qx Aqua
/usr/libexec/PlistBuddy -c 'Print :RunAtLoad' ~/Library/LaunchAgents/dev.bosco.deskpanel.plist | grep -qx true
test ! -e /Library/LaunchDaemons/dev.bosco.deskpanel.plist
! launchctl print system/dev.bosco.deskpanel > /dev/null 2>&1
python3 server/verify_login_scope.py
```

Behaviour. macOS gives the cleanest proof of the three: the `gui/<uid>` domain does not exist
until someone logs into the GUI, so this needs no reboot-and-guess.

```bash
# at the login window, over SSH from another device:
! ssh mac 'launchctl print gui/501/dev.bosco.deskpanel'
python server/probe.py --host <mac-ip> --expect down
# log in, wait 30s
python server/probe.py --host <mac-ip> --expect up
```

## Notes

- The macOS Application Firewall is per-binary, off by default, and its prompt says "python3",
  not "desk-panel". Document it; do not try to configure it.

## What the first Mac found (2026-09-29, wave 34)

macOS 26.5, Apple Silicon, Homebrew Python 3.13. The shape block exits 0, `verify_login_scope.py`
exits 0, `/ping` answers from the agent, and `after_update.py` restarts it with `kickstart -k`.
Getting there found three things that no fixture could:

- **The template's own comment made it unreadable.** `--` inside an XML comment is illegal;
  `plutil -lint` accepts it and `plistlib`, which the verifier uses, does not. The agent loaded,
  ran and answered while the verifier said *unknown*. `server/tests/test_agent_rendering.py` now
  runs the installer's renderer against XML-hostile paths and hands the result to the verifier.
- **`parse_launchctl_print` read nested blocks.** A real print carries `resource coalition` and
  `jetsam coalition` blocks, each with its own `type =` and `state =`, after the service's. The
  flat scan reported a correctly loaded agent as `type='jetsam'` and FAILed. The loaded and absent
  fixtures are now real captures, and the old parser fails four self-test cases against them.
- **The firewall names a different binary.** A framework Python re-execs into `Python.app`, so
  the path in `ProgramArguments` is not what listens. The installer reads the running process
  once the socket is open, and the first cut of that asked too early and named the wrong one anyway.

With the Application Firewall on and no allowance, `/ping` answers on `127.0.0.1` and not on the
LAN address. That is a manual grant, recorded in `docs/SERVER-SETUP.md` and not automated.
