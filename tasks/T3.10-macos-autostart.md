# T3.10 — macOS: LaunchAgent

Size: S · Prereqs: T3.5 · Files: `server/dev.bosco.deskpanel.plist.in`,
`server/install_agent.sh`, `docs/SERVER-SETUP.md`

Requires: **a Mac.** There isn't one — this task is `blocked`, deliberately

## Goal

The same signal on macOS. The plist, the installer and the documentation ship now; the
behavioural acceptance waits for hardware.

## Why this is `blocked` rather than `todo`

`CLAUDE.md` says every acceptance criterion is a command with an exit code. Without a Mac,
half of these cannot be executed, and a task whose acceptance can never run is a task file that
lies. `blocked` is the honest state and `STATUS.md` already has it.

The parser half **is** testable today, from fixtures, on any machine — that is TT.10.

## Steps

1. `~/Library/LaunchAgents/dev.bosco.deskpanel.plist`. Never `/Library/LaunchDaemons`, which
   loads at boot as root with no login — the macOS Windows Service. Never
   `/Library/LaunchAgents` either, which loads for *any* user's login.

   | Key | Value | Why |
   |---|---|---|
   | `Label` | `dev.bosco.deskpanel` | |
   | `ProgramArguments` | absolute python3, `-u`, absolute `server.py`, `--config`, absolute path | launchd runs no shell |
   | `RunAtLoad` | `true` | |
   | `KeepAlive` | `{ SuccessfulExit: false }` | restart on crash, not on clean exit |
   | `LimitLoadToSessionType` | `Aqua` | **the invariant.** Unset also loads in `LoginWindow` and `Background` — answering at the login screen |
   | `ProcessType` | `Interactive` | keeps App Nap from throttling a long-lived listener |
   | `StandardOutPath` / `StandardErrorPath` | `~/Library/Logs/desk-panel.log` | launchd's only log capture |

2. Run `python3 server/server.py` in the foreground once, interactively, **before** installing
   the agent, so a human answers the "accept incoming network connections" dialog. Under
   launchd with no foreground app that dialog is a coin flip. On macOS 15+, check Local Network
   access too.

## Acceptance

Shape:

```bash
sh server/install_agent.sh
plutil -lint ~/Library/LaunchAgents/dev.bosco.deskpanel.plist
/usr/libexec/PlistBuddy -c 'Print :LimitLoadToSessionType' ~/Library/LaunchAgents/dev.bosco.deskpanel.plist | grep -qx Aqua
/usr/libexec/PlistBuddy -c 'Print :RunAtLoad' ~/Library/LaunchAgents/dev.bosco.deskpanel.plist | grep -qx true
test ! -e /Library/LaunchDaemons/dev.bosco.deskpanel.plist
! launchctl print system/dev.bosco.deskpanel > /dev/null 2>&1
python3 server/verify_login_scope.py
```

Behaviour. macOS gives the cleanest proof of the three: the `gui/<uid>` domain does not exist
until someone logs into the GUI, so this needs no reboot-and-guess.

```bash
# at the login window, over SSH from another device:
! ssh mac 'launchctl print gui/501/dev.bosco.deskpanel'
python server/probe.py --host <mac-ip> --expect down
# log in, wait 30s
python server/probe.py --host <mac-ip> --expect up
```

## Notes

- The macOS Application Firewall is per-binary, off by default, and its prompt says "python3",
  not "desk-panel". Document it; do not try to configure it.
