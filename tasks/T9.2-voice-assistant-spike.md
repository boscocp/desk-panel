# T9.2 — Spike: can the panel talk to an assistant for nothing?

Size: M (time-boxed) · Prereqs: T8.2, ADR 0015 · Files: `spikes/voice/`,
`docs/spikes/2026-voice-assistant.md`

Requires: the PC only. No phone, no APK, no account. That is deliberate — see the box below.

**This is a future improvement and it is a spike, not a feature.** Asked for on 2026-09-20. It
produces a written answer and a throwaway prototype; it changes nothing under `server/`,
`android/` or `web/`, and it is allowed — expected, even — to conclude *do not build this*.
The feature it would justify is T9.3, which does not exist yet and must not be written before
this is `done`.

## The question

A button on the panel to ask something out loud and hear an answer: press, speak, the PC
listens, an assistant answers, the PC speaks it back. The requirement that makes it a spike is
**at no running cost** — so the interesting path is a local model on the PC, with the Claude
and DeepSeek APIs as the paid fallback to measure against, not as the plan.

Four things have to be true at once, and the spike is worth doing because at least two of them
are unknown on this hardware:

1. **speech in**, offline, in pt-BR and en, on this PC, in seconds and not tens of seconds,
2. **an answer**, from a model small enough to run here, that is worth having,
3. **speech out**, offline, in a voice that can be understood across a desk,
4. all three inside a latency a person will actually wait for, standing at a phone.

## Why it does not touch the phone

The panel cannot make a network request — invariant 1, ADR 0002 — so nothing about this is a
web problem. The whole pipeline runs on the PC, and the phone's part is a button and a
microphone, which is T8.2's inbound bridge plus `RECORD_AUDIO`.

That part is not free either and the spike should say so rather than pretend: `RECORD_AUDIO` is
the first dangerous permission this app would ask for, on a device that has none today, and it
is a permission that MIUI shows a persistent indicator for. Keep it out of the spike; measure
the PC.

## Steps

1. **Time-box it.** A spike that runs until it works is not a spike. Two sittings, and if the
   numbers are not there at the end of the second one, write down what they were and stop.

2. **A fixture, not a live microphone.** Record three short WAVs once — one pt-BR, one English,
   one with the panel's own fan noise in the background — and commit them under
   `spikes/voice/fixtures/`. Every measurement below runs against the same bytes, or the
   numbers are about how clearly you spoke that afternoon.

3. **Measure speech-to-text.** `whisper.cpp` and `vosk` are the two credible offline options;
   both run on CPU. Record, per model size, the wall-clock seconds for each fixture and whether
   the transcript is usable — and record the RAM, because this PC also runs the panel's server
   and whatever the owner is actually doing.

4. **Measure the model.** A local runner (llama.cpp or Ollama) with a small instruct model,
   against the same three prompts every time. What matters is not benchmark quality but
   whether a two-sentence answer to "what's the weather tomorrow" arrives before the person has
   given up — so measure **time to first audible word**, not tokens per second.

   Then measure the paid path once, honestly, as the comparison: Claude and DeepSeek both
   answer in well under a second and both cost money per question. The spike's job is to say
   how much worse the free path is, in seconds and in usefulness, not to argue for either.

5. **Measure speech-out.** Piper is the obvious offline candidate. The bar is low and specific:
   understandable from across a desk, over the noise that is already in fixture three.

6. **Add up the round trip** and compare it against the only number that matters — how long
   somebody will stand at a panel with their finger off a button before deciding it is broken.
   Write that number down *before* measuring, so the answer is not adjusted to fit the result.

7. **Say what it would cost to keep.** Disk for the models, RAM while idle, whether anything
   has to run permanently (it must not: the PC server dies with the login session, invariant 2,
   and a model daemon that outlives it would be the first thing in this project to break that),
   and what happens to the panel's own responsiveness while a model is answering.

8. **Write the findings**, with the numbers in a table, and end with one of three
   recommendations: build it local, build it paid and say what a question costs, or do not
   build it. Each needs a sentence saying what would change the answer later.

## What the spike must also answer, because they are the awkward ones

- **The server has no authentication** and is LAN-only by design (ADR 0004). ADR 0015 was
  written for actions that are safe to repeat. An unauthenticated endpoint that runs a model
  and speaks out loud in someone's room is not in that family, and neither is one that
  forwards room audio to a third party. Whatever the recommendation, it names the ADR this
  would need.
- **A microphone in a room is not the owner's data alone.** Anyone who speaks near it is in the
  recording, and on the paid path the recording leaves the house.
- **What happens when it fails?** The panel's entire design is that a dark screen means one
  thing. A button that sometimes answers and sometimes does not needs an answer to "how does
  the user know it heard me", and it cannot be a spinner on a panel read from two metres away.

## Acceptance

The spike is `done` when the prototype runs end to end with no network and the findings are
written:

```bash
test -f docs/spikes/2026-voice-assistant.md
python spikes/voice/roundtrip.py --fixture spikes/voice/fixtures/pt-br.wav --offline --budget 12
python spikes/voice/roundtrip.py --fixture spikes/voice/fixtures/noisy.wav --offline --budget 12
python spikes/voice/roundtrip.py --self-test
```

`roundtrip.py` exits 1 if any stage fails or the round trip is slower than `--budget` seconds,
and 2 if it could not run at all — a missing model is "could not run", never a pass. `--offline`
makes it refuse to open a socket to anything but localhost, so the free path is proved to be
the free path rather than quietly falling through to an API.

`--self-test` runs the stage plumbing against a recorded transcript and a recorded answer, with
no model loaded, so this file's acceptance still means something on a machine that has not
downloaded eight gigabytes.

## Manual check

Listen to the three answers. The measured round trip can be inside the budget and the result
still be useless — a transcript that turns "PETR4" into "petrol" and an answer built on it is a
worse outcome than no button, and no exit code is going to say so.

## Notes

- **The prototype is throwaway and must look it.** `spikes/voice/` is not `server/`, it is not
  bound by the standard-library rule, and nothing in it is imported by anything that ships.
  Say that at the top of every file in it, or the next person will find a working pipeline and
  wire it in.
- Deleting `spikes/voice/` when T9.3 is decided either way is part of T9.3, not a loose end.
- The cheapest possible version of this feature is worth costing too, and the spike should
  spend ten minutes on it: no speech at all, a fixed set of phrases the panel can answer from
  data it already has. Most of what a desk panel gets asked is already on the screen.
