# T3.1 — `/ping`

Size: S · Prereqs: none (does not need the container) · Files: `server/server.py`

## Goal

The login signal, in its simplest form. Everything else in phase 3 hangs off this file.

## Steps

1. `server/server.py` using `http.server` from the standard library. **No pip, ever** — see
   `server/CLAUDE.md`.
2. `GET /ping` returns 200 with a tiny JSON body (`{"ok": true}`).
3. Bind to `0.0.0.0` on port 8777 so the LAN can reach it; the firewall rule in T3.5 keeps that
   scoped to the Private profile.
4. Unknown paths return 404.
5. Structure the file so logic is importable and testable without starting a server — the
   handler routes and serialises, nothing more. This matters for TT.2, and Python documents no
   way to drive a handler without a socket.

## Acceptance

```bash
python server/probe.py --serve --expect up
python server/probe.py --host 127.0.0.1 --port 1 --expect down
```

The first starts the server, probes `/ping`, stops it, and exits 0 only if the probe matched.
The second proves the probe can fail: nothing listens on port 1.

Then, from **another device on the LAN** — the real test, and where an unnoticed firewall
prompt shows up:

```bash
python server/probe.py --host <pc-ip> --expect up
```

## Notes

- `http.server` carries an official warning against production use. This is a LAN-only,
  unauthenticated, non-sensitive endpoint on a home network, which is within what that warning
  contemplates. Do not expose it beyond the LAN and the assumption holds.
- No authentication by design. The security boundary is the network, and T3.5's firewall rule
  is what enforces it.
