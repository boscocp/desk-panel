# T6.5 — A sparkline beside every value

Size: M · Prereqs: T5.1 · Pairs with: TT.1 · Files: `server/providers_awesomeapi.py`,
`server/providers_binance.py`, `server/server.py`, `web/js/format.js`, `web/js/app.js`,
`web/js/mock.js`, `web/css/style.css`

Requires: none for the tests; the phone only for the manual check

## Goal

A small trend line next to each quote, FX rate and crypto price, so the panel says where a
number came from and not only where it is.

## Where the history comes from

Nothing in the project kept a series, and the panel is the wrong place to grow one: the WebView
reloads on every wake (ADR 0014), so anything accumulated in the page is lost exactly when the
screen comes back. The server could keep a ring buffer, but it dies with the login session, so
the chart would restart every morning.

So the series is fetched, not accumulated — real daily closes, from the same upstreams that
serve the prices. Both are key-free, and both were measured on 2026-09-19:

```
GET economia.awesomeapi.com.br/json/daily/USD-BRL/30   -> newest first
GET api.binance.com/api/v3/klines?symbol=BTCUSDT&interval=1d&limit=30  -> oldest first
```

**The two disagree about direction**, which is the trap: drawing AwesomeAPI's response without
reversing it renders a rise as a fall, and nothing about the picture says so. Each provider has
its own `normalise_history` and its own test against a recorded response.

brapi's historical range needs a token, like its crypto and currency endpoints (T3.3 subtask 0),
so B3 rows carry an empty series until one is configured. That costs those rows their picture
and nothing else.

## Steps

1. `normalise_history(raw) -> [float]`, **oldest first**, pure, one per provider.
2. `load_history(symbols, days)` returning `{symbol: [values]}`, skipping any symbol whose fetch
   failed — a missing sparkline must never cost a row its price.
3. A separate cache on `history_interval_s` (default 6h). Daily closes do not move between
   refreshes of the prices beside them, and the series must never mark the payload `stale`: it
   is a decoration on a row that already carries the number it decorates.
4. Each `quotes`/`fx`/`crypto` row gains `history: [...]`. `web/js/mock.js` gains one too — it
   is the third copy of the payload contract, and a panel developed in a browser without one
   would never show the chart.
5. `sparklinePath(values, width, height)` in `format.js`: pure, returns an SVG path `d`. Scaled
   to the series' own min and max, not to zero — a currency that moved 0.4% is a flat line
   against a zero baseline, which is true of the magnitude and useless about the trend.
6. `app.js` wraps it in an inline `<svg>` built with `createElementNS`. `createElement('svg')`
   produces an HTML element of that name which renders as nothing, silently.

## Acceptance

```bash
node --test "web/test/**/*.test.js"
python -m unittest discover -s server/tests -t .
```

Both with no network. And, against a running server:

```bash
curl -sf http://localhost:8777/quotes | python -c "import json,sys; d=json.load(sys.stdin); sys.exit(0 if all(r['history'] for r in d['fx'] + d['crypto']) else 1)"
```

Every FX and crypto row carries a non-empty series. B3 is excluded deliberately: it has none
without a brapi token.

## Manual check

- The line's direction matches the sign of the change beside it. A green line sloping down is
  the reversed-series bug, and it is the only way to see it.
- No label is truncated. The crypto card has the panel's widest prices and no slack, so the
  sparkline shrinks before the ticker does; `BTC` rendering as `B…` means the floor moved.

## Notes

- The line takes the same colour as the change, so direction is said twice — once as a shape,
  once as a hue — and neither has to be read alone. That is the same three-way separation
  `--up`/`--down` already use (T6.1).
- `vector-effect: non-scaling-stroke` is load-bearing: with `preserveAspectRatio="none"` the
  stroke would stretch with the geometry and the horizontal runs would come out fatter than the
  vertical ones.
