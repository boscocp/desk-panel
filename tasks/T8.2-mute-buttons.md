# T8.2 — Two buttons under the clock

Size: L · Prereqs: T8.1, T6.7, T4.2 · Files: `android/app/src/main/java/dev/bosco/deskpanel/`
(**including `DataPayload.java` — the payload is rebuilt key by key there and a new key that is
not named is silently dropped**), `web/js/app.js`, `web/js/format.js`, `web/themes/neon/`,
`web/themes/plain/`, `e2e/layout/check_actions.py`, `docs/THEMING.md`

Requires: the phone on adb, and a reachable PC, for everything but the unit tests.

## Goal

Two buttons in the bottom-left corner of the panel, under the clock: mute the PC's speakers,
mute the PC's microphone. Tap and the PC obeys.

## The space already exists

`#shortcuts` has been in the sidebar since T6.1 — `align-self: end`, a 56px minimum, a column
grid, and nothing in it. It was left empty on purpose so that adding the buttons would be a
fill and not a re-layout. This is the task it was left for.

## The hard part is not the buttons, it is invariant 1

**The page cannot make the request.** `web/` has no network code at all, by design: the WebView
is served from `https://appassets.androidplatform.net/`, so reaching a `http://` LAN address
from JavaScript is mixed content and is blocked (ADR 0002). The acceptance of T1.2 greps `web/`
for `fetch(` and must keep exiting 0 after this task.

So a tap has to cross into Java. That means a `@JavascriptInterface`, which is **the first
inbound bridge this app has had** — `onData`, `onPcState` and `onThermal` all run the other
way, from Java into the page. Two consequences, and both belong in the code review:

- `addJavascriptInterface` exposes a Java object to every script in the WebView. The panel's
  scripts are all local assets over the virtual https origin and the WebView loads nothing
  else, which is what makes it safe — say so at the call site, and keep the interface to one
  method taking one string.
- The method must **not** be a passthrough. `invoke(id)` takes an id, matches it against a
  small set the Java side knows, and calls the poller with a constant. An id that arrives from
  the page and is concatenated into a URL is the same mistake T8.1's ADR exists to prevent,
  made on the other side of the wire.

## Steps

1. **Java: one interface, one method.** `window.__actions.invoke(id)`. Off the main thread —
   it is an HTTP request — and onto the same executor `DataPoller` already uses rather than a
   new one.
2. **Java: the POST.** `POST http://<pc>:<port>/action/<id>` with the same short timeout the
   data poller uses, and a logcat marker per attempt: `action=mute-audio result=ok` /
   `=err`. Android exposes no way to read what is on screen (ADR 0009), so the marker is how
   the E2E suite will assert this, exactly as `ping=` and `data=` do.
3. **Nothing happens while the PC is away.** The buttons are dead when `PcState` is OFFLINE —
   there is nothing to mute, the screen is black anyway, and a queued action that fires on
   reconnect would mute the PC minutes after somebody pressed a button they could not see.
4. **The page: which buttons exist is config, not code.** The enabled action ids ride the
   payload the way `theme` does (T6.7), so adding a third button later is a config change on
   the PC and not a rebuild. An empty list renders nothing and `#shortcuts` stays the empty
   strip it is today.
5. **The buttons are markup, so they belong to the theme.** `render(payload, root)` draws them;
   `host.js` gains nothing. Core's half is one call — a theme asks it to invoke an id, and core
   decides whether that is possible and reaches Java. `docs/THEMING.md` gains a section: the
   action contract, the ids, and that a theme must render *nothing* for an action it does not
   recognise rather than a button that cannot work.
6. **Touch targets, not mouse targets.** 56px minimum on both axes — this is a phone at arm's
   length with no pointer, and the two buttons sit next to each other. A mis-tap that mutes the
   microphone instead of the speakers is the failure this number prevents.
7. **Feedback on the press.** The panel cannot know the PC's mute state — T8.1's toggles report
   one, but only at the moment of the call — so the button shows *the last result*, not a live
   state, and shows it as such: a brief acknowledgement on `ok`, a visible failure on `err`,
   and nothing pretending to be a state it is not. A button that lies about whether the mic is
   live is worse than no button.

The two negated greps are T1.2's and T6.7's, re-run here on purpose: this is the task most
likely to break either — the first by making the page talk to the PC, the second by putting a
button in `app.js` because that is where the click handler wanted to live.

On the device, with the PC up:

```bash
adb logcat -c
# tap the speaker button
adb logcat -d -s DeskPanel | grep -q 'action=mute-audio result=ok'
adb logcat -d -s DeskPanel | grep -q 'action=mute-mic result=ok'
```

`adb logcat -c` **before** the taps, never after: `-d -s DeskPanel -t N` filters after taking
the last N lines, so it can look empty on a healthy app.

## Manual check

- Something audible playing on the PC. Tap the speaker button; it stops. Tap again; it returns.
- A recording meter open. Tap the mic button; it dies. Tap again; it comes back.
- Press a button with the PC off (or the server stopped): nothing is sent, nothing is queued,
  and the panel is black anyway — confirm with `adb logcat` that no `action=` line appears.
- Tap each button twenty times quickly. Twenty toggles, no crash, no queue of pending requests,
  and `/ping` never misses a beat — watch the panel stay lit while you do it.

## What was actually done, 2026-09-26 (wave 27)

Every step was followed. Four notes.

- **The bug this task's own layers could not catch.** `DataPayload.merge` rebuilds the payload
  key by key on its way into the WebView and nothing named `actions`, so the phone drew no
  buttons with a correct server, a correct page and a correct bridge. Unit tests, the browser
  harness and `./gradlew test` were all green. **The device install is what found it.** That
  file's own comment had warned about exactly this, written when T6.4 shipped the identical
  failure — so if this task's `Files:` line had named `DataPayload.java`, the pass would have
  been free. It does now.

- **The core/theme seam.** Step 5 says "`host.js` gains nothing", and it does not: `invoke` is
  added by `js/app.js` to the object `host.js` already exposes. `host.js` is the core's contact
  with the *DOM*, and this is a native bridge — the same thing `window.onData` is, pointing the
  other way — so it belongs in `app.js`. A theme finds it at `DeskPanel.invoke(id, done)` and
  has one place to look.

- **`invoke` returns a boolean and the callback arrives later.** `false` means nothing was sent
  and no result is coming, which a theme has to settle itself or the button sits pressed for
  ever. That is asserted in `e2e/layout/check_actions.py`, the sixth browser check and this
  task's extra deliverable: the right buttons in the right order, 56px on both axes, an id and
  nothing url-shaped reaching the bridge, and nothing sent while the PC is away. Mutation-tested
  three ways.

- **`shortcutsFor` lives in `format.js`**, which keeps the rule "a theme renders nothing for an
  action it does not recognise" testable without a browser, and makes a third action a config
  change in one direction only: the PC can *remove* a button by editing a file and can add one
  only for an id the APK has words for.

The **manual check is done for Linux**, all four items: both toggles observed moving
`wpctl get-volume` on the sink and the source, the buttons pressed with the server stopped and
nothing sent, and nothing firing when it came back. **The twenty-taps item was not done** — each
button was pressed four times, not twenty, and nobody watched `/ping` while presses queued.

## Changed from the chair, 2026-09-26, after the buttons were seen on the device

Four asks, and one of them moves a rule this file wrote.

- **No caption, bigger icon.** The word moved to the accessible name; the icon went 22px → 36px
  and took the room back. A theme may still draw the word — `shortcutsFor` still returns it.

- **A cross when the PC is muted, and no cross when it is not.** This contradicts **step 7 as
  written** ("shows *the last result*, not a live state"), and the reason step 7 said that was
  that every Linux mixer toggles in silence, so the state genuinely was not knowable.

  Rather than draw a cross on an inference, **the server now measures it**: a second, read-only
  command after the toggle (`wpctl get-volume`, `pactl get-sink-mute`), reported as the response's
  `state`. ADR 0015 is amended with the three limits that keep it honest — it is the *last known*
  state and says so in the accessible name, a failed press does not move it, and a read-back that
  fails is `unknown` rather than a failed action.

  **The sentence step 7 exists to protect is untouched**: a button that says the microphone is off
  while it is live is a privacy failure. What changed is that the panel stopped having to guess.

- **The clipped corner.** `#sidebar` is `overflow: hidden` and the strip sat flush against it, so
  the button's own 1px border landed on the clip. 6px of clearance, and 6 rather than less because
  the burn-in shift moves the panel up to 4px and anything smaller brings the cut back for part of
  every cycle.

- **Taller and narrower.** 144×56 → 104×72. 56px stays the floor on both axes, which
  `e2e/layout/check_actions.py` still asserts.

All four verified on the device: both crosses appear and clear following `wpctl`, and the border
is whole.
