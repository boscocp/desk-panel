# T6.6 — A very slow scroll, but only when a card overflows

Size: M · Prereqs: T6.7, T5.1 · Files: `web/js/format.js`, `web/themes/neon/`,
`web/themes/plain/`, `e2e/layout/`

**Paths amended by T6.7.** `app.js` and `css/style.css` were where the rows were built and
styled when this was written; both are a theme's now, and a scroll is presentation. What
stayed in core is the arithmetic, in `format.js`, because "is this card hiding a row" is a
question about the panel and not about a look — `docs/THEMING.md` says so, and the plain theme
answers it too.

Requires: the phone, for the manual check only

## Goal

Let the owner configure more rows than fit and still see all of them, by scrolling each
overflowing card slowly enough that the panel never looks busy.

## The problem this is fixing

`style.css` says it outright today: *"The page is exactly one screen: nothing scrolls, and every
card clips its own content, so an extra ticker arriving from server config can never push a
section off the bottom edge."* That was the right call when the alternative was a broken layout.
Its cost is that the sixth ticker is **invisible** — not truncated, not marked, just absent,
with nothing on the panel saying so. Once T3.12 makes adding tickers easy, that cost is paid far
more often.

## Steps

1. A pure `overflowsBy(rowCount, visibleRows)` in `format.js` — how many rows are hidden, zero
   when they all fit. Pure, so the decision is tested without a DOM; the acceptance asserts on
   it rather than on pixels.
2. Scroll **only** when it returns non-zero. A card that scrolls with two rows in it is motion
   for its own sake, and this panel sits in someone's peripheral vision all day.
3. Slow: on the order of one row every few seconds, and a pause at the top and bottom of each
   pass. The number belongs in a CSS custom property so T6.7's themes can set it.
4. **The refresh must not restart the scroll.** `window.onData` rebuilds each list wholesale
   (`container.textContent = ''`), so any CSS animation resets every 60s and the card would
   never reach the rows it exists to reveal. Either update rows in place when the symbol set has
   not changed, or carry the scroll offset across the rebuild. This is the whole of the task's
   difficulty.
5. Loop rather than snap back: a seamless wrap, or a slow return pass. A jump is the one motion
   the eye cannot ignore.

## Acceptance

```bash
node --test "web/test/**/*.test.js"
node --check web/themes/neon/theme.js
node --check web/themes/plain/theme.js
python e2e/layout/check_layout.py
python e2e/layout/check_layout.py --theme plain
python e2e/layout/check_scroll.py
python e2e/layout/check_scroll.py --theme plain
```

The node tests cover `overflowsBy` at the boundary in both directions — exactly filling the
card must not scroll, one more row must — and that a refresh which changes no rows produces
an identical plan. That is only half of step 4, and the weaker half: it says the theme will
ask for the same animation, not that the browser keeps running the one it had.

`check_scroll.py` is the other half, and it is new for this task. A pure function cannot see
an animation and a layout measurement is one frame, so the only way to check "the refresh must
not restart the scroll" is to drive a real browser over time: deliver an overflowing payload,
sample the card's transform, sleep, sample it again, deliver the identical payload, and assert
the offset did not go back to the top. It also asserts the card moves at all — a declaration is not a movement — and
that a payload which fits takes the scroll away and leaves nothing translated. The
restart-on-refresh assertion was mutation-tested against the obvious wrong implementation
(rebuilding the animated element inside `render()`), which it catches at −37px against 0.

`check_layout.py` grew a third pass for this task, `e2e/layout/overflow.js`: more rows than
any card on either theme can show. It is the only pass in the harness that requires something
to *happen* rather than requiring that nothing goes wrong, and it fails in both directions —
a card that overflows without declaring `data-scroll`, and a card that declares it with
everything already on screen. Both were mutation-tested when they were written.

**The second acceptance line was replaced, not amended.** It read:

```bash
! grep -n 'overflow: hidden' web/themes/neon/theme.css | grep -q 'card-list'
```

with the gloss *"the clip that hid the rows is gone from the lists it hid them in"*. Two
things are wrong with it, and the second is the one that matters.

It never asserted anything. `grep -n 'overflow: hidden'` prints the declaration's own line,
and in this stylesheet the selector `.card-list,` is on a line of its own two rows above it —
so the second `grep -q 'card-list'` never matched, the `!` always succeeded, and the command
exited 0 against every possible state of the file. That is the failure mode STATUS.md calls
"an assertion that passes on a log nobody has proved contains anything", in CSS.

And what it asked for is wrong on its own terms. **The clip is what makes the scroll work.**
The rows sit in a window and the window is what hides the ones that have not arrived yet;
remove `overflow: hidden` from the list and the extra rows spill over the cards below instead
of waiting their turn — which `check_layout.py` fails, correctly. The line also contradicts
T6.1's acceptance, which asserts that the shared `.card-list, .card` block clips, so one of
the two had to give.

What was actually wrong was never the clip. It was that a card could hide a row and say
nothing. The replacement asserts that instead, and it can only be satisfied by the feature
existing.

## Manual check

- With two tickers, nothing moves at all. This is the one most likely to regress, and it is
  the one thing here `check_layout.py` now also checks on its own.
- With ten, every row becomes readable within one pass, and the movement is slow enough to be
  unnoticeable unless looked at.
- A data refresh mid-pass does not jump, restart, or skip a row.

## Notes

- Movement helps burn-in rather than hurting it, so this pulls in the same direction as T6.2's
  layout shift. Check they do not fight: two independent motions on one card would be visible in
  a way neither is alone.
- The clock and weather cards do not overflow and must not acquire motion from a shared rule.
- `prefers-reduced-motion` is worth honouring even though this device will never set it, because
  the browser is where this gets developed.
