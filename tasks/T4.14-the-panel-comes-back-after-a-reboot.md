# T4.14 — The panel comes back after a reboot

Size: S · Prereqs: T4.10 · Files:
`android/app/src/main/java/dev/bosco/deskpanel/BootReceiver.java`,
`android/app/src/main/java/dev/bosco/deskpanel/PanelService.java`,
`android/app/src/main/AndroidManifest.xml`,
`docs/adr/0025-the-app-starts-itself-at-boot.md`, `docs/adr/0023-a-watchdog-brings-the-service-back.md`,
`docs/PHONE-SETUP.md`, `docs/INSTALL-PHONE.md`

Requires: the phone on adb, a reboot of it, and a person to type the PIN if it has one

## Goal

Reported from the chair on 2026-11-04: the owner logged in and the panel did not come on. The
phone had shut down and booted at about 12:25, the same minute as the login. The PC server was
up. The app had no process three minutes later, although MIUI Autostart was allowed. The app
had no boot receiver, and the documentation's claim that Autostart brings it back had never
been measured (T2.4).

## Steps

1. `BootReceiver`, not exported, filters `BOOT_COMPLETED` and calls
   `PanelService.startAtBoot`. It starts the service and not the Activity
   ([ADR 0025](../docs/adr/0025-the-app-starts-itself-at-boot.md)).
2. `RECEIVE_BOOT_COMPLETED` in the manifest.
3. `PanelService` logs `service started at boot` for a fresh start with `ACTION_BOOT`.
4. `PHONE-SETUP.md`, `INSTALL-PHONE.md` and ADR 0023 stop saying that the app has no boot
   receiver, and say what Autostart does and does not do.

## Acceptance

```bash
docker compose -f docker/compose.yml run --rm build ./gradlew test
grep -q 'android.intent.action.BOOT_COMPLETED' android/app/src/main/AndroidManifest.xml
grep -q 'android:name=".BootReceiver"' android/app/src/main/AndroidManifest.xml
grep -q 'RECEIVE_BOOT_COMPLETED' android/app/src/main/AndroidManifest.xml
grep -q 'startAtBoot' android/app/src/main/java/dev/bosco/deskpanel/BootReceiver.java
test -f docs/adr/0025-the-app-starts-itself-at-boot.md
python scripts/check_acceptance.py
```

On the phone, with this build installed, Autostart and "Display over other apps" allowed, and a
PC logged in:

```bash
adb shell appops get dev.bosco.deskpanel SYSTEM_ALERT_WINDOW | grep -q allow
adb shell dumpsys package dev.bosco.deskpanel | grep -q 'stopped=false'
adb reboot && adb wait-for-device
adb shell 'while [ "$(getprop sys.boot_completed)" != 1 ]; do sleep 2; done'
adb logcat -b main -G 4M
adb shell 'until dumpsys user | grep -q RUNNING_UNLOCKED; do sleep 2; done'
timeout 180 sh -c 'until adb logcat -d -s DeskPanel | grep -q "service started at boot"; do sleep 3; done'
timeout 30 sh -c 'until adb shell dumpsys activity activities | grep -q "ResumedActivity.*dev.bosco.deskpanel"; do sleep 2; done'
```

`./gradlew test` covers nothing of this change: the receiver is Android glue with no logic to
lift into a plain class, as in T4.11. The device run is the test. `wait-for-device` returns
when adbd is up, well before `sys.boot_completed`, so the loop waits for the property. With a
PIN, `BOOT_COMPLETED` waits for the first unlock, which is why the run waits for
`RUNNING_UNLOCKED`: somebody types the PIN there. On 2026-11-05 the receiver ran 42 s after the
unlock. The main buffer goes back to 256 KiB at boot (TESTING.md), so it is enlarged before the grep.

## Manual check

- The next time the phone restarts on its own (an update, a power cut with the battery flat),
  the panel is on screen with the PC once the PIN is typed, without the app being opened.
