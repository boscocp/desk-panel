# T8.1 — `POST /action/{id}` actually acts

Size: L · Prereqs: T3.7, T3.11, T3.12 · Files: `server/server.py`, `server/actions.py`,
`server/config.example.toml`, `server/config.example.json`, `server/tests/`,
`docs/adr/0015-the-panel-can-act-on-the-pc.md`, `docs/ARCHITECTURE.md`

Requires: none for the tests. A desktop session for the manual check, one per OS.

## Goal

Mute the PC's speakers and its microphone from the panel, without giving anything on the LAN a
shell.

## Why this is the first task where the server stops being read-only

Every route the server has today answers a question. This one changes the machine it runs on,
and the server has **no authentication** — deliberately, because it is LAN-only and bound to a
login session (invariant 2, ADR 0004). Those two facts were compatible while the worst a
stranger on the Wi-Fi could do was read a stock price.

So the allowlist is not a nicety, it is the whole design, and T3.7 wrote the constraint down
before anything existed:

> the request carries an id and **nothing else** — never a command, path or argument

That has to survive contact with an implementation. **Write ADR 0015 first**, and state in it:
what an action may be, why the id can never be interpolated into a command line, why the
allowlist lives in config rather than in the request, and what an attacker on the LAN can do
with this endpoint (the honest answer is: exactly the actions the owner enabled, as often as
they like — so every action must be idempotent-ish and harmless to repeat, which mute is and
`shutdown` is not).

## Steps

1. **`server/actions.py`**, standard library only, no Android and no HTTP — so it is unit
   testable the way `config_format.py` is.
2. **A closed catalogue, in code, not in config.** `config.toml` says *which* actions are
   enabled; it never says what they run. `actions = ["mute-audio", "mute-mic"]` is a list of
   names the server already knows; a name it does not know is a config error at load, named in
   the message, not a 404 at request time — a typo must be found when the owner restarts the
   server, with a console in front of them, not silently at the desk.
3. **Two actions to start**: `mute-audio` and `mute-mic`, both **toggles**, because the panel
   has no reliable way to know the current state and a button that only mutes is half a button.
4. **The command is chosen by platform**, the same way T3.11 does it — `sys.platform`, and a
   table, never a string built from anything that arrived over the network:
   - **Linux**: `wpctl set-mute @DEFAULT_AUDIO_SINK@ toggle` (PipeWire), falling back to
     `pactl set-sink-mute @DEFAULT_SINK@ toggle`. `@DEFAULT_AUDIO_SOURCE@` /
     `@DEFAULT_SOURCE@` for the microphone. Probe which of the two exists at startup and log
     it, so "nothing happened" is diagnosable.
   - **macOS**: `osascript -e 'set volume output muted not (output muted of (get volume settings))'`.
     Input has no toggle in that API — read `input volume`, and store the previous level so
     unmuting restores it rather than jumping to 100.
   - **Windows**: PowerShell with `Add-Type` against the Core Audio `IAudioEndpointVolume`
     COM interface, `eRender` for output and `eCapture` for input. **No third-party tool** —
     `nircmd` is the usual answer and it is a download the owner has to trust, which is a worse
     trade than a long `-Command` string this repo can read.
5. **`subprocess.run`, never `shell=True`**, argument list only, with a timeout (2s is
   generous; this is a local mixer call). A timeout is a failure, not a hang: the phone gives
   the whole request a few seconds and a blocked action thread must not sit on a worker while
   `/ping` queues behind it (invariant 2 — the threading note in `Server` explains why that
   matters more here than it looks).
6. **Responses.** `200` with `{"ok": true, "id": ..., "state": "muted"|"unmuted"|"unknown"}` —
   the state the command reports, or `unknown` where the platform cannot say. `404` for an id
   not in the enabled set, and it must not run anything to find that out. `501` where the
   platform has no implementation. `500` with a short body on a non-zero exit, and the
   stderr goes to the server's log, never to the response.
7. **`POST` only**, as T3.7 reserved. A `GET` that changes the machine is one browser
   prefetch away from muting the PC by accident.

## Acceptance

```bash
python -m unittest discover -s server/tests -t .
python server/probe.py --serve --url /action/not-an-action --method POST --expect-status 404
python -c "import ast,sys; src=open('server/actions.py').read(); sys.exit(0 if not any(isinstance(n,ast.keyword) and n.arg=='shell' for n in ast.walk(ast.parse(src))) else 1)"
! grep -rnE 'shell\s*=\s*True' server/
```

The AST check is there because `grep` for `shell=True` passes against `shell = True` and against
a variable, and this is the one line in the project where being clever about the check is worth
it.

Unit tests, with the runner injected so nothing is executed:

- every enabled id resolves to an **argument list**, never a string;
- an id that is not enabled resolves to nothing and the runner is not called at all — assert on
  the fake's call count, not on the response alone;
- an id containing `;`, `&&`, a path separator or a newline is rejected by `action_id()` before
  it reaches the catalogue (`action_id` already refuses `/` and `?`; this widens it and proves
  it);
- a non-zero exit becomes a 500 and the stderr does not appear in the body;
- a timeout becomes a 500 rather than raising;
- an unknown name in `config.toml` fails the load with the name in the message.

## Manual check

One per platform, and each is a human at a keyboard:

- Play something audible, `POST /action/mute-audio` twice, and hear it stop and start.
- Open a recording meter, `POST /action/mute-mic` twice, and watch it die and come back.
- On macOS, mute the input at a non-zero volume and confirm unmuting returns that volume and
  not 100.

## Notes

- **Order matters: this lands before T8.2.** The buttons are useless without it, and the
  temptation while building them is to have the page do something else in the meantime.
- `shutdown`, `sleep` and `lock` are the obvious next actions and are deliberately not here.
  They are not repeatable, and the ADR's threat model is written around actions that are.
