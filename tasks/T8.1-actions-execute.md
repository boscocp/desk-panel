# T8.1 — `POST /action/{id}` actually acts

Size: L · Prereqs: T3.7, T3.11, T3.12 · Files: `server/server.py`, `server/actions.py`,
`server/config.example.toml`, `server/config.example.json`, `server/tests/`,
`docs/adr/0015-the-panel-can-act-on-the-pc.md`, `docs/ARCHITECTURE.md`

Requires: none for the tests. A desktop session for the manual check, one per OS.

## Goal

Mute the PC's speakers and its microphone from the panel, without giving anything on the LAN a
shell.

## Why this is the first task where the server stops being read-only

Every route the server has today answers a question. This one changes the machine it runs on,
and the server has **no authentication** — deliberately, because it is LAN-only and bound to a
login session (invariant 2, ADR 0004). Those two facts were compatible while the worst a
stranger on the Wi-Fi could do was read a stock price.

So the allowlist is not a nicety, it is the whole design, and T3.7 wrote the constraint down
before anything existed:

> the request carries an id and **nothing else** — never a command, path or argument

That has to survive contact with an implementation. **Write ADR 0015 first**, and state in it:
what an action may be, why the id can never be interpolated into a command line, why the
allowlist lives in config rather than in the request, and what an attacker on the LAN can do
with this endpoint (the honest answer is: exactly the actions the owner enabled, as often as
they like — so every action must be idempotent-ish and harmless to repeat, which mute is and
`shutdown` is not).

## Steps

1. **`server/actions.py`**, standard library only, no Android and no HTTP — so it is unit
   testable the way `config_format.py` is.
2. **A closed catalogue, in code, not in config.** `config.toml` says *which* actions are
   enabled; it never says what they run. `actions = ["mute-audio", "mute-mic"]` is a list of
   names the server already knows; a name it does not know is a config error at load, named in
   the message, not a 404 at request time — a typo must be found when the owner restarts the
   server, with a console in front of them, not silently at the desk.
3. **Two actions to start**: `mute-audio` and `mute-mic`, both **toggles**, because the panel
   has no reliable way to know the current state and a button that only mutes is half a button.
4. **The command is chosen by platform**, the same way T3.11 does it — `sys.platform`, and a
   table, never a string built from anything that arrived over the network:
   - **Linux**: `wpctl set-mute @DEFAULT_AUDIO_SINK@ toggle` (PipeWire), falling back to
     `pactl set-sink-mute @DEFAULT_SINK@ toggle`. `@DEFAULT_AUDIO_SOURCE@` /
     `@DEFAULT_SOURCE@` for the microphone. Probe which of the two exists at startup and log
     it, so "nothing happened" is diagnosable.
   - **macOS**: `osascript -e 'set volume output muted not (output muted of (get volume settings))'`.
     Input has no toggle in that API — read `input volume`, and store the previous level so
     unmuting restores it rather than jumping to 100.
   - **Windows**: PowerShell with `Add-Type` against the Core Audio `IAudioEndpointVolume`
     COM interface, `eRender` for output and `eCapture` for input. **No third-party tool** —
     `nircmd` is the usual answer and it is a download the owner has to trust, which is a worse
     trade than a long `-Command` string this repo can read.
5. **`subprocess.run`, never `shell=True`**, argument list only, with a timeout (2s is
   generous; this is a local mixer call). A timeout is a failure, not a hang: the phone gives
   the whole request a few seconds and a blocked action thread must not sit on a worker while
   `/ping` queues behind it (invariant 2 — the threading note in `Server` explains why that
   matters more here than it looks).
6. **Responses.** `200` with `{"ok": true, "id": ..., "state": "muted"|"unmuted"|"unknown"}` —
   the state the command reports, or `unknown` where the platform cannot say. `404` for an id
   not in the enabled set, and it must not run anything to find that out. `501` where the
   platform has no implementation. `500` with a short body on a non-zero exit, and the
   stderr goes to the server's log, never to the response.
7. **`POST` only**, as T3.7 reserved. A `GET` that changes the machine is one browser
   prefetch away from muting the PC by accident.

## Acceptance

```bash
python -m unittest discover -s server/tests -t .
python server/probe.py --serve --url /action/not-an-action --method POST --expect-status 404
python -c "import ast,sys; src=open('server/actions.py').read(); sys.exit(0 if not any(isinstance(n,ast.keyword) and n.arg=='shell' for n in ast.walk(ast.parse(src))) else 1)"
! grep -rnE 'shell\s*=\s*True' server/
```

The AST check is there because `grep` for `shell=True` passes against `shell = True` and against
a variable, and this is the one line in the project where being clever about the check is worth
it.

Unit tests, with the runner injected so nothing is executed:

- every enabled id resolves to an **argument list**, never a string;
- an id that is not enabled resolves to nothing and the runner is not called at all — assert on
  the fake's call count, not on the response alone;
- an id containing `;`, `&&`, a path separator or a newline is rejected by `action_id()` before
  it reaches the catalogue (`action_id` already refuses `/` and `?`; this widens it and proves
  it);
- a non-zero exit becomes a 500 and the stderr does not appear in the body;
- a timeout becomes a 500 rather than raising;
- an unknown name in `config.toml` fails the load with the name in the message.

## Manual check

One per platform, and each is a human at a keyboard:

- Play something audible, `POST /action/mute-audio` twice, and hear it stop and start.
- Open a recording meter, `POST /action/mute-mic` twice, and watch it die and come back.
- On macOS, mute the input at a non-zero volume and confirm unmuting returns that volume and
  not 100.

## Windows runbook — written 2026-09-26, NOT YET RUN

The Windows branch of `server/actions.py` has never executed. It is ~30 lines of C# handed to
`Add-Type`, written from the Core Audio interface definitions and corrected once by review
before anything ran it. **Assume it is broken until these steps say otherwise**, and do them in
this order — each one fails faster than the one after it.

### 0. The server on that box is running the old code

It was started by the Scheduled Task at the last logon and holds `server.py` as it was then, so
`POST /action/mute-audio` answers **501** there no matter what is on `main` (this is T3.13's
whole subject). Pull, then:

```powershell
git pull
python scripts\after_update.py
```

### 1. Enable the actions

In the `--config` the Scheduled Task actually passes — `schtasks /query /tn desk-panel /xml`
names it if you are not sure:

```toml
actions = ["mute-audio", "mute-mic"]
```

### 2. Prove the config loads and see which command it resolved to

```powershell
python server\server.py --check-only --config <the path from step 1>
```

Expected, on stderr:

```
notice: actions enabled: mute-audio, mute-mic
  mute-audio: powershell
  mute-mic: powershell
```

An unknown name is fatal here with the name in the message. If `powershell` is not found the
line says so and the endpoint will answer 501 — that is the design, not a bug, but on Windows it
would mean `powershell.exe` is off `PATH`, which is worth knowing before anything else.

### 3. Run the PowerShell by hand, outside the server

**This is the step most likely to fail and the fastest to read.** A C# syntax error, a wrong
GUID or a wrong vtable slot all surface here as a PowerShell error with a line number, instead
of as a 500 with the detail in the server log.

```powershell
python -c "import sys; sys.path.insert(0,'.'); from server import actions; print(actions.candidates('mute-audio','win32')[0][-1])" > $env:TEMP\mute.ps1
powershell -NoProfile -NonInteractive -File $env:TEMP\mute.ps1
```

It should print `muted` or `unmuted` and the speakers should change. Two known risks, both
already corrected once by review and neither verified by running:

- **the vtable.** `IAudioEndpointVolume` has **eleven** methods before `SetMute` — the two
  notify registrations, `GetChannelCount`, four master-volume calls and four per-channel ones.
  COM dispatches by slot, so a miscount does **not** throw: it silently calls a different method.
  If this prints a word and the volume does not change, that is the symptom.
- **`bool` marshalling.** A bare C# `bool` on a COM interface marshals as a 2-byte
  `VARIANT_BOOL`, not a Win32 `BOOL`.

Then the microphone, which is the same code with `Toggle(1)`:

```powershell
python -c "import sys; sys.path.insert(0,'.'); from server import actions; print(actions.candidates('mute-mic','win32')[0][-1])" > $env:TEMP\mic.ps1
powershell -NoProfile -NonInteractive -File $env:TEMP\mic.ps1
```

### 4. Time it, because the timeout is a guess

```powershell
Measure-Command { powershell -NoProfile -NonInteractive -File $env:TEMP\mute.ps1 }
```

`Add-Type` invokes the C# compiler on **every** press. `timeout_for("win32")` is **15s** against
2s everywhere else, and that number was chosen by reasoning rather than by measuring. If this
comes back near or over 15s, the timeout is wrong and the fix is the timeout, not the command.
Record the number here either way — it is the only measurement this branch will ever have.

### 5. Through the server, which is what the panel does

```powershell
curl.exe -s -o NUL -w "%{http_code}`n" -X POST http://127.0.0.1:8777/action/mute-audio
```

`200` and the speakers change. `500` means it ran and failed — the reason is on the server's
stderr, which the Scheduled Task sends to the log file named in its arguments, never to the
response.

**Watch for a console window flashing.** `_default_runner` passes `CREATE_NO_WINDOW` on Windows
precisely so a mute press does not throw a black rectangle over whatever is on screen; that flag
has never been observed working either.

### 6. The browser refusal, which is the security property

```powershell
curl.exe -s -o NUL -w "%{http_code}`n" -X POST -H "Origin: https://evil.example" http://127.0.0.1:8777/action/mute-audio
```

Must be **403**, and the speakers must not change. Then confirm the real thing still works by
repeating step 5 — a check that refuses everything is not a check.

### 7. Put it back

```toml
actions = []
```

unless the panel is meant to keep them, and restart through `after_update.py` again.

## Notes

- **Order matters: this lands before T8.2.** The buttons are useless without it, and the
  temptation while building them is to have the page do something else in the meantime.
- `shutdown`, `sleep` and `lock` are the obvious next actions and are deliberately not here.
  They are not repeatable, and the ADR's threat model is written around actions that are.

## What was actually done, 2026-09-26 (wave 26)

The steps were followed, ADR first. Four notes a reader of this file needs.

- **The `--serve` acceptance line needs port 8777 free**, and on a machine where the panel is
  installed the user unit holds it — `probe.py` refuses to probe a server it did not start,
  deliberately, so that an acceptance cannot go green against the installed service instead of
  the working tree. It was run against a temp config on a spare port, which exercises the same
  code:

  ```bash
  sed 's/^port = .*/port = 8791/' server/config.example.toml > /tmp/t81.toml
  DESK_PANEL_CONFIG=/tmp/t81.toml python server/probe.py --serve --port 8791 \
      --url /action/not-an-action --method POST --expect-status 404
  ```

  Running the line as written means `systemctl --user stop desk-panel` first, which takes the
  panel down for the duration.

- **The acceptance's `! grep -rnE 'shell\s*=\s*True' server/` fails on a comment.** The first
  cut of `actions.py` explained the AST check by quoting the literal, and the grep found it. The
  comment is reworded; the lesson is that this particular acceptance forbids the string in prose
  as well as in code, which is worth knowing before writing a docstring about it.

- **Review found three things in the two branches that have never run**, all of them the kind
  only reading catches:
  - The Windows `IAudioEndpointVolume` declared **eight** placeholder methods before `SetMute`.
    It has eleven — the two notify registrations, `GetChannelCount`, four master-volume calls
    and four per-channel ones. COM dispatches by vtable slot, so this does not fail, it calls
    `SetChannelVolumeLevelScalar` instead and mutes nothing. A test now counts the slots.
  - **Step 5's 2s is a Linux and macOS number.** `Add-Type` compiles that C# on *every* press,
    in a fresh `powershell -NoProfile`, so 2s made the whole platform answer 500 on a timeout
    with nothing actually wrong. `timeout_for()` gives win32 15s and leaves the rest at 2s.
  - **The macOS output toggle ended on `set volume output muted …`**, a command with no result,
    so osascript printed nothing and `mute-audio` would always have reported `unknown`. It
    returns the word now, the way the input toggle already did. Relatedly, `state_from` read
    `missing value` as `muted`: that is AppleScript for "the API would not say", and answering
    `muted` to it is the guess ADR 0015 forbids.

- **`POST` alone does not keep a web page out, and the ADR said it did.** A cross-origin form
  with `enctype=text/plain` is a CORS *simple request*: no preflight, so nothing here is asked,
  and the attacker not being able to read the response does not matter because the mute has
  already happened. The endpoint's reach was **every site the owner opens**, not every machine
  on their LAN. It refuses with 403 when `Origin` or `Sec-Fetch-Site` is present — a browser
  announces itself, and `HttpURLConnection`, `curl` and `probe.py` announce nothing, which is
  what keeps the acceptance line above meaning what it says. ADR 0015 is amended, not patched
  around. Found by review; **this is the finding this task should have had in its own steps.**

- **Step 4's macOS input branch is written and has never run.** It keeps the previous level in
  `dev.bosco.deskpanel`'s preferences through `do shell script`, which is the one shell in the
  table and is named in ADR 0015. It is also the only branch with logic rather than a single
  call, so it is the one most likely to be wrong.

- **The `{}`/`%s` scan for placeholders did not survive contact.** It was written to prove there
  was nothing to interpolate into and it failed on the Windows command, which is C# and full of
  braces. Replaced by the property it was a proxy for: **the id never appears in any argument
  list**, asserted for every action on every platform.

Step 3's "config says which actions are enabled" changed shape: `actions` was a reserved empty
table and is a list of names now. An empty table still loads as "nothing enabled", because
`config.example.toml` shipped `[actions]` and installed configs have it — an update that refuses
to start is a worse failure than a shape change.

The **Linux manual check is done**: with both enabled, two POSTs to `/action/mute-mic` moved
`wpctl get-volume @DEFAULT_AUDIO_SOURCE@` to `[MUTED]` and back, and `mute-audio` did the same to
the sink. **macOS and Windows are not**, and neither is the macOS input-volume restore.
