# T10.4 — The notes guard checks the heading and not the thing under it

Size: S · Prereqs: none · Files: `scripts/check_harness_notes.py`, `docs/harness-notes/README.md`

Requires: none

## Goal

`scripts/check_harness_notes.py` asserts that every finished wave has a note carrying three
headings — `## What ran`, `## What the review found`, `## What is not proven`. It checks that the
**strings are present** and never looks at what follows them.

Found the way findings here are supposed to be found: wave 30 shipped its note with

```markdown
## What the review found

<!-- filled in after the review runs -->
```

and `make check` was green. The heading is written before the review runs by design — the section
cannot be filled until there is something to fill it with — so the placeholder is the normal
workflow and the guard has nothing to say about whether it was ever replaced.

A guard that reads the label and not the thing is this repository's recurring failure, and this
one was caught by a review of a wave whose subject was checks that cannot fail.

## Steps

1. **A required section needs content.** Non-blank, not only a comment, and past some floor that
   a placeholder cannot clear — a handful of lines of prose rather than a character count picked
   for the sake of having one. Whatever it is, state the reason in the code.

2. **A comment-only section is empty.** `<!-- ... -->` is how a placeholder is written here, and
   the check must not be satisfied by one.

3. **`--self-test`, which this script does not have.** It is one of four guards without one
   (`check_acceptance`, `check_harness_notes`, `check_permission_parity`, `check_status`), named
   in [the design review](../docs/DESIGN-REVIEW.md). Prove each rule can fail: a note with a
   heading and nothing under it, a note with a heading and a comment, and a complete note that
   passes. A guard whose rules are not shown failing is the thing this task is about.

4. **Do not let it fail the wave being written.** The note is created before the review runs, so
   the guard has to be red only once the wave's section is *claimed finished* — the simplest
   honest rule is that it runs on notes for waves already in `STATUS.md`, which is what it
   already does, and a session writing its note mid-wave sees it red until it is written. Say so
   in `docs/harness-notes/README.md` so the redness reads as a reminder rather than a bug.

## Acceptance

```bash
python scripts/check_harness_notes.py --self-test
python scripts/check_harness_notes.py
make lint-selftests 2>&1 | grep -q 'check_harness_notes'
make check
```

The third line is the wiring: a `--self-test` no target invokes is the defect this repository has
paid for twice already (TT.12, and T10.3's narrower half).

## Notes

- The floor is a judgement call and should be generous. A guard that fires on a short but honest
  section teaches people to pad, which is worse than the placeholder it was written to catch.
- The same question applies to `check_status.py` and `check_acceptance.py`, which also read
  structure rather than substance. Out of scope here; worth a look if this one goes well.
