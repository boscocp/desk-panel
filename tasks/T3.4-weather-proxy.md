# T3.4 — `/weather` proxy

Size: S · Prereqs: T3.2 · Files: `server/providers_openmeteo.py`, `server/server.py`

## Goal

Current temperature, daily min and max, and a condition code for the configured city.

## Steps

1. Geocode the city name once at startup via
   `https://geocoding-api.open-meteo.com/v1/search?name=...`, then cache the coordinates. No
   need to geocode on every poll.
2. Forecast call:

   ```
   https://api.open-meteo.com/v1/forecast
     ?latitude=..&longitude=..
     &current=temperature_2m,weather_code
     &daily=temperature_2m_max,temperature_2m_min
     &timezone=America/Sao_Paulo
   ```

3. A **pure** `normalise(raw) -> dict` producing `{tempC, minC, maxC, code, city}`.
4. Cache for `weather_interval_s`.
5. `weather_code` is the standard WMO table. Mapping code to a human label belongs in
   `web/js/format.js`, not here — the server returns data, the panel decides wording.

## Acceptance

```bash
curl -sf http://localhost:8777/weather | python -m json.tool
```

Shows a plausible temperature for the configured city. Unit tests pass with no network.

## Notes

- Open-Meteo needs **no API key** for non-commercial use, and allows 10k requests/day. There is
  no secret to protect here; it goes through the proxy purely so the panel has one code path
  rather than two ([ADR 0004](../docs/adr/0004-server-is-login-signal-and-proxy.md)).
- The timezone parameter matters: without it the daily min and max are aligned to UTC days and
  look wrong in the evening.
