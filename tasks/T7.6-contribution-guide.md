# T7.6 — A contribution guide about keeping the code readable, and the templates that enforce it

Size: M · Prereqs: T7.5 · Files: `CONTRIBUTING.md`, `.github/PULL_REQUEST_TEMPLATE.md`,
`.github/ISSUE_TEMPLATE/bug.yml`, `.github/ISSUE_TEMPLATE/feature.yml`, `.githooks/commit-msg`,
`scripts/check_commit_msg.py`, `Makefile`

Requires: none

## Goal

This repository has an unusual property worth protecting: **it explains itself.** Comments say
why rather than what, the ADRs record what was rejected and on what evidence, and the task files
carry the reasoning that produced each commit. That survives exactly as long as the next
contributor understands it is the point.

So the contribution guide is not a style guide with a brace convention. It is an argument about
maintenance, with the mechanical parts automated so nobody has to enforce them by hand in review.

## Steps

1. **`CONTRIBUTING.md`**, and the readability section is the substance of it:

   - **Comments carry the *why*.** The repo's own examples are the teaching material — read
     `BatteryReading.ABSENT` or `PcState`'s ladder. A comment restating the code is noise; a
     comment explaining why -1 was the wrong sentinel is the thing that stops the bug returning.
   - **Logic stays out of Android classes** (`android/CLAUDE.md`), so it can be tested on the
     JVM. `ThermalState` and `PcState` are the pattern; a `View` with a decision in it is not.
   - **`web/js/format.js` is pure functions only**, which is why the web tests need no browser.
   - **The three invariants are not open for casual change.** Point at the README's statement of
     them and at the ADRs. A PR that breaks one is not wrong by definition — it needs an ADR.
   - **No new dependency without an argument.** See [T7.5](T7.5-running-locally.md): the empty
     dependency list is a design decision with its own consequences, not an accident of youth.
   - **A decision worth arguing about gets an ADR**, numbered, with the alternatives it rejected.
     Say how to write one and point at 0010 and 0014 as the models — both record the reasoning
     that a reader six months later would otherwise have to reconstruct.

2. **Conventional commits, written down and checked.** `feat:`, `fix:`, `docs:`, `test:`,
   `chore:`, `refactor:`, English, imperative, body explaining *why* when the subject cannot.
   `scripts/check_commit_msg.py` decides; `.githooks/commit-msg` is a three-line shim that calls
   it, installed with `git config core.hooksPath .githooks`, documented in the guide and wired to
   a `make hooks` target. The script is the authority so CI and the hook cannot disagree.

3. **`.github/PULL_REQUEST_TEMPLATE.md`** — shaped like the PRs this project already writes:
   what changed and why, which task file it closes, the acceptance command and its exit code,
   what was verified on the device versus what was only reasoned about, and what was deliberately
   left out. That last field is the one worth keeping: every wave here has had one.

4. **Issue templates**, two, deliberately small. A bug form that asks for the device, the Android
   version, whether the PC server was reachable, and the relevant `DeskPanel` logcat lines — the
   four things every diagnosis in this repo has started from. A feature form that asks which
   invariant the idea touches, because most ideas for this panel touch one.

5. **Review expectations, in one paragraph.** Reviews land *before* the merge, not after — that
   is how every wave in this repo has run, and PR #12's second review is the example. Say so, so
   a contributor expects the round trip rather than reading it as rejection.

## Acceptance

```bash
printf 'feat: a subject in the right shape\n' | python scripts/check_commit_msg.py /dev/stdin
! printf 'fixed some stuff\n' | python scripts/check_commit_msg.py /dev/stdin
! printf 'feat: Add A Capitalised Subject That Also Runs On Far Too Long For Any Terminal\n' | python scripts/check_commit_msg.py /dev/stdin
test -x .githooks/commit-msg
python scripts/check_links.py CONTRIBUTING.md .github/PULL_REQUEST_TEMPLATE.md
git log --format=%s -30 | python scripts/check_commit_msg.py -
python scripts/check_acceptance.py
```

The sixth line is the one that makes the rest honest: the checker is run against this repo's own
last thirty subjects. A convention the existing history violates is a convention nobody will
follow, and it should fail here rather than in a contributor's first PR.

## Manual check

Read `CONTRIBUTING.md` as someone who has written Android code but has never seen this project.
The question it has to answer is not "where do the braces go" but "why is this file laid out the
way it is, and what will get my PR sent back".

## Notes

- Keep it one file. A contribution guide split across five documents is read by nobody.
- The commit checker rejects shape, never content. Subject line length, a known type, a lowercase
  start, no trailing period, and a blank second line. Anything cleverer will fire on a legitimate
  message and teach contributors to pass `--no-verify`.
- **No attribution trailers.** `git log` here carries one author and the guide should say that
  the project does not use `Co-Authored-By` trailers for tooling.
