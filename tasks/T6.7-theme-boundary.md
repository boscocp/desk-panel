# T6.7 — A theme boundary, so a contributor can restyle without reading the core

Size: L · Prereqs: T3.12, T6.1 · Files: `web/themes/`, `web/js/app.js`, `web/index.html`,
`web/css/style.css`, `docs/THEMING.md`

Requires: a local Firefox for the two browser checks; the phone only for the manual check

## Goal

Someone who wants a different-looking panel should change files in one directory, and nothing
else. No touching the poll loop, the payload contract, the formatters, or Java.

## What is actually coupled today

Colours are already themeable — `style.css` keeps the palette in custom properties precisely so
T6.4's night profile can redefine them without hunting hex literals (T6.1). That is the easy
half, and it is done.

The hard half is **markup**, and it lives in the wrong place. `app.js` builds every element by
hand: `renderRow` decides that a row is a label, a price, a sparkline and a change, in that
order; `renderList` decides that a card is a flat list of rows; `index.html` fixes the six
sections and their ids. A theme that wants the change above the price, or a card as a grid, or
the sparkline as a background wash, cannot express that in CSS — and to change it, a contributor
has to edit the same file that holds `window.onData`.

So the boundary is not missing, it is in the wrong place: it currently separates *colour* from
everything, and it needs to separate *presentation* from *data*.

## Where to put the line

**Core keeps:** `window.onPcState` and `window.onData` (the native bridge — invariant 1 means the
page never fetches), the payload contract, `format.js` in full. Those are the things the Android
and server layers are written against, and a theme that could change them would break the
contract in `tasks/T1.2-mock-fixtures.md`.

**A theme owns:** the markup it produces from a payload, its stylesheet, and its own assets.

A theme is a directory, `web/themes/<name>/`, holding at least `theme.css` and `theme.js`. The
JS exports one function:

```js
export function render(payload, root) { ... }
```

Core does the polling, formatting and state; it calls `render` and does nothing else to the DOM.
`format.js` stays importable by themes, because a theme that reimplemented `formatPrice` would
reintroduce the sub-1 bug the yuan found (T6.5) in every new theme.

## Steps

1. Move today's rendering into `web/themes/neon/` unchanged. It must look pixel-identical
   afterwards — this step is a move, not a redesign, and mixing the two would make a regression
   impossible to attribute.
2. `app.js` keeps `window.onData`/`window.onPcState`, the clock, and the theme handoff. Nothing
   in it may mention a class name or an element id.
3. **Theme selection is runtime config**, not a build: the `theme` key from T3.12, delivered in
   the payload, so a contributor swaps themes by editing a file on the PC. Shipping every theme
   in the APK and choosing at runtime keeps the project's rule that changing what the panel shows
   never needs a rebuild.
4. An unknown or missing theme falls back to `neon` and says so once in the log. A panel that
   renders nothing because of a typo in a config file is the worst failure available here.
5. `docs/THEMING.md`: the payload shape a theme receives, the two functions it must export, what
   it may and may not import, and the offline state contract — a theme **must** honour
   `window.onPcState(false)` by rendering nothing lit, because that is invariant 3 reaching the
   page (ADR 0005) and not a stylistic choice.

## Acceptance

```bash
node --test "web/test/**/*.test.js"
test -f web/themes/neon/theme.js && test -f web/themes/neon/theme.css
```

Core no longer knows about markup:

```bash
! grep -nE "createElement|classList|getElementById|\.className" web/js/app.js
```

Every theme is packaged, so switching one needs no rebuild:

```bash
docker compose -f docker/compose.yml run --rm build ./gradlew assembleDebug
python -c "import zipfile,sys; names=zipfile.ZipFile('out/app-debug.apk').namelist(); sys.exit(0 if any(n.startswith('assets/themes/') for n in names) else 1)"
```

The blackout survived the move, and so did the panel's shape, in both themes:

```bash
python e2e/layout/check_blackout.py
python e2e/layout/check_blackout.py --theme plain
python e2e/layout/check_layout.py
python e2e/layout/check_layout.py --theme plain
```

`check_blackout.py` is new and it is here because **this task moved a safety rule**. The
blackout used to be two class names in the panel's own stylesheet; it is now one attribute on
`<html>`, one rule in core CSS, and a hold in `app.js` that keeps a payload out of a hidden DOM.
Every one of those is invisible in a screenshot and none of them had a command. It drives the
real page through `check_layout.py`'s Marionette plumbing and asserts the whole round trip:
dark on both causes, a payload delivered while dark is *not* drawn, the latest one is drawn on
the way back with its theme switch, the clock stops and restarts, and `#clock` holds a time
before any payload has arrived at all.

Mutation-tested in both directions, because a check nobody has seen fail is not a check:
deleting the hold in `onData` fails it on three lines, and turning `visibility: hidden` into
`visible` in `css/style.css` fails it on two.

## Manual check

- The neon theme after the move is indistinguishable from before it. Compare two screencaps.
- A second, deliberately plain theme renders the same payload legibly — that is the only proof
  the boundary is real rather than a directory rename.
- Setting `theme` to a name that does not exist still gives a working panel.

## Notes

- Keep `mock.js` working against every theme. It is how a theme gets developed in a browser with
  no phone and no server, and a theme that only works with live data cannot be reviewed.
- This is the task most likely to be over-designed. A plugin system with hooks, lifecycles and a
  registry would be worse than one exported function: there is exactly one consumer, and it is
  a page that renders a payload.
- T6.6's scrolling is presentation and belongs on the theme side once this lands, which is why
  T6.6 lists this as a prerequisite — writing the scroll into `app.js` first would only mean
  moving it again.
