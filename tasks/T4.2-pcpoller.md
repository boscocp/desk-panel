# T4.2 — `PcPoller`

Size: M · Prereqs: T4.1 · Files: `PcPoller.java`, `PcState.java`, `MainActivity.java`

Requires: phone (on adb), PC server reachable

## Goal

Know, within a couple of seconds, whether the PC is awake and logged in.

## Steps

1. `PcState.java` — a plain class with **no Android imports**: current state, transition logic,
   and the backoff schedule. Kept Android-free so `./gradlew test` can cover it on the JVM with
   no device (TT.5).
2. `PcPoller.java` — a background thread or `ScheduledExecutorService` hitting
   `http://<pc-ip>:8777/ping` with `HttpURLConnection`. Short connect and read timeouts, around
   1500 ms; a hung socket must not stall the loop.
3. Never touch the network on the UI thread. Marshal results back with
   `runOnUiThread` / a `Handler`.
4. Start polling in `onResume`, stop in `onPause`. A poller surviving the Activity is a leak.
5. Log every transition — and only transitions, not every poll:
   `Log.i("DeskPanel", "state=online")` / `state=offline`.

## Acceptance

The server must be up on the PC and the app installed. **Ordering is not optional**: `am start`
on an already-foregrounded Activity reloads nothing, and a marker emitted by `am start` is wiped
by a `logcat -c` that runs after it. Every block below is `force-stop`, clear, start, sleep,
grep — the shape the backlog-run note argues for.

`UNKNOWN` is a state, so the first probe after a fresh start is a transition either way; that is
what makes these greps observable at all rather than depending on a lucky window.

Online, from a cold start:

```bash
adb shell am force-stop dev.bosco.deskpanel && adb logcat -c \
  && adb shell am start -n dev.bosco.deskpanel/.MainActivity && sleep 15 \
  && adb logcat -d -s DeskPanel | grep -q 'state=online'
```

Stop the server, then — no restart here, the transition is what is being measured:

```bash
adb logcat -c && <stop the server> && sleep 15 \
  && adb logcat -d -s DeskPanel | grep -q 'state=offline'
```

Start it again and re-run the first block. Then the no-spam check — a steady state must not log
at all, because only transitions do:

```bash
adb logcat -c && sleep 30 && test "$(adb logcat -d -s DeskPanel | grep -c 'state=')" -le 1
```

### The runtime half of T4.1

The call to the PC succeeds while a call to any other cleartext address is refused. **This
cannot be observed from the shipping APK**, and an earlier version of this file asked for it as
if it could. `build.gradle.kts` substitutes one placeholder across the generated `res/` tree, so
`pc_host` and the domain pinned in `network_security_config.xml` are the same address by
construction — the app only ever dials the host the pin allows. The marker is reachable only by
building a deliberate divergence, which is a throwaway artefact and never committed:

```bash
# A literal, not the placeholder, so the .env substitution leaves it alone:
# the pin still moves to PC_IP while pc_host stays put.
sed -i 's|>192.168.1.100<|>192.168.15.4<|' android/app/src/main/res/values/config.xml
docker compose -f docker/compose.yml run --rm build ./gradlew assembleRelease
adb install -r out/desk-panel-release.apk
adb shell am force-stop dev.bosco.deskpanel && adb logcat -c \
  && adb shell am start -n dev.bosco.deskpanel/.MainActivity && sleep 12 \
  && adb logcat -d | grep -q 'Cleartext HTTP traffic to .* not permitted'
```

The build prints the divergence itself — `cleartext pinned to <PC_IP>` against a `pc_host` that
differs — so a run that accidentally kept them equal is visible before the grep. Restore, and
prove the restore rather than assuming it:

```bash
sed -i 's|>192.168.15.4<|>192.168.1.100<|' android/app/src/main/res/values/config.xml
docker compose -f docker/compose.yml run --rm build ./gradlew assembleRelease
adb install -r out/desk-panel-release.apk
adb shell am force-stop dev.bosco.deskpanel && adb logcat -c \
  && adb shell am start -n dev.bosco.deskpanel/.MainActivity && sleep 15 \
  && adb logcat -d -s DeskPanel | grep -q 'state=online' \
  && test "$(adb logcat -d | grep -c 'Cleartext HTTP traffic')" -eq 0
```

**Be at the phone for the first install, and use `assembleRelease`.** These are two separate
things and conflating them wasted a session here.

MIUI raises a confirmation dialog on the *device* for an adb install. Unanswered, it fails with
`INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` after about four seconds — quick
enough to look like a policy refusal rather than a dialog nobody answered, and quick enough that
`adb install` looks like it never reached the phone. It succeeds the instant someone taps
*authorise*; later installs in the same session do not prompt again. If no dialog appears at
all, cycle Developer options → "Install via USB", which is what T2.2 needed.

Use `assembleRelease` because the device carries the release key from its first install (T7.1),
and Android will not install a differently-signed APK over it — `INSTALL_FAILED_UPDATE_INCOMPATIBLE`,
whose only way out is an uninstall that throws away the MIUI grants T2.4 spent a session
collecting. That is a signing constraint and has nothing to do with the dialog above. Backing
the good `out/desk-panel-release.apk` up first is worth the one command: this build overwrites it.

## Notes

- Poll every 2s while online. The offline backoff arrives in T5.3 — do not build it here, but
  do put the interval behind `PcState` so T5.3 only changes one place.
- Any failure is offline: timeout, connection refused, non-200, DNS. Do not try to distinguish
  them for the state decision.
