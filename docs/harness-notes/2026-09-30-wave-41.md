# Wave 41 — spectrum bars over the buttons

One request from the chair, in Portuguese, with a screenshot of Winamp's analyser: bars in the
empty space over the buttons, "que seja real ao som tocando atualmente". The owner chose macOS
first. The owner watched it run on the panel ("ficou mt bom!") and then asked for Windows and
CachyOS in the same wave. The owner also asked that the PR **not be merged until they approve
it**, and that the Windows half be checked against Microsoft's official documentation.

## What ran

**A spike first.** A 60-line Swift program created a Core Audio process tap. It got a format
(48 kHz stereo float) and no audio callbacks at all. The system log showed the cause:
`tccd: AUTHREQ_PROMPTING ... kTCCServiceAudioCapture` for Terminal, meaning macOS was asking.
Once the owner allowed it, callbacks arrived with real peaks around 0.58. A second spike showed
the aggregate device needs no speaker in it, so switching outputs cannot break the helper. That
simplification came out of re-running the case that had looked broken.

**The design** is [ADR 0021](../adr/0021-the-spectrum-is-a-stream.md):
- one long-lived `GET /spectrum` of hex frames;
- the FFT in pure Python on the PC, at 1.2 ms a frame;
- capture only while a stream is open;
- off by default.

**Per platform:**
- **macOS:** a Swift helper.
- **Windows:** a C# 5 helper that Windows' own `csc.exe` compiles.
- **Linux:** `parec` on `@DEFAULT_MONITOR@`, with no helper.

**Measured:**
- **macOS**, on the Redmi against the owner's music: `spectrum=open`, and real levels on the
  wire. macOS prompted for `python3` once the server ran the helper.
- **Linux**, in a Debian container with a real PulseAudio: a 1 kHz tone at −6 dB read 227 in bar
  8, where the scale says 229. The same run showed 1.0 fps on a steady tone, which confirmed a
  review finding live (below).
- **Windows**: compiled only.

## What the review found

One fresh-context agent reviewed the first commit read-only, mutated it in a scratch worktree,
and reported one high, two medium and two low findings. All were applied:
- **High: two capture threads and two helpers.** The capture thread asked `_should_run` a second
  time after it had already said stop, so a reconnect just after the linger could leave two
  helpers running. The same race was spotted at the same moment in this session. The fix makes
  the first "stop" final, and a test that turns red without the fix pins it.
- **Medium:** a stale linger timer could close a lingering source. Any non-`OSError` exception
  killed the hub for good.
- **Low:** a sustained note blinked, because identical frames were not resent and the page
  counts a stale frame as silence. The fix resends frames with sound every 200 ms and widens
  the page's freshness to 400 ms. The second low finding was a helper that could never start
  but respawned every 5 s; it now backs off to 60 s.
- **Tests:** six mutations that had stayed green now each turn the suite red. That was measured,
  not assumed.

## The Windows check against the docs

This was the owner's request. Microsoft Learn's pages changed three things:
- `[MTAThread]` became `[STAThread]`. The IAudioClient page says the first use "should be on the
  STA thread. Calls from an MTA thread may result in undefined behavior."
- 10 ms polling became an event-driven shared stream, which Initialize documents as working from
  Windows 10 1703. Both durations are 0, and the event is set before Start. A 100 ms wait is
  the fallback.
- A 2 s poll of the default device became `IMMNotificationClient`. Its callback only sets a flag,
  per the page's rules.

Every vtable was checked against Microsoft's `windows-rs` bindings: IAudioClient,
IAudioCaptureClient, IMMDevice, IMMDeviceEnumerator and IMMNotificationClient, plus every IID
and constant. The reference pages list methods alphabetically, so they cannot confirm slot
order.

Results: `make check` exit 0.

## What is not proven

- **The Windows helper has never run.** It compiles as C# 5 against Microsoft's documented
  interfaces, and that is all that is known. The first run is the owner's, on the Windows PC.
- **CachyOS on PipeWire.** `parec` was measured against PulseAudio in a container, not against
  `pipewire-pulse`.
- **Private mode end to end.** `/spectrum` behind TLS and the key has unit coverage; the desk's
  panel runs open.
- **The indicator.** Whether macOS shows its audio-recording indicator while the tap runs was
  not looked at on screen.

## What it cost

The permission prompt was the one thing no code could do, and it came up twice: once for
Terminal and once for Python. The owner's config holds tokens, so the session asked for the
one-line edit instead of making it. A sabotage run hung on a mutation, because a test's reader
thread was not a daemon. That was fixed in the test.
