# Wave 28 — every input, and the direction the review found pointing the wrong way

**T8.3.** The MIC button mutes every microphone on Linux, the way it started doing on Windows
the day before. macOS cannot, and ADR 0015 now says so instead of a comment.

The wave's finding is not the feature either. It is that a fix for "the button acted on the
wrong device" shipped, green and manually verified on real hardware, **with a direction read
from a device the press never touches** — and that the case where it mattered is the exact case
the task was written for.

## What ran

**T8.3**, on `wave/28-mute-every-mic-linux`, cut with `make wave-start` — which refused nothing
and fast-forwarded four commits, the Windows fixes from the day before, including the row that
became this wave.

`make check` green. The task's three acceptance commands green. 105 tests in
`server/tests/test_actions.py`, 350 in the server suite.

**Verified on this desk**, which has three real capture devices and four `.monitor` sources:
`POST /action/mute-mic` against a server on a spare port moved all three to `Mute: yes` and back,
the monitors never moved, `/ping` kept answering, and the startup line read `mute-mic: pactl`.

## Why this and not the documentation cluster

Wave 27's `Next:` line said T7.4 + T7.5 + T7.6 and was right when it was written — before the
Windows box had ever been used. The first press of MIC there muted the default input while the
owner was talking into a different one, Windows was fixed the same day, and **T8.3 was filed for
the other two platforms**: a row the wave-27 section could not have known about.

Two things made taking it first the obvious call rather than a judgement one. It is the failure
ADR 0015 singles out as worse than having no button at all. And this session is the Linux desk,
with three inputs and four loopbacks plugged in, so the manual check the task asks for could
actually be run — which is the thing the Windows session could not do.

## What the shape of `actions.py` cost

`run_action` ran one argument list per press. The Linux microphone cannot: nothing knows what to
mute until `pactl list short sources` has answered. So `_SEQUENCES` sits beside `_TABLE` for the
ids that are a **press** rather than a command, and the row left in `_TABLE` is the press's first
command — which is also exactly the binary the 501 path and the startup line probe for, so
`candidates`, `describe` and `Unsupported` learned nothing new.

`wpctl` lost the microphone and kept the speakers. It has no verb for "every source", so a
fallback would have put a PipeWire box quietly back to muting the default alone: **the failure
being fixed, reintroduced by the kindness that was meant to help.**

## What the review found

Four, and the first is the wave.

- **The direction was read from `@DEFAULT_SOURCE@`, which the press may never touch.** Two ways
  to fail, both real. A machine whose default source is a *monitor* — a normal thing to set for
  screen recording — has a default that is never in the list of things being muted, so its state
  never moves: the button mutes for ever and no press unmutes. And a machine whose default is
  muted while another input is live — **precisely the mixed state this task exists to end** —
  answers "already muted", so the press computes "unmute" and **opens every microphone in the
  machine**. The direction now comes from the inputs being muted, decided by `state_from_sources`
  — the same function the cross is drawn by, so a press unmutes exactly when the panel would be
  showing one and mutes in every other case, a mix or an unreadable mixer included. The review
  left it as a decision rather than applying it, because it contradicted the ADR paragraph and
  the tests written hours earlier this same wave; taking it was not close, and ADR 0015, step 1
  of the task file and five tests moved with it.
- **`pactl`'s answers are translated.** It binds the `pulseaudio` text domain, so `Mute: yes` is
  `Stumm: ja` on a desktop with language packs, `state_from_readback` reads `unknown`, and the
  press — which at the time refused to act on `unknown` — would have answered **500 on every
  press while muting nothing**. The old Linux press was a locale-independent `toggle` and a
  translated mixer cost only the cross; this was a regression in kind, not degree. Fixed: every
  child runs in `LC_ALL=C`, with the whole environment preserved around it, because a bare
  `env={"LC_ALL": "C"}` strips `PATH` and the session bus address `pactl` needs. Two tests.
- **A `_SEQUENCES` key that drifted from `_TABLE` would fail silently and successfully.** The
  `mute-mic`/`linux` row is a read-only listing, which is safe only because the sequence takes
  over before it is reached; if the two ever key differently, `run_action` runs the listing *as
  the action* — exit 0, nothing muted, HTTP 200. Unreachable today. Closed with a test rather
  than an unreachable branch: a `pactl`/`wpctl` row whose verb only asks a question must have a
  press behind it.
- **A device unplugged mid-press fails a press that otherwise succeeded.** A Bluetooth headset
  dropping between the listing and its own `set-source-mute` aborts the loop with a 500 even
  though every input still present took the mute. Not fixed: "a partial mute is a failure" is
  explicit in the task and the ADR, and the two cases are genuinely hard to tell apart from the
  outside. Recorded here because the message covers both and only one is a real failure.

`make check` green afterwards, and the manual check was re-run on the mixed machine the finding
describes: one input muted by hand, the other two live, and the press **closes all three**
rather than opening them.

## The pattern, which is the same one as last wave

Wave 27's bug was one line between three green layers. This one is one *source of truth* beside
the thing it claims to describe. In both cases every test passed, the manual check passed, and
the property that mattered was never asserted because the author was thinking about the normal
case — three microphones in the same state, a default that is one of them.

The cheap version of the lesson: **when a press acts on a set, the state it reads has to be the
state of that set.** Reading a neighbouring thing that is *usually* the same is how a fix for
"the wrong device" ships with the wrong device still in it.

## What is not proven

- **macOS is unrun and now also unimplementable within the rules.** The default-input limit is
  in ADR 0015; nobody has pressed the button on a Mac at all.
- **The twenty-taps check is still not done**, carried from wave 27 and more interesting than it
  was: a Linux microphone press is ten `pactl` invocations on this desk, not two, so twenty
  presses queue ten times the work behind the poller's single thread. `/ping` was observed
  answering between presses, which is not the same thing.
- **The phone was not touched.** TT.7, TT.8, T2.4 and T7.2 have been waiting since wave 22; the
  cable was not used this session.
- **`invoke`'s `rejected` path still has only unit tests**, because no theme can produce an id
  outside `Actions.ALLOWED`.
- **`check_pulse.py --theme plain` still fails on `main`**, unchanged from wave 27. One line in a
  task file, not a bug.
- `server/config.json` is still mode 0644 and holds `actions` as well as the brapi token. One
  `chmod 600`; T7.3 wants it. Carried from wave 19.
