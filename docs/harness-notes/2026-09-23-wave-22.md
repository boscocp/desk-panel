# Wave 22 — a twenty-line route, and a property of adb

## What ran

T3.6 and T7.2, on `wave/22-the-apk-over-the-wire`, PR #28. The backlog's next two rows, paired
because both are "get a build onto the phone without a cable". They came apart on contact: T3.6
landed whole, T7.2 split into a container half that could be measured on this desk and a phone
half that needs a finger on the device.

**T3.6** — `GET /app` serves the newest `.apk` in `out/` by modification time, with
`Content-Type: application/vnd.android.package-archive` and a `Content-Disposition` filename;
`GET /` is one page with one link to it. A missing `out/` is a 404 whose body is the build
command, in plain text, because the client of this route is a person holding a phone and every
other error in the file is JSON for the panel.

**T7.2** — `docker/compose.yml` gains `extra_hosts: host.docker.internal:host-gateway`, and
`docs/INSTALL-PHONE.md` now says, with the measurements behind it, that adb belongs on the host.
The row is `blocked`, not `done`.

## What the review found

**Seven, all applied, none declined.** Two of them are the wave's own reasoning being wrong
rather than its code being sloppy, and those are the ones worth reading.

1. **`/app` would have handed the phone a debug-signed APK.** The route served the newest
   `.apk` in `out/` by mtime, and the reasoning behind that — "the one to install is whichever
   was built last" — is exactly backwards for this project. `make apk` is `assembleDebug` and
   drops `app-debug.apk` into the same `out/`, so a developer checking a build makes the debug
   APK the newest, and the bookmarked `/app` that `docs/INSTALL-PHONE.md` now advertises then
   serves it. `INSTALL_FAILED_UPDATE_INCOMPATIBLE`; the only way past it is an uninstall; an
   uninstall drops MIUI's autostart and battery grants, which are manual per-device toggles.
   **The cost of this bug is a person standing at the phone re-granting permissions**, and
   `android/app/build.gradle.kts:238` says so in a comment nobody re-read while writing the
   route. The release build wins now, however old it is; newest-by-mtime survives only among
   the rest, for a checkout that has no release build.

2. **The acceptance could only pass on this desk.** Both probe lines assert 200 on `/app`,
   which is true only when `out/` already holds an APK — and `out/` is gitignored, `make clean`
   deletes it, a fresh clone has none, and TT.9's CI (named in this wave's own "next") would
   have had none. `STATUS.md` said "both acceptance commands exit 0", which was true and was
   about the machine. The block now creates a four-byte fixture and removes it, and the removal
   is not tidiness: an APK left in `out/` is a file `/app` will hand to a phone.

   This is the third wave in a row to find a criterion that only passes where it was written —
   wave 19's timezone test, wave 20's server suite red on Windows, and now this. The pattern is
   not carelessness; it is that a criterion is written while looking at the machine that just
   made it pass.

3. **`stat()` and `read_bytes()` were unguarded** where `iterdir()` was guarded. A dangling
   symlink, or a build replacing the APK between the choice and the read, raises out of
   `route()` into the handler's blanket `except` — so the phone gets a JSON 500 from a route
   whose every other answer is plain text. Both are guarded; a file that vanishes is the 404
   that says "build first", which is the accurate answer as well as the useful one.

4. **`probe.py` showed half of why it failed.** `detail` was a single slot, so with
   `--expect-header` and `--expect-json-keys` both failing, the second overwrote the first.
   A list now. And a header expectation against a host that is down said nothing at all.

5. **Five of the new tests did not run when the file was run directly.** The
   `if __name__ == "__main__"` guard sat above the two new classes in `test_http.py`:
   `python server/tests/test_http.py` ran 8 and exited 0 while `unittest discover` ran 13. In a
   wave whose whole theme is "an assertion that cannot fail", that is the joke writing itself.

6. **A filename went into a header unescaped.** `f'attachment; filename="{apk.name}"'`, and
   `send_header` validates nothing, so a file in `out/` named with a quote or a CRLF breaks or
   injects a response header. Selection is by what is in the directory, so it is whatever landed
   there. Anything not `[A-Za-z0-9._-]+` is served as `app.apk` now.

7. **The `extra_hosts` comment overstated the fix.** It implied `make connected` works once the
   name resolves. It does not: the target runs a plain `adb start-server`, which binds
   `127.0.0.1:5037`, so the container's connection is refused anyway — which is this wave's own
   finding, written two files away. Necessary, not sufficient, and the comment says which.

One more was found by self-review before the reviewer reached it: `newest_apk` matched on the
suffix alone, so a **directory** named `x.apk` was chosen and then read — and `out/` already
contains a directory. That one came from listing what is actually in `out/` instead of reading
the function.

## Where the rework went

Nothing in this wave was reworked. What it cost instead was three things the task file assumed
existed and that did not — each one cheap on its own, and each one a line of the acceptance that
could not have run as written:

1. **`route()` returned three values and needed four.** `Content-Disposition` is not decoration:
   without it the browser saves the download as `app`, with no extension, and Android will not
   open it. A header is the router's business — the handler is dumb by rule (`server/CLAUDE.md`)
   — so the contract changed and nine unpackings in two test files moved with it. This is
   wave 17's lesson in a smaller key: grep for the other readers before redefining what a
   function returns. Here the grep was two minutes because every other reader was a test.
2. **`HEAD` did not exist.** `BaseHTTPRequestHandler` answers 501 to any method without a `do_`
   method, so `--method HEAD` in the acceptance could never have passed. `do_HEAD` routes as GET
   and drops the body on the way out, which is what HEAD means and what keeps `Content-Length`
   describing the body a GET would have returned — the only thing that makes asserting a
   content-type over HEAD worth doing rather than moving two megabytes to read one header.
3. **The assertion the acceptance rests on had to be built.** `probe.py` read headers off the
   wire and discarded them. `--expect-header NAME=VALUE` is new.

That third one is the note worth keeping. T3.6's own task file already said why:

> `curl -sI | grep -i content-type` succeeded whenever *any* content-type header came back,
> which is always. The value is the assertion.

So the task was written *knowing* the old criterion could not fail, and the new one arrived
untested. `mismatched_headers` is pure and now has nine tests, including the one that decides:
**a prefix does not match**, so `application/vnd.android.package` is rejected against
`application/vnd.android.package-archive`. A substring test would have passed for the wrong
server. This repository has shipped four criteria that could not fail (T0.5's count, then T6.6,
T6.4, T5.5); testing the mechanism is the cheapest place to stop the fifth.

## What T7.2 actually answered

The task asked whether `adb pair` works from inside the build container. That turned out to be
the wrong question, and the right one was answered by three measurements rather than by reading:

- The image **does** ship adb — `platform-tools`, 1.0.41 / 37.0.1 — so "can it" was never it.
- **`host.docker.internal` does not resolve on Docker Engine.** It is a Docker Desktop
  invention. `getent hosts` returned nothing; with `extra_hosts: …:host-gateway` it returns
  `172.17.0.1`. This was already a live bug: `make connected` (TT.7) passes
  `-PadbHost=host.docker.internal`, and on this machine that name did not exist. The symptom
  would have been "Gradle cannot find a device", which names neither the cause nor the file.
- **adb cannot listen on a single interface.** `adb -a -L tcp:172.17.0.1:5037 nodaemon server`
  exits with `could not install *smartsocket* listener: listening on specified hostname
  currently unsupported`. The only server a container can reach is `adb -a`, which binds
  `0.0.0.0:5037` and hands every host on the LAN unauthenticated control of the phone.

With such a server running, a container does attach to it — so the route exists. It costs a
LAN-wide adb listener on a desk whose entire security model is "the network is the boundary"
(T3.6's own note says so about serving a binary). The task's step 4 fallback — run adb on the
host — is therefore the recommendation, and it is written into `docs/INSTALL-PHONE.md` and into
TT.7's notes, where it changes a design that has not been built yet.

## What this wave found in somebody else's file

`python scripts/after_update.py --self-test` exits 1 on this Linux box, two cases red, and it is
red on `main` — wave 22 did not cause it. `python_for` uses `Path`, which is `PosixPath` here, so
a Windows path is one opaque name and the function returns it unchanged. On Windows that is
correct; on Linux the test cannot pass.

The interesting part is the symmetry. **Wave 20 found that the server suite had been red on
Windows since wave 18, because both waves were judged on Linux. Wave 20's own script is red on
Linux, because it was judged on Windows.** Two waves apart, the same loop, the same blind spot
pointing the other way — and in both cases the thing that would have caught it is that nothing
in `make check` runs the check on both platforms. `--self-test` is not in `make check` at all.

It is not fixed here. It belongs to another session's task and the fix is
`PureWindowsPath`, which `verify_login_scope.py` already learned in T3.8. What this wave owes it
is the record, and a row in `STATUS.md` that does not exist yet.

## What is not proven

- **The phone is not on adb.** It answered `unauthorized` over USB at the start of this wave and
  had dropped off entirely by the end. T7.2's acceptance, and T2.4, TT.7 and TT.8, all need it
  back; the first step is the RSA prompt on the device, which nobody can tap from a checkout.
- **T3.6's manual check is unperformed.** Nothing has downloaded `/app` from the phone's browser
  and installed it. The bytes, the status, the type and the filename are asserted by command;
  that MIUI offers to install them is not.
- **`extra_hosts` is verified on Docker Engine and unverified on Docker Desktop**, where the
  name already exists and the line should be inert. "Should be" is the honest word, and Windows
  is the primary platform.
- **The container's adb was seen attaching to a host adb server with no device attached.** The
  connection is what was in question and the connection is proved. A real device over that
  socket is not.
- **The `-a` server was bound for about ten seconds and then killed**, and `ss -ltn` confirms
  5037 is back to `127.0.0.1` only. That is the state this desk is in; nothing in the repo can
  assert it.
- `server/config.json` is still mode 0644 with the brapi token in it. Carried from wave 19
  through 21 and now 22. One `chmod 600`; T7.3 wants it.

## Cost

Not measured in tokens. Two restarts of the panel's own server, because `probe.py --serve`
refuses to probe a listener it did not start and T3.9's user unit owns 8777 on this box — so
the panel slept and woke twice, and a restart is a logout as far as the phone is concerned.
Two container runs, about a minute each, to settle the Docker half.
