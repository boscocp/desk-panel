# Wave 51 — A failing ping says where the phone is

The owner reported that the panel had not come on, and suspected the Windows server, which had
not been updated. They asked for a fix, review and merge if it was a bug. It was not a bug in the
code; this wave is the diagnostic it took an adb session to supply.

## The investigation

The phone was on adb, the app resumed, and every cycle read:

```
ping=err hosts=192.168.3.97:SocketTimeoutException,192.168.15.3:SocketTimeoutException
```

The Mac's server was listening on `:8777` and answered `200` locally. The phone was on
`192.168.4.7/24` with gateway `192.168.4.1`. The repository records it on `192.168.3.100`, the
Mac's subnet. Its DHCP record put the change at 06:53 that morning, after a power cut overnight.
The gateway's MAC was `c4:d7:38:ec:15:1c`, which the Mac's ARP table also has at
`192.168.3.3`: the HUAWEI Mesh 3 satellite. The satellite had come back as a router of its own,
under the same Wi-Fi name. From behind it the phone reached `192.168.3.1` and `192.168.3.3`, but
not the Mac and not `8.8.8.8`.

Unplugging the satellite moved the phone to `192.168.3.107` (the main unit) at 14:27, and
`ping=ok host=192.168.15.3` followed within seconds: the Windows PC was up. Plugged back in, the
satellite behaved. The owner also moved the phone's DHCP reservation to its device MAC, which
had stopped matching the random one it was bound to.

The README has described this symptom since PR #80 (2026-10-15). Its step 3 was "compare the
phone's address with the PC's", which needs adb or a hand on the phone.

## What ran

**T4.13**:

- `LinkSummary.describe(addresses, gateway)`, plain Java, 4 JVM tests:
  `self=<ip>/<prefix>[,...] gw=<ip>`, IPv4 only, `none` for a missing half.
- `PcPoller` appends it to `ping=err` lines only, through a `Link` interface. A throw logs
  `self=unknown gw=unknown`.
- `PanelService.describeLink` reads the Wi-Fi network's `LinkProperties`, with the default
  network as the fallback. `ACCESS_NETWORK_STATE` added.
- `docs/TESTING.md` and the README's troubleshooting use the new tokens. The README gains the
  mesh-satellite case.

**Measured on the Redmi**, final build: `ping=ok host=192.168.15.3` with no `self=`, and with
Wi-Fi switched off for 30 s, `ping=err hosts=192.168.15.3:ConnectException,192.168.3.97:ConnectException self=none gw=none`.
Wi-Fi back on, `ping=ok` again at 14:43:02. `./gradlew test`: 160 tests, none failing.

## What the review found

One fresh-context review pass over the diff:

| Severity | Finding | What happened |
|---|---|---|
| Medium | `getActiveNetwork()` is the default network. A Wi-Fi with no internet loses the default to mobile data, so the incident would have logged the carrier's address, not `192.168.4.7`. | Fixed: the Wi-Fi network is read, the default only when there is no Wi-Fi. |
| Low | The device acceptance regex failed on two IPv4 addresses, and the healthy check failed with the PC's display off (`ping=idle`). | Fixed both. |
| Low | `self=unknown` was one token, where every doc promises two. | Now `self=unknown gw=unknown`, documented. |
| Low | An `Error` from `describe()` would skip that cycle's delivery. | Declined: `poll()`'s catch keeps the loop alive, and an `Error` from a binder read is not a state worth designing around. |
| Low | Depended on `LinkAddress.toString()`; a point-to-point route's `0.0.0.0` would read as a gateway. | Fixed: built from `getAddress()` and `getPrefixLength()`, `0.0.0.0` skipped. |
| Nit | `Link` was inserted between `Listener`'s Javadoc and `Listener`. | Moved below it. |

No existing grep was broken. The reviewer checked every `ping=` consumer in tasks, e2e, scripts
and docs.

## What is not proven

- **A failing line with an address was not seen on the device.** It needs Wi-Fi up and every PC
  down, and the Windows PC was up all session. The format is covered on the JVM, and the
  no-network path ran on the device.
- The Wi-Fi-over-default choice was reasoned from the API, not measured: the phone showed no
  cellular network when Wi-Fi was off.
- **`SYSTEM_ALERT_WINDOW` was `ignore` again** at 14:35, before this wave's install, with
  `rejectTime` four minutes earlier. That is wave 50's open question, a third time. It was set
  back to `allow` after the install.
