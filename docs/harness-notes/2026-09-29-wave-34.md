# Wave 34 — the first Mac

Every macOS claim in this repository had been reasoned about, written to a documented shape and
tested from fixtures somebody typed. On 2026-09-29 the repository was cloned onto a MacBook Pro
(macOS 26.5, Apple Silicon) with the instruction "set the repo up to run here and do the Mac
validations that were left pending". This is what running them found.

## What ran

On `wave/34-macos-validation`, cut with `make wave-start`.

- **Setting it up.** `make check` failed in two places, neither of them in the code. There was no
  `python`, because Homebrew installs `python3` only and the Makefile and CI compare their command
  strings literally, so the fix is the `PATH` (`docs/REQUIREMENTS.md`) and not the Makefile. And
  `test-android` died because AAPT2 for Linux is x86-64 only and the image had resolved to arm64.
  `docker/compose.yml` now pins `platform: linux/amd64`, which is a no-op on every x86 host.
- **T3.10.** `server/dev.bosco.deskpanel.plist.in` and `server/install_agent.sh` are new. The
  STATUS row had said "Plist and docs ship anyway", and neither file existed. The shape block exits
  0, `verify_login_scope.py` exits 0, and the agent serves `/ping` and `POST /action/*`.
- **T8.3 / T8.2 on macOS.** Both presses, directly and over HTTP from the agent. The input went
  63 → 0 → 63; the remembered-level path had never executed anywhere.
- **T3.13.** `after_update.py` has a Darwin branch. It passes on this Mac, including a pid-verified
  restart through `launchctl kickstart -k`.

`make check` is green on macOS: 366 server tests, web, the Android JVM suite in the amd64 image,
every guard and every self-test.

## Where the rework went

Three defects, and no fixture could have found any of them, because each fixture was written by
the same understanding that wrote the code:

- `--` inside the template's XML comment. `plutil -lint` accepts it and `plistlib` rejects it,
  so a working agent was reported *unknown*. The fail-closed rule did its job, on this
  repository's own file.
- `parse_launchctl_print` read the nested `jetsam coalition` block's `type =` and FAILed a loaded
  agent. The loaded and absent fixtures are real captures now, and the old parser fails four
  self-test cases against them.
- **Re-installing over a running agent raced launchd.** `bootout` returns before the label is
  released, and the owner's first re-run hit `Bootstrap failed: 5` with the old job already gone:
  no server at all. Every run in this session had won the race by luck. The installer now waits
  for the label to vanish and retries once; three back-to-back re-installs exit 0.
- The firewall allows by binary, and a framework Python listens as `Python.app`, not as the
  `python3` in `ProgramArguments`. The first fix asked too early and named the wrong one anyway.

## What the review found

One fresh-context reviewer, with mutations run in a throwaway worktree. Five findings, and all
five were applied:

- **After an update, the script read the plist on disk rather than the job launchd had loaded.**
  After `install_agent.sh --no-start --config B`, it would check B while `kickstart` restarted A.
  It reads `launchctl print`'s `arguments` block now.
- **The brace-counting parser broke on an argument ending in `{` or equal to `}`.** The second
  case brought `type='jetsam'` straight back. Blocks now open only on `name = {` and close at the
  opener's indentation, and both cases are tests.
- **The absent message said "Bad request."**, which was the first line of the real capture.
- **Dropping `-k` from the kickstart left every test green**, and the step would have reported a
  restart that never happened. A self-test now pins `-k`, and the step fails if the pid did not
  change. **Linux has the same gap** (`systemctl --user restart` is not pinned) and it is
  recorded, not fixed.
- **`--no-start` named the previous install's listener.** It no longer asks.

It also flagged an unsourced claim, and it was right: the plist comment said an unset
`LimitLoadToSessionType` "also loads in LoginWindow", and `launchd.plist(5)` documents no
default. The comment now says that, and says the key is written out for that reason.

## What is not proven

- **Nothing answering at the login window.** T3.10's behaviour block needs a logout and a second
  machine to SSH from. The row stays `blocked`.
- **The LAN path.** The Application Firewall is on here and `/ping` answers on `127.0.0.1` but
  not on the LAN address until `Python.app` is allowed. That is a manual grant nobody has made.
- **The other two inputs.** The mic press moved the default input. The USB DAC's line-in and
  Teams' virtual device were not measured, because nothing within the rules can read them.
- The daemon fixture is still hand-written; capturing it means installing a LaunchDaemon.
- The agent was installed against a scratchpad copy of the example config, because the session's
  permissions forbid touching `server/config.toml`. The owner re-runs the installer with the real one.
