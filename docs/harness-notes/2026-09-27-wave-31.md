# Wave 31 — the payload is described once, and three layers are held to it

**T10.1.** `DataPayload.merge` rebuilds the payload key by key, so a key added on the PC and not
there never reaches the phone — silently, with a correct server and a correct page. It shipped
twice: `night` in T6.4 and `actions` in T8.2, the second time with a comment in the file warning
about the first.

It is not silent any more.

## What ran

**T10.1**, on `wave/31-one-payload-description`, cut with `make wave-start`.

`server/tests/fixtures/payload.json` is generated by `server/tests/test_payload_contract.py` from
`App`'s own assembly, with every provider replaced, and two other suites read it:

- `DataPayloadTest` asserts `merge` preserves **every top-level key** of the `/quotes` body plus
  `weather` — a loop over the file, not a list somebody remembered.
- `web/test/payload_contract.test.js` loads `mock.js` as the browser it expects and asserts it
  feeds the page the same key set, plus the two the phone folds in (`weather`, `battery`).

`server/tests/fixtures/action_ids.json` does the same for the action list that lives in Python,
Java and JavaScript at once.

`make check` green: 359 server tests, 102 web tests, the Android suite.

## The fourth copy is gone

`DataPayloadTest` carried its own `QUOTES` literal — a hand-typed payload that could not know
when the server changed. It is `Contract.quotes()` now, and the variants that used to be built by
splicing text into that literal (`QUOTES.replace("\"stale\":false", …)`) are built through
`org.json` instead.

That change is worth its own line, because it was nearly a trap. A generated file is free to
change its spacing, and every one of those `.replace` calls would have quietly become a no-op
that still passed — the same shape of failure the wave is about, introduced by fixing it.

## Three mutations, because an assertion nobody has seen fail is a decoration

- `payload.put("language", …)` deleted from `merge` → the Android suite fails, naming the key and
  telling you where to add it.
- `actions: ACTIONS` deleted from `mock.js` → the web suite fails saying the PC sends it and the
  mock does not, so a browser-only contributor would build against a panel missing it.
- `payload["actions"]` renamed in `App.quotes()` → the server suite fails with the regeneration
  command in the message.

Each was backed out from a `cp` copy taken first, never with `git checkout --` — the rule this
repository learned the expensive way in wave 27.

## The generator had a race and it was worth removing

The first cut called `warm_history()` and then asked for the payload twice, hoping the background
thread had landed. `warm_history` starts a thread per market **on purpose** — a sparkline must
never make a payload wait — so a fixture generated against it is one that is sometimes written
without its histories, and the difference would be invisible in a diff full of numbers.

The generator primes each history cache synchronously through the app's own producer instead.
Same code path, no thread, same bytes every run — which the test asserts by running three times
and comparing to the committed file.

## What is not proven

- **Nothing checks the fixture was regenerated for the right reason.** The server test goes red
  when the committed file has drifted; a contributor who regenerates without reading the diff
  still ships whatever they changed. Every golden file makes that bargain.
- **The e2e path is untouched.** Three unit suites now agree about a file. The device still only
  proves itself by being installed, which is what caught the `actions` bug in the first place.
- **`withBattery` has no contract assertion of its own**, only the key's presence in the web test
  and the existing battery tests on the Java side.

## Cost

One prompt. The wave was the record's own recommendation, and the only judgement call in it was
correcting one line of the task file's acceptance — the Android test reads the description
through a helper, because three test classes need it and a copy of the reader in each would be
the duplication the task exists to remove.
