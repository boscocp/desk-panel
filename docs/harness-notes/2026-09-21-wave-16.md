## What ran

T6.4 and TT.10, on `wave/16-night-profile-and-login-scope-tests`, merged as
[PR #21](https://github.com/boscocp/desk-panel/pull/21): +2372 / −50.

## What the review found

`/code-review 21 high`, four findings, **four applied, none declined**.

The one worth the line: `NightWindow` accepted `22.5` and truncated it to 22:00 where `isNight`
rejects it. `night_start = 22.5` is legal TOML, so a fractional bound would have dimmed the
backlight behind a page that kept its glow — each half correct on its own, which is the most
confusing way this feature could have failed. It was the only input where the two readers could
disagree, and the javadoc directly above it claimed that parity was the point of accepting bare
hours at all.

The other three: a config path that bypassed `config_search_paths` and would have died with a
traceback on a machine set up the documented way; a browser check that hard-failed a theme
answering an overflow without motion, which the theme contract allows; and a comment claiming
three custom properties where the block redefines two — the third being the alarm glow the same
block says must never be dimmed.

**The review also read a tree that moved under it.** It re-verified against the current state
and said so, and its top finding had already been fixed in the working tree by the time it
reported. That is a cost of running the review against a live branch and is worth knowing
before doing it again.

## Where the rework went

Three re-entries, and only the first was a defect in the product.

1. **`DataPayload.merge` never copied `night`.** The payload is rebuilt key by key, so a key
   nobody names there never reaches the phone. Correct server, correct page, correct predicate
   on both sides — and a panel that stayed bright all evening with nothing in logcat. Only the
   device acceptance could find it. *What would have prevented it:* the task file's `Files:`
   line did not name `DataPayload.java`, and nothing in the repo says "a new payload key is
   three edits". It says so now, in T6.4's notes and in `DataPayloadTest`.
2. **The acceptance in the task file could not pass.** `adb logcat -c && sleep 90 && grep -q
   night=on` waits for a line a correct app is right not to write, because every marker here
   fires on a transition. An implementation that *did* pass it would be the one breaking the
   contract. *What would have prevented it:* `scripts/check_acceptance.py` checks that an
   acceptance is a command, not that the command can distinguish a working implementation from
   a broken one. Nothing can check that automatically; writing the acceptance *after* knowing
   the marker contract would have.
3. **The device scenario took three attempts**, and the first two passed for the wrong reason.
   A restart is a gap in the server's answers, and a gap the probe ladder notices is a logout
   as far as the phone is concerned — so `night=off` was logged by the PC leaving, not by the
   window. The log said so plainly two lines apart, and the check was not reading the two lines
   together. The third version restarts nothing: the window is served once before it opens and
   the clock walks into it and out of it. *What would have prevented it:* asking "what else
   could produce this line?" before trusting a green marker assertion. There is now a guard
   that rejects either marker if a `state=offline` precedes it in the buffer.

## What is not proven

- **The 0.15f backlight has never been judged by eye in a dark room.** The marker says the
  profile engaged and the browser check says the glow dropped; whether the panel is legible at
  50cm at 03:00, and whether halved glow reads as *dim* rather than as *broken*, is outstanding.
- **The scroll does not run at night**, so a card with hidden rows keeps them until 07:00. That
  is the intended trade and nobody has lived with it.
- Verified by command: `make check`; `node --test` under five timezones; `--self-test` 97/97;
  the five browser checks on both themes; `e2e/check_night_marker.py` on the phone against the
  final build.
