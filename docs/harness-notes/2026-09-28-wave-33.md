# Wave 33 — the sweep, before the thing that cannot be undone

Making a repository public is the one action in this project with no undo. T7.3 step 1 checked
for it by grepping the log for four words. A word list only finds a secret that happens to sit
near a word somebody thought of, and it runs once, by hand, for ever.

## What ran

**T7.10**, on `wave/33-pre-public-sweep`, cut with `make wave-start`.

- `scripts/check_secrets.py` — eleven credential shapes plus two rules that are not about
  credentials at all: a LAN address that is not the agreed placeholder, and anything tracked
  that `.gitignore` excludes. Two halves, `--history` walks every blob in the pack.
- `scripts/secrets-allowlist.toml` — thirteen entries, a reason on each, enforced.
- `docs/PRE-PUBLIC-SWEEP.md` — what was found, what was changed, what is published on purpose.
- `Makefile` (`lint-secrets`, in `check`) and `.github/workflows/lint.yml`, where the history
  half is its own job.

Acceptance, all eight lines, exit 0. `make check` green: 362 server tests, the web suite, the
Android JVM suite, every guard, ten self-tests (this wave's is the tenth).

**The result: no credential in the 336 tracked files, and none in any of the 1,080 blobs in
the history.**

## Making it fail first

A secret scanner that has never found anything is indistinguishable from one that cannot. Two
fake credentials — an AWS example key and a `ghp_` string that opens nothing — were committed to
a throwaway branch and **deleted in a following commit**. The history half found both, named the
blob, and exited 3. The branch was deleted and the sweep went green.

That sequence is the whole argument for the history half: `git rm` removes nothing from a clone,
and a sweep that only reads the working tree would have called that branch clean.

The tree half was made to fail too, by running it before the allowlist existed: eighteen
findings, every one of them noise, which is how the entropy rule got its three conditions.

## The green tick that would have lied

The obvious wiring was one more step in the existing `guards` job. That job checks out with
`fetch-depth: 30` — correct for the commit-message convention it also runs — and
`git rev-list --objects --all` over a shallow clone walks **what was fetched**. The history
sweep would have reported "nothing found" about thirty commits under a label saying it had read
the history, and it would have said it in green on every push.

It is a separate job with `fetch-depth: 0`, and the comment in the workflow says why. This is
the same failure shape as waves 30–32, arriving in the wiring rather than in the check.

## What the review found

Ten findings, all ten applied. CI had already gone red on the first one before the review
reported it, which is the most useful thing that happened in this wave.

**The guard failed on its own file, and the local run could not see it.** `check_secrets.py`
carries a table of strings shaped like credentials — that is what its self-test feeds its own
rules — so the scanner found fifteen things in it. It passed on this desk because the tree half
reads `git ls-files`, and the file was **untracked** when `make check` was run. The scan was
right (a clone does not get an untracked file) and the conclusion drawn from it was wrong, and
the fix is a habit: *run it after `git add`, not before*.

The review's suggested fix was an allowlist entry for the path. That would work and it is the
wrong shape: it blinds the sweep to a real key pasted into the one file nobody would think to
look in. The samples are assembled from parts instead (`_sample`), each split falling inside the
part of the pattern that cannot be spelled around — so the scanner stays live over its own
source. Two of them needed splitting twice: a GitHub token's body is itself a 36-character
high-entropy run, so `random-blob` caught what `github-token` no longer did.

**The allowlist tripped the guard on its own prose.** Two reasons quoted the address they were
allowing. The file is scanned like any other, `*.md` does not cover a `.toml`, and an entry
whose reason contains its own finding re-breaks the build every time somebody writes one. Both
reasons are reworded and the file says why no reason quotes its string.

**The headline number was wrong by 80%.** `rev-list --objects --all` names trees as well as
blobs, and the success line counted every named object: "1,970 blobs" for a history with 1,080
of them. That figure had already been copied into the sweep document, the STATUS row and this
note as the proof of coverage. The count now comes from what `cat-file` called a blob.

**Identical blobs collapsed to one path.** `rev-list` emits a sha once per path it has ever had
and the map kept the last one, so a secret committed at `server/config.toml` and later copied
elsewhere would be reported under the wrong file — and a path-scoped allowlist entry naming the
real one would silently fail to match.

**`stale()` would have reddened a correct `where = "history"` entry** at exactly the moment it
started to matter: it exempted `history = true` and not `where = "history"`, so renaming or
deleting a file whose *history* is allowed would fail the tree half.

Three smaller ones: the docstring promised a combined report that no invocation produces (there
is no combined mode — CI runs the two halves as two jobs); stale entries printed as unlabelled
lines under the exit code documented as "a finding in the tree", which a stale entry is not; and
`ruff` caught an f-string with no placeholder, which is the `lint` job and not `make check`.

**In CI the tree half ran twice** — `make lint-secrets` in `guards` and the same scan again in
`secrets`. The second job is `--history` only now.

And the sweep document had three wrong counts and one bullet that was not a check at all:
`TODO`/`FIXME` was a grep run by hand, listed under "each of these is a command that will keep
saying so". It is now marked as an observation with a date on it, which is what it is.

## What is not proven

- **A scanner reads shapes.** A password that looks like a word passes straight through, and the
  only defence against that is the rule this project already follows: secrets live in gitignored
  files on the PC and never in the repository.
- **`gradle-wrapper.jar` was not read.** It is not text. It is Gradle's own vendored wrapper,
  pinned by the checksum beside it, and the scanner skips every binary blob by design.
- **The entropy floor is tuned against this repository, not validated.** 4.0 bits per character
  with a digit and both cases was chosen by running the rule over 336 files and reading every
  hit. A key that is all lowercase and all letters would not trip it.
- **The allowlist's `path` uses `fnmatch`, where `*` crosses `/`.** One `*.md` entry therefore
  covers four directories. That is what was wanted here and it is a wider brush than a shell
  glob reader will expect; the entry says so.
- **Nothing proves the sweep is re-run before the flip.** It is in `make check` and in CI, so it
  cannot go stale silently — but T7.3 and T7.7 are prose steps performed by a person, and the
  record only shows the sweep was true on 2026-09-28.
- **The author's email is in all 164 commits** and publishing the repository publishes it. That
  is recorded, not fixed: fixing it means rewriting every commit.
- Carried unchanged: `server/config.json` is still mode 0644 with the brapi token in it — the
  sweep does confirm it has never been committed, which is the part that would have been
  permanent — the Windows installer's TOML branch has still never been run, and
  `WINDOWS-NEXT-SESSION.md` ships unless T3.8 clears first.

## Where the rework went

One place, and it was the review-shaped kind found by running the thing: the history half
decorated each finding's path with the blob sha **before** sieving it against the allowlist, so
every path-based entry matched nothing and the first `--history` run reported thirty-six allowed
digests as findings. It looked like a scary result and was a string-formatting order. Sieve on
the bare path, decorate for the report.
