# Wave 20 — a pull is not a deploy

Unplanned. It began as a question from the chair — *do I have to update the server that starts
with Windows?* — whose short answer is no, and whose real answer took the evening.

## What ran

**T3.13**, `scripts/after_update.py` plus `docs/UPDATING.md`: one command to run after a pull.
**TT.11**, a skip in `test_unit_rendering` for a shell that cannot run it — found by T3.13 on a
clean `main`, not planned at all.

The failure that started it: the phone had a fresh APK with the moon (T6.13) and the chance of
rain (T6.15), and both cards were empty. Every check this repo owns said the machine was fine.
`/ping` answered. The config was valid. The tests were green. The APK was current. `probe.py`
would have exited 0.

The Scheduled Task had started at 00:31:18. The pull rewrote `server.py` at 00:32. The process
serving the phone was **one minute older than the code it was serving**, and nothing had any
reason to say so — the launcher's action points into the checkout, so a pull updates the files
and never the process.

What the diagnosis cost, in order:

1. Reading the task's action and the process start time. Cheap, and it settled it.
2. A wrong turn worth recording: `Get-ScheduledTaskInfo` reports `LastRunTime` in **UTC** while
   `Get-Date` is local, so the task looked three hours in the future on a box whose RTC is UTC
   for unrelated dual-boot reasons. Two clocks disagreeing is not a clue; it was noise.
3. The restart itself took the server down. `Stop-ScheduledTask` then `Start-ScheduledTask`
   back to back hit `WinError 10048` — the new process could not bind, and the survivor was the
   one that had just been told to die. That is `allow_reuse_address = False` behaving exactly as
   designed on Windows, and it means the obvious two cmdlets are the wrong way to restart this.

So the script watches the socket between the two, and the check it exists for is not liveness:
`/weather` is compared against the key set the tree's **own** `normalise()` produces, imported
rather than hardcoded. A field added to the payload later starts being required with nobody
editing the script.

## What the review found

Nine: three found by running the thing, six by the review, and all of them real.

The three from running it:

- **The test suite gated the restart, backwards.** The first cut refused to restart if anything
  failed, which reads as prudence. It is not: the new code is already on disk and the next login
  loads it regardless. The pull deployed it; the restart only decides whether the phone waits
  until tomorrow. Refusing leaves the panel on stale code *and* the tree broken — strictly worse
  than one of the two. Now only a broken config or a missing launcher gates it, because those
  are the two things that stop the server coming back up at all.
- **`python_for` corrupted the paths it was meant to leave alone**, caught by its own self-test:
  it round-tripped through `Path`, so `/usr/bin/python3` came back with Windows separators. It
  returns the argument untouched now.
- **`step_rebuild` took a `head` it never used** and re-resolved `HEAD` itself, so the verdict
  could be about a different commit than the one the report named. Flagged by the editor's own
  diagnostics, not by a test, which is worth noting: nothing in the acceptance would have caught
  a dead parameter.

And the six from the review, of which the first is the one that matters:

- **The Linux branch was unreachable code.** `config_path` was only ever set in the Windows
  branch, so Linux got a launcher, no config, no port, and the restart guard was never true.
  `restart_linux`, `step_payload` and `step_login_scope` could not run, while this note's own
  task file and `docs/UPDATING.md` both described them running. Two documents and a test suite
  agreed with each other about behaviour that did not exist — which is the argument for a
  reviewer that reads the code rather than the claims.
- **A cold cache read as stale code.** The payload check runs right after the restart, when the
  cache is empty by construction; a failed first fetch drops to a five-key fallback and the
  script called that "older code". The worst kind of wrong answer: confident, about the exact
  thing it was built to detect.
- **An `apk` failure pinned its own marker.** FAIL means exit 1, exit 1 means the marker does not
  advance, so no rebuild could ever clear it. The sibling deadlock had been fixed an hour
  earlier and this one was left standing; `--rebuilt` closes it.
- **A refused `Stop` was blamed on "something else owns it"**, with the real error discarded.
- **`--dry-run` said "all clear" and exited 0** on the very failure this wave is about.
- **A red web suite reported nothing about why.**

## What is not proven

- **The Linux branch has been simulated, not run.** After the review found it unreachable, it
  was exercised with `sys.platform` patched, a fake unit file and the three end steps stubbed:
  that proves the path is *reached* — `config`, `restart`, `payload`, `login scope` all report
  instead of stopping at "no port to probe" — and proves nothing about `systemctl --user
  restart` itself, which has never executed. The CachyOS box is where that gets settled. The
  macOS branch does not exist and reports `unknown` by design (T3.10 is `blocked`).
- **`install_user_unit.sh`'s escaping is now unverified on this desk**, because TT.11 skips the
  test here. It is verified on the CachyOS box — which is also the only machine the installer
  runs on, so the coverage sits where the code does.
- **The two cards were confirmed by eye, not by command.** `/weather` carrying `moon` and
  `precipProb` is asserted; that the phone *draws* them was checked from the chair.
- **The APK proxy is cold.** `.after-update-state.json` was written by this wave's first clean
  run, so the first report said `unknown` instead of naming files. It answers from the second
  run onward, and it is a proxy for what is installed on the phone — which the repo cannot know.

## Cost

One evening, most of it in the wrong place. The diagnosis was twenty minutes; **three of the
four hypotheses about `sed` were wrong**, each because a different quoting layer mangled the
evidence — including the agent's own shell, which collapses a doubled backslash in the very
commands written to investigate backslash handling. Reading bytes out of the file with `od -c`
was the only thing that settled it.

The transferable lesson is not about `sed`. When the bug is about escaping, every layer between
you and the evidence is a suspect, and the shell you are debugging *from* is a layer.

The second finding is about this loop rather than about code: **nothing in the harness runs the
server suite on the primary host.** `make check` had been red on Windows for two waves, both
judged on Linux. `after_update.py` now runs it as a side effect of its own job, which is the
only reason anybody noticed.
