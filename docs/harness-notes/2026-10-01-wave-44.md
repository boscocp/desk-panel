# Wave 44 — A busy PC is not a logout

A bug report from the chair, not a planned wave: "quando iniciei o jogo battlefield a tela do
celular começou a piscar, como se tivesse abrindo e fechando o app". The panel slept and woke
while a game loaded on the Windows PC. The owner chose both fixes offered, and asked along the
way for a GIF of the spectrum for the README.

## What ran

**The diagnosis, from the server log alone.** The phone was not on adb, because this PC has no
`adb`. `%LOCALAPPDATA%\desk-panel\server.log` was enough:
- The 2 s `/ping` cadence broke into 4–8 s gaps. After each gap came `/ping`, `/spectrum`,
  `/quotes` and `/weather` together, which is the reload of an offline-to-online edge. That
  happened six times in ninety seconds.
- It was not `IDLE`, because IDLE keeps the 2 s cadence.
- `Win32_Process` showed `pythonw.exe` at base priority 6, BELOW_NORMAL. `Export-ScheduledTask`
  had no `<Priority>`, so the Task Scheduler's default of 7 applied.

The owner set the running process to Normal with one PowerShell line and reported "aparentemente
parou de piscar". That one measurement is what the rest rests on.

**T4.7** on `wave/44-ping-survives-a-busy-pc`, PR #72:
- `install_task.ps1` registers `-Priority 4`, and `Assert-TaskShape` reads it back.
- `verify_login_scope.py` adds `windows.task.priority`, which passes 4–6 only.
- The handwritten "good" fixture had carried `<Priority>7</Priority>`, the bug itself, since
  T3.8.
- A new real capture after the reinstall passes, and the old one now fails only on priority.
- `PcState.ONLINE_GRACE_FAILURES = 1`: one failed probe while ONLINE is ridden out.
- ADR 0010 and ADR 0005 record both changes.

The task was reinstalled on this PC. Both `pythonw.exe` and `spectrum-tap.exe` run at NORMAL
(base 8), and the verifier exits 0.

**The GIF** was captured in headless Edge over CDP from `web/` with `mock.js`, at the phone's
viewport (872×392 at DPR 1.25). It is 60 frames, 4.8 s, 217 KB. It does not come from the phone:
there is no adb here, and the fixture data also keeps the owner's real calendar off a public
README.

## What the review found

One fresh-context agent reviewed the diff read-only. It found no correctness bug and confirmed
the Task Scheduler priority mapping and the Java by reading, since no JDK is here. CI's
`./gradlew test` was green before the review. It made six findings, five applied and one
declined.

| Severity | Finding | What happened |
|---|---|---|
| Medium | No wave note, so `lint-notes` and CI's guards job were red. | Expected: the guard is red until the note exists. This note is the fix. |
| Low | `server.py` said "`PcState` flips to OFFLINE on a single failure". | Reworded. Its argument (a 30 s queue fails every ping) still holds. |
| Low | `PcPoller.TIMEOUT_MS` javadoc promised the offline marker within ~1.5 s. | Rewritten: from online it is ~4 s for a refused connection, ~8 s for one that hangs. |
| Low | `PcStateTest` comments: "a single failure is enough", "probe 10". | Reworded. |
| Low | `docs/TESTING.md` never said offline-from-online is two probes. | One paragraph added. The 20 s budgets still hold. |
| Low | An old Windows install now fails the verifier, but `after_update.py` printed only the summary line, with no next step. | The priority failure names `install_task.ps1`, and `step_login_scope` prints the first `[FAIL]` line. |

Declined: rewording CLAUDE.md's invariant 3. The grace counts probes, not time, so it is not a
timeout. ADR 0005 carries it, and the invariant text is the owner's.

## Where the rework went

- **`make wave-start` could not run.** This PC has no `make`, so its five commands were typed by
  hand. Every other `make check` target was run the same way, script by script. The protocol
  assumes a tool that one of the three desks lacks.
- **No Docker on this PC either**, so the Android half was verified only in CI. That held, but
  only because CI runs `./gradlew test`. The phone half is unmeasured.
- **The handwritten fixture encoded the bug as correct.** `<Priority>7</Priority>` in
  `windows_schtasks_good.xml` was copied from a default export. A fixture written from the
  defaults certifies the defaults.

## What is not proven

- **The grace on the phone.** The Redmi runs wave 43's APK. Build this one on the Mac or
  CachyOS, install it, and load a game on Windows: there should be no `state=offline`.
- **A stall two probes long** (about 5 s or more) would still blink. The priority fix should make
  that rare, but it is not measured.
- **Battlefield itself, after the reinstall.** "Parou de piscar" was observed with the
  hand-raised priority, not under the re-registered task.

## Cost

Seven prompts from the owner. Tokens and wall clock were not measured.
