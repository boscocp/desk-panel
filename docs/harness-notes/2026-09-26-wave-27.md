# Wave 27 — two buttons, and the one line between three green layers

**T8.2.** The panel can mute the PC it sits next to. Phase 8 is closed.

The wave's finding is not the feature. It is that the feature was written end to end, unit
tested, exercised in two themes in a real browser by a harness check written for it, built,
installed on the phone — and drew **no buttons at all**.

## What ran

**T8.2**, on `wave/27-two-buttons`, cut with `make wave-start`. Also a Windows runbook for T8.1's
unrun branch, asked for from the chair mid-wave.

`make check` green. 100 web tests, 311 server tests, the Android suite, and the browser harness
on both themes. **Verified on the device**: `action=mute-audio result=ok` in logcat and the PC's
sink and source actually moving.

## The bug three green layers could not see

`server/server.py` put `actions` in the payload. `web/` drew buttons for whatever `actions` held.
`android/` had a bridge, an allowlist and a POST. Every layer was right.

`DataPayload.merge` rebuilds the payload key by key on its way into the WebView, and nothing
named `actions`. The phone never saw the key.

The file's own comment, written when T6.4 shipped the identical bug two waves earlier:

> **This copy is the whole of the wiring, and forgetting it is silent, and it is true of every
> line above it as well.** The payload is rebuilt key by key rather than patched, so a key nobody
> names here simply does not reach the phone.

It was read **after** the failure, while looking for the cause. That is the whole lesson: a
warning sitting in the file a change has to touch is not a gate, and this is the second time this
exact one has been paid for. Two tests cover the key now and the comment names both occurrences —
which is the cheapest thing available and is still not a check.

The narrower version, which is the useful one: the browser harness proved the page, `./gradlew
test` proved the classes, and **neither could see the one line between them**. A five-minute
device install closed it, and that was only possible because the phone came back onto adb this
session.

## What the review found

Seven, and the two that matter are both **a button that is silently dead**, which is the exact
failure this task's own notes call worse than no button at all. Neither is visible in any of
the three green layers, and one of them reproduces in the browser harness in four lines.

- **A press abandoned by the panel going dark left the button dead for ever.** `forgetPresses`
  cleared the pending callbacks in silence. `PanelService` stops the poller on the transition
  down and `DataPoller.stop` calls `shutdownNow`, so the result for a press that was in flight
  when the PC went away never arrives — the theme's `busy` flag stays set, `press()` returns
  early on it from then on, and `renderShortcuts` will not rebuild it because the id set has
  not changed. Abandoned presses are settled as failures now.
- **The buttons vanished after a theme switch away and back.** `drawnActions` is module scope
  and `mount()` did not reset it, so a remount handed `renderShortcuts` an empty strip and a
  signature that still matched. Reproduced against `main` before the fix: `neon → plain → neon`
  draws nothing.
- **`check_actions.py` did not freeze `mock.js`.** Every other check in `e2e/layout/` stops the
  3s feed with `cl.FREEZE`; this one did not, and mock's payload carries **both** action ids, so
  a tick landing between a `deliver([])` and the query after it puts the buttons back and
  reports a correct panel as broken. Intermittently, which is worse than a failure.
- **The check was in no registry.** `docs/TESTING.md` still said "five checks", the
  `e2e/layout/README.md` table listed four siblings, and `docs/THEMING.md`'s "Checking it"
  block — directly under the new section telling a theme author what to implement — did not
  name the one check that verifies it. A sixth check nobody lists is a check the next wave does
  not run.
- **The action POST gave the PC 5s; the server allows itself 15s on Windows.**
  `actions.timeout_for("win32")` is 15s because the mixer call there is PowerShell handing C#
  to `Add-Type`. The phone would have given up first, logged `result=err`, and made the button
  say it failed on a PC that then mutes — on the one platform the runbook above says has never
  run. The POST has its own `ACTION_TIMEOUT_MS` now; connecting still gets 5s, so an absent PC
  is still refused fast.
- **`settle` could run twice for one press.** Core answers a refusal through the callback *and*
  through its return value, and both themes' `settle` ran on both, leaving two fade timers on
  one button. Both are idempotent now, and each cancels the previous fade on the next press —
  without that, the old acknowledgement's timer fires part-way through the new press and puts
  the resting caption back on a button that is still sending.
- **`Markers.action` logs a string the page made up** on its two refusal paths, which its own
  javadoc denied. Control characters are stripped: a marker is what every E2E assertion reads
  (ADR 0009), and a candidate carrying a newline would let the page write its own
  `action=… result=ok` into logcat.

`make check` green afterwards, and `check_actions.py` and `check_layout.py` pass on both themes.

Verified by command so far: every acceptance line in the task file, the browser harness on both
themes, and three mutations of the new `check_actions.py` — a 30px target, the offline guard
removed from `app.js`, and `shortcutsFor` made permissive. Each turns it red.

## The chair changed a rule, and the fix was to stop guessing

The buttons went on the panel and four asks came back: no caption, a bigger icon, **a cross when
the PC is muted**, and a border being shaved off by `#sidebar`'s `overflow: hidden`.

Three are visual. The cross contradicts T8.2 step 7 as written — *"shows the last result, not a
live state"* — and step 7 said that for a good reason: every Linux mixer toggles in silence, so
`state` came back `unknown` on every press and the panel had nothing honest to draw.

The interesting part is that **the rule did not have to be relaxed**. The server runs a second,
**read-only** command after the toggle and reports what the mixer actually holds. The cross is
now the PC's own answer rather than the panel's inference, and the sentence step 7 exists to
protect — a button that says the microphone is off while it is live is a privacy failure — is
untouched. ADR 0015 carries the three limits: it is the *last known* state and the accessible
name says so, a failed press does not move it, and a read-back that fails is `unknown` rather
than a failed action.

That is the shape worth keeping: **an ask that appears to contradict a written rule is often an
ask to make the rule's premise false.** The premise here was "the panel cannot know", and it cost
one extra local process per press to stop being true.

The clipped corner deserves its own line. The fix is 6px of clearance and **6 rather than less
because the burn-in shift moves the whole panel up to 4px** — a 2px margin would have looked
right in every screenshot and brought the cut back for part of every cycle.

## What is not proven

- **The twenty-taps check was not done.** Each button was pressed four times and every toggle
  landed; nobody hammered one to watch `/ping` keep its beat while presses queue on the poller's
  single thread.
- **`invoke`'s `rejected` path has never run on the device.** An id that reaches Java and is not
  in `Actions.ALLOWED` has unit tests and no way to happen in production, because no theme can
  produce one — which is the point, and also why it is untested where it matters.
- **macOS and Windows mute are still unrun** (T8.1, unchanged). `tasks/T8.1-actions-execute.md`
  now carries a seven-step Windows runbook, ordered so each step fails faster than the one after
  it, written after the chair asked for one mid-wave.
- **The read-back is Linux-only in practice.** macOS and Windows toggles end on a word and never
  reach it, so the `state` those platforms report has never been produced by anything but a unit
  test — on top of their toggles never having run at all.
- **The night profile over the buttons was not seen.** `:root[data-night="on"] .shortcut` dims
  them; that rule has been read and not looked at.

## Where the rework went

Three places, and the third is mine rather than the code's.

- **The plain theme overflowed.** Stacking the 56px buttons under the device line cost the
  columns 66px, and `check_layout.py --theme plain` reported `#quotes` hiding 42px of rows without
  scrolling — a card eating a row in silence, which is the one thing T6.6 forbids. They share one
  row now. The harness caught it in the first run after the buttons landed.
- **`check_actions.py` failed on `--theme plain` and passed on `neon`**, because its injected
  payloads carried no `theme` key — so `host.useTheme(undefined)` fell back to neon and the panel
  switched out from under the run. `check_blackout.py` had already solved this and the solution
  was not copied. A check that only works on the default theme is half a check.
- **`git checkout -- web/js/format.js` destroyed this wave's work in that file.** It was used to
  undo a deliberate mutation, and the file held every uncommitted change of the wave — the
  language strings, `shortcutsFor`, the export. Every other mutated file had a `cp` backup taken
  first; this one used git, on a file git had nothing of. Redone from the transcript, and the rule
  is one line: **to undo a mutation, restore the copy you took, never the index.**

## What the second look cost, and what it caught

The review's own two high findings were both **a button that is silently dead**, and one of them
was reproduced first-hand rather than taken on trust: with the fix backed out, `neon → plain →
neon` renders zero buttons. `check_actions.py` had not switched themes, so it could not see it.
It does now, and so does the cross assertion — mutation-tested by making the cross always visible,
which turns three cases red.

The pattern across this wave is the same three times: **the check written alongside a feature
tests the path the author was thinking about.** The device found the missing payload key, the
review found the theme switch, and the chair found a clipped border. None of them were things a
green suite could have been expected to notice, and all three were cheap to assert once someone
had looked.

## Cost

Not measured. Five prompts from the chair, and two of them were interruptions worth more than the
wave: *"a 8.1 foi feita ou n? nao entendi"* — which is a real answer about how the phases were
split, and the sign that a server-only task is invisible from the desk — and *"nao apareceu o
botao"*, which is how the `DataPayload` bug was found at all.

The panel was dark at the start of this session with the PC plainly on, and that turned out to be
the MIUI trap the root `CLAUDE.md` names, seen with markers for the first time: `PanelService`
polling `ping=ok` every two seconds into an Activity that was gone.
