### Line 5 is a defect in the task file, not in the model

`node --test "web/test/**/*.test.js"` fails in all four reps because `web/test/`
contains nothing but `.gitkeep`, and **T1.2 never asks anyone to write a test** —
that is TT.1, a separate row that pairs with this one. As written, T1.2 cannot
pass. Four reps, four identical failures, zero information about the model.

This is the same family as the T1.1 finding: an acceptance block that is not
coupled to what the task actually asks for. There the coupling was too loose (a
negated grep that passes on an empty tree); here it is too tight (a command that
depends on a different task's deliverable).

Discounting line 5, the model-attributable score is **4/4, 3/4, 3/4, 4/4**.

### Lines 2 and 4 are the model, exactly where the routing doc predicted

`docs/LOCAL-MODELS.md` says the measured weakness is "surgical edits to existing
code, where it repeatedly misses the anchor text", and that writing new files
plays to its strengths. T1.1 was greenfield and scored 4/4 four times. T1.2 asks
it to **extend** `index.html` and `app.js`, and:

- **R3 broke `app.js`.** `node --check` fails at line 6, `SyntaxError: Unexpected
  token '}'` — a stray brace left by an edit. The file was valid before the run.
- **R2 shipped the mock unguarded.** `<script src="js/mock.js"></script>`, no
  condition. The task's own words: load it "only when there is no native bridge,
  so it never ships active inside the APK". That is a real product defect, and
  **line 4 caught it** — the acceptance block doing exactly its job, in useful
  contrast with the T1.1 round where four green commands certified a stylesheet
  that 404s.

All four wrote `web/js/mock.js` and extended the two existing files.

| Q2 | nothing in the harness interrupts a flood | **confirmed**, by code rather than by occurrence: there is no bound (`grep` for a tool-call limit returns nothing), `defaultReasoningByteLimit` says in its own comment that it "does not cancel generation" and covers reasoning only, and the 300 s watchdog is an **idle** timer that never fires while data flows |
| Q3 | T1.2's acceptance is harder than T1.1's and some rep fails | **confirmed**, 4 of 4 — though for a reason that is the task file's fault |
| Q4 | the negated `! grep` is mangled again | **confirmed** — no rep ran the acceptance block as written |
| Q5 | at least one rep reports an exit code that does not match mine | **confirmed** |

Q1 is the interesting miss. R1 ran 1 162 s and burned 67 884 completion tokens
without a flood: it degenerated into **verbosity**, not repetition — 194 780
characters of reasoning for a task whose deliverable is one 40-line file. The
failure mode is real but its shape is not stable across tasks, which is worth
remembering before anyone designs a detector around one observation.

## What this round produced upstream

R1's reasoning trace became the evidence for a review of
[#8085](https://github.com/esengine/DeepSeek-Reasonix/pull/8085), an open PR that
adds a client-side repetition guard. Fed the reasoning and visible text of all
eight sessions from both rounds, that guard aborts one — R1 — at 30% of its run,
on the segment `\`\`\`javascript`, because a Markdown fence with a 13-rune language
name clears its 12-rune floor. `"let's do it."` is twelve runes and sits on the
same floor.

The same constant is why the guard would **not** have caught the T0.1 run-2
degeneration: 35 197 hyphens, one rune each, all discarded before counting.

Both directions are in the review, with a deterministic test each.

## Where the effort goes next

This round closes the question the two-agent setup was opened to answer. The
local model is not the limiting factor: given a task it is routed to, it
delivers — 4/4 on T1.1, and 4/4, 3/4, 3/4, 4/4 on T1.2 once the unpassable
criterion is discounted. Every lever for making it *better* has now been measured
and falsified (`notas/estudo/metodo.md` carries the table: temperature is omitted
from the wire, `num_ctx` is not a per-request knob on `/v1`, restricting the tool
registry breaks capability routing, a `stop` sequence erases the answer instead of
truncating it, and an output cap never binds on a real task).

What does limit the arrangement is **trust**, and that is not a model-size
problem. A run invented four exit codes; another edited `STATUS.md` to mark its
own task done; the `verifier` inverted a passing tree; and `outcome: success`
means only that `Run` returned nil. A larger model makes each of these rarer, not
absent — which is why the ADR's "never accept the report" rule is written the way
it is.

So the local model's remaining value here is as a **cheap generator of
pathology**: it produces the leaked template markers, the tool-call floods and the
195 000-character reasoning traces that a well-behaved model never emits, and
those are what expose harness defects. Both upstream contributions of the last
three days came out of its failures, not its successes.
